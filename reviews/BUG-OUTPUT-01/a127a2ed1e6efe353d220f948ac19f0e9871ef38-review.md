## Blocking finding

### P2 — bundled yt-dlp short-option clusters bypass the pre-execution `-o` / `-P` model

The current static preflight parser does not fully model Python `optparse` short-option clustering, while the bundled yt-dlp runtime does. This leaves two physical output-confinement escape shapes under one root cause.

### 1. Clustered `-o` can still select an absolute output outside owned staging

Current `YtdlpCommandOutputTemplateParser` recognizes only a token equal to `-o`/`--output`, `--output=...`, or a token beginning directly with `-o` (`YtdlpOutputPlan.kt:553-566`). A clustered token such as `-qo...` or `-vqo...` does not meet those branches and can therefore yield `YtdlpCommandOutputTemplateResolution.None` even though bundled yt-dlp interprets the same token as `-q -o ...` / `-v -q -o ...`.

Independent bundled-runtime probes at the reviewed SHA showed:

- `-qo/owned-escape.%(ext)s` -> effective `outtmpl.default=/owned-escape.%(ext)s`;
- `-qo /owned-escape.%(ext)s` -> the following token is the `-o` value;
- `-vqo/owned-escape.%(ext)s` -> effective absolute output template;
- with owned `-P home:/owned/staging` and `-P temp:/owned/staging`, `prepare_filename()` for `-qo/escaped/out.%(ext)s` resolves to `/escaped/out.m4a`.

`resolveOutputPlan()` relies on that parser before the Worker builds the native phase (`YTDLPUtil.kt:1590-1608`, `DownloadWorker.kt:1463-1494`). Because the cluster is missed, the pre-native boundary is crossed. An absolute output template then defeats the intended owned `--paths` location and produces an unowned physical filesystem side effect before later provenance can reject it.

### 2. Clustered `-P` in non-command `extraCommands` can override app-owned staging

Current `YtdlpCommandPathParser` recognizes `-P`, `--paths`, `--paths=...`, and tokens beginning directly with `-P` (`YtdlpOutputPlan.kt:177-186`). The current regression suite explicitly classifies `-qP /shared/unmodelled-cluster` as `None` (`YtdlpOutputPlanTest.kt:129-132`). That is not the bundled runtime behavior: yt-dlp interprets `-qP /path` as `-q -P /path`.

For non-command downloads, `resolveOutputPlan()` treats `YtdlpCommandPathResolution.None` as acceptable (`YTDLPUtil.kt:1610-1623`). Production request ordering then places the app-owned `-P` first (`YTDLPUtil.kt:2570`) and appends raw non-command `extraCommands` later (`YTDLPUtil.kt:2607-2611`). The bundled runtime probe confirmed:

- app `-P home:/owned/staging -P temp:/owned/staging` followed by `-qP /escaped/home` -> effective paths `{home: /escaped/home, temp: /owned/staging}`;
- `prepare_filename()` then resolves the normal media output under `/escaped/home/...`.

Thus the extra-command cluster can supersede the app-owned home staging after preflight classified it as no path override.

For `DownloadType.command`, the raw command is placed before the generated owned home/temp `-P` entries (`YTDLPUtil.kt:2592-2601`), so the same clustered `-P` does not by itself escape the actual write in that ordering; the bundled probe showed the later app-owned paths win. Nevertheless, the parser should model the actual effective cluster semantics so command final-destination intent and non-command rejection policy are derived from the same real parser behavior rather than from token-prefix approximations.

## Required remediation boundary

Before any output-producing native yt-dlp execution, preflight must model or reject every effective short-option cluster that can carry output/path semantics according to the actual bundled yt-dlp parser.

At minimum:

1. Model `-o` inside valid short-option clusters, including attached and following-token values such as `-qoVALUE`, `-qo VALUE`, and multi-flag forms such as `-vqoVALUE`.
2. Pass the resulting effective output template through the same existing confinement validator as ordinary `-o`/`--output`; unsafe absolute/traversal/unprovable templates must fail before the native boundary.
3. Model `-P` inside valid short-option clusters, including `-qP VALUE` and `-qPVALUE`, according to real bundled `optparse` value-consumption/ordering semantics.
4. For non-command `extraCommands`, any effective clustered path override that can appear after app-owned staging must be rejected before execution, or the request must be transformed/reordered in a way that proves app-owned staging remains the effective native destination.
5. For `DownloadType.command`, preserve the established final-destination semantics for supported authored paths while retaining the later generated home/temp staging rewrite that confines the actual native write.
6. Do not globally ban safe relative `-o` templates merely to avoid parsing the cluster; safe supported forms should remain usable where confinement is provable.
7. Do not recover an escaped output after execution through basename coincidence, directory rescans, mtime/recent-file heuristics, or file absence at attempt start.

The implementation should share one effective-option interpretation model where practical rather than maintaining contradictory cluster behavior between the output-template parser and path parser.
