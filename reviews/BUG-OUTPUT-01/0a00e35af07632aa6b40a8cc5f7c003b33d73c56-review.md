## Blocking finding

### P2 — custom `-o/--output` can bypass operation-owned staging before provenance rejection

The production custom-command path still allows user-authored `-o/--output` semantics that can cause yt-dlp to physically write outside the operation-owned staging root before the later provenance checks reject the escaped path.

Relevant production chain at the reviewed checkpoint:

1. a `DownloadType.command` stores the user command in the download format note;
2. the production argument builder preserves that raw custom command;
3. the app appends generated owned `-P home:<staging>` and `-P temp:<staging>` arguments;
4. policy blocks external config/process-spawning/external-ffmpeg classes of escape, but does not yet fully parse/confine `-o/--output`;
5. yt-dlp semantics allow an absolute output template to defeat the intended `--paths` confinement;
6. the later provenance layer can reject the escaped output as unauthoritative, but the physical unowned filesystem side effect has already occurred and may remain behind.

This is not currently a P0 authority-escalation finding: the review did not find proof that the escaped file becomes authoritative for verified quality, History persistence, replacement deletion, or later destructive consumers. It is nevertheless a P2 blocker because the owned-staging/output-confinement contract is not closed before the native output-producing boundary.

## Required remediation boundary

Before native yt-dlp output production starts, the app must either:

- prove every effective output-producing `-o/--output` template is confined to the operation-owned staging model after the app's rewrite/normalization rules, or
- reject the command before execution.

The remediation must not authorize an escaped file after the fact and must not recover authority through basename coincidence, directory rescans, mtime/recent-file heuristics, or file absence at attempt start.

At minimum, the implementation-side audit/test matrix must classify:

- absolute output templates;
- statically escaping relative/traversal templates such as `../...` after normalization;
- safe relative templates such as `%(title)s.%(ext)s`;
- safe nested relative templates where confinement is provable;
- attached and separated `-o` / `--output` forms;
- typed output templates and repeated declarations according to the actual bundled yt-dlp semantics;
- malformed or ambiguous templates that cannot be proven safe;
- special output semantics such as `-o -` and typed empty templates, explicitly rather than accidentally.

## Required production evidence

Positive real-Worker coverage should demonstrate that a safe relative custom output actually executes inside operation-owned staging and publishes only through exact authoritative publication results.
