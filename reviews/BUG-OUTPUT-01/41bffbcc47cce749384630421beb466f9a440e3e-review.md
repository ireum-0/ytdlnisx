## P2 blocker — fixed-arity multi-argument options can grant false destination authority

### Runtime semantics

The bundled app dependency remains `io.github.junkfood02.youtubedl-android:library:0.18.1`, and the inspected bundled yt-dlp release surface is `2025.11.12` (`RELEASE_GIT_HEAD=335653be82d5ef999cfc2879d005397402eebec1`). In that parser:

- `--alias` has `nargs=2`;
- `--print-to-file` has `nargs=2`;
- `--replace-in-metadata` has `nargs=3`.

For example, actual Python optparse argument grouping for:

```text
--replace-in-metadata title -P /tmp/metadata-replacement
```

consumes `title`, `-P`, and `/tmp/metadata-replacement` as the three values of `--replace-in-metadata`. `-P` is data, not a path option. The same is true for `-o`. The unambiguous abbreviation `--replace-in-met` follows the same arity. An equals form such as:

```text
--replace-in-metadata=title -P /tmp/metadata-replacement
```

uses the inline `title` as the first value and still consumes the next two tokens as values.

### Current app parser mismatch

`YtdlpCommandPathParser` / `YtdlpCommandOutputTemplateParser` model generic option consumption as a Boolean `consumesFollowingToken`. For a value-taking long option they skip exactly one following token. They do not model fixed `nargs > 1`.

Consequently, for command text such as:

```text
--replace-in-metadata title -P /some/writable/directory
```

the app skips only `title`, then interprets the data token `-P` as an effective destination option and returns `YtdlpCommandPathResolution.Explicit`.

The analogous `-o` form can be falsely interpreted as an output template and rejected even though yt-dlp treats it as metadata-replacement data.

This gap is not newly introduced by the `41bffbcc...` cluster change. The one-value consumption model already exists at `a127a2e...`, and the older `0a00e35...` path parser would also interpret a later `-P` token without accounting for the preceding multi-argument option. Attribution therefore does not change the blocking status.

### Production consequence

This is not limited to a helper-level false positive.

For `DownloadType.command`, `YTDLPUtil.resolveOutputPlan()` trusts an `Explicit` command path map as destination authority:

- `finalDestination = commandPathMap.home`;
- `explicitCommandPath = true`;
- `directNoCache = true`;
- the operation-owned staging parent is derived from the parsed command path when no separate temp path exists.

`buildYoutubeDLRequest()` writes the authored command into the generated yt-dlp config before the app-generated owned `-P home:<staging>` / `-P temp:<staging>` entries. The generated config is later parsed by yt-dlp with shlex/optparse semantics.

Therefore the actual native parser treats the authored `-P` above as metadata data, while the app has already treated the same token as final-destination authority. The generated owned `-P` values still confine native media production to the operation-owned staging directory, but that staging directory and the later publication destination were selected from a token that yt-dlp never interpreted as a destination.

The Worker then:

1. accepts only exact current-attempt files under the owned staging root through `DownloadOutputProvenance`;
2. passes those exact authoritative source files to `FileUtil.moveFile(..., destDir = downloadLocation, sourceFiles = ...)`;
3. records only exact move/copy results with `recordMoveResults()`;
4. promotes those exact results to `finalPaths`;
5. writes `finalPaths` into History and uses them in the existing authorized replacement/cleanup flow.

So provenance remains exact, but the publication destination itself is parser-false. A valid metadata replacement containing a path-looking replacement value can reroute an otherwise authoritative current download to a directory the actual yt-dlp command did not select. This violates BUG-OUTPUT-01 destination/confinement authority and blocks CLEAN.

### Config sanitization coupling

The generated-config rewrite in `YtdlpArgumentPolicy.stripExternalFfmpegLocationOptionsWithReport()` also scans tokens as if every blocked-looking token is an option with at most one value. A blocked-looking string may itself be data owned by a preceding multi-argument option. The correction must therefore keep pre-execution validation and config sanitization on the same arity-aware token ownership model; fixing only the path parser can leave app/native effective semantics divergent after sanitization.
