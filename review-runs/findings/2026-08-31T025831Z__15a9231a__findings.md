## BUG-UNDO-03 — Failed in-flight removal Undo can resurrect dead lifecycle authority after the abandonment scan

- Severity: **P2**
- Evidence: **SOURCE-LEVEL ONLY**
- Reviewed checkpoint: `15a9231a02a1c5687663f071d851e23c6ad9bd9f`
- Attribution: **incomplete closure / remediation follow-up** in the live Undo-authority handoff remediation, classified only after correctness and dedup review.

### Scope / invariant

A process-local pending-removal Undo owner may disappear only if the exact token is either durably resolved or transferred to a guaranteed successor executor. A fallible resolver must not make its token temporarily invisible to lifecycle abandonment and then restore that token as "live" after the owning ViewModel has already been cleared.

### Concrete production-reachable failure path

1. In `SavedDownloadsFragment`, a left swipe calls `DownloadViewModel.deleteDownloadForUndo(itemID)`, receives a `DownloadUndoHandle`, and shows an indefinite Snackbar. The Undo action calls `restoreDownloadUndoFromUi(handle)`; Snackbar dismissal calls `commitDownloadUndoFromUi(handle)`. Both UI entry points launch the work in the activity-owned `DownloadViewModel.viewModelScope`.
2. `DownloadRepository.deleteForUndo()` has already deleted the Download row, retained the linked low-quality child as exact `CANCELLATION_REQUESTED` pending-removal debt where applicable, registered `livePendingRemovalTokens[token]`, and stored `pendingRemovalSnapshots[token]` with the repository/ViewModel `ownerId`.
3. `restoreUndo(token)` begins resolution by executing `pendingRemovalSnapshots.remove(token)` **before** entering the fallible Room restore transaction. `commitUndo(token)` has the same structure: it removes the exact snapshot before its fallible commit transaction. On failure, each catch block simply re-inserts `pendingRemovalSnapshots[token] = snapshot` and rethrows; the live pending-removal token remains registered because unregister occurs only on success.
4. While the snapshot is temporarily absent, the activity/ViewModel can be cleared. `DownloadViewModel.onCleared()` starts the detached lifecycle handoff `repository.abandonPendingUndoSnapshots()`.
5. `abandonPendingUndoSnapshots()` inventories only the repository-owned entries currently present in `pendingRemovalSnapshots`. Because this token was removed by the in-flight resolver, it is absent from `ownedRemovalEntries`, absent from `successorTokens`, and therefore no `LowQualityRedownloadLedger.scheduleAbandonedUndoConvergence(dbManager, token)` successor is published for it. The handoff also cannot unregister/consume the token because it never observed the missing snapshot.
6. The in-flight `restoreRemovalSnapshot()` or `commitRemovalSnapshot()` then throws — for example a Room/SQLite persistence failure, or cancellation/failure of the ViewModel-owned coroutine while resolving the transaction. Its catch block re-inserts the old snapshot after the lifecycle abandonment scan has already completed.
7. The ViewModel/Snackbar owner is now gone, but process memory again contains the snapshot and still reports `isLivePendingRemovalToken(token) == true`. No token-scoped abandoned-Undo job was installed because the lifecycle handoff missed the temporarily removed entry.
8. The durable low-quality row remains the exact pending-removal `CANCELLATION_REQUESTED` carrier and the Download row remains absent after the failed transaction. Generic abandoned-debt reconciliation cannot rescue the live process: `LowQualityRedownloadRepository.reconcileAbandonedUndoItem()` explicitly returns `false` for a pending-removal token while `DownloadRepository.isLivePendingRemovalToken(token)` is true.
9. The application can therefore remain in the same live process with a dead UI owner represented as live authority, no successor executor, a deleted Download row, and nonterminal linked debt. Process restart eventually clears the in-memory false-live token and startup reconciliation can consume the durable carrier, but ordinary process survival has no guaranteed progress path.

The race is reachable through both user-visible resolution choices: explicit Undo (`restoreUndo`) and Snackbar commit/dismissal (`commitUndo`). It needs only the legal concurrency order `snapshot remove -> lifecycle abandonment inventory -> resolver persistence failure -> snapshot reinsert`.

### Why this is a substantive correctness defect

The new lifecycle handoff relies on the process-local snapshot map as the authority inventory from which successor jobs are created. `restoreUndo()` and `commitUndo()` temporarily remove an exact owner from that inventory before their durable resolution succeeds, then can resurrect the entry if durability fails. That breaks the carrier-to-carrier handoff invariant: a token can outlive its actual owner while still positively blocking the recovery path intended for abandoned debt.

This is more than delayed UI cleanup. For a linked low-quality replacement the child remains nonterminal `CANCELLATION_REQUESTED`; the corresponding Download row is absent; and same-process recovery intentionally refuses to consume the token because it appears live. The state can remain stuck until process restart.

### Dedup / candidate-rejection discipline

- **Not `BUG-UNDO-01`:** that finding begins when lifecycle abandonment successfully observes an owned token, releases the old owner, and then the first successor convergence read/write fails. `BUG-UNDO-03` fails earlier at the concurrency boundary: the resolver temporarily hides the token, so lifecycle abandonment never inventories it and never creates the successor owner at all; the resolver failure then resurrects stale authority after the owner has died.
- **Not `BUG-UNDO-02`:** that finding concerns a stronger rollback-capable Room transition deleting process-local pending-cancellation authority before durable commit. This path concerns pending-**removal** snapshot resolution racing lifecycle teardown; no stronger transition needs to commit or roll back an owner-map deletion.
- No `TASKS.md` or `TASKS_DELTA.md` finding found during dedup owns the exact invariant "a fallible in-flight removal-Undo resolver may not become invisible to lifecycle abandonment and later resurrect the dead owner." Existing History/Log Undo defects concern different persistence graphs.
- Do not reject because process restart repairs the carrier. v4 requires same-process recovery ownership and cross-attempt closure; startup-only repair is insufficient for an ordinary lifecycle race while the process remains alive.
- Do not reject because map removal is intended to serialize two UI resolutions. Temporary absence is semantically observable by `abandonPendingUndoSnapshots()`, which uses the map itself as the successor-publication inventory. Therefore the intermediate state is an authority mutation, not an implementation-private detail.

### Required result

- Make pending-removal resolution and lifecycle abandonment one exact token state machine instead of using temporary map absence as the resolver claim.
- Keep an in-flight `RESOLVING(ownerId, token)` state visible to lifecycle handoff, or otherwise synchronize resolver claim/rollback with lifecycle abandonment so a token cannot disappear from successor inventory.
- If restore/commit fails after its owner has been cleared, do **not** blindly reinsert a live snapshot. Atomically mark/transfer the exact token as abandoned and ensure a token-scoped same-process successor owns convergence before returning/rethrowing.

### P2 — BUG-UNDO-03 — Prevent failed in-flight removal Undo from resurrecting dead lifecycle authority

**State:** Open  
**Reviewed checkpoint:** `15a9231a02a1c5687663f071d851e23c6ad9bd9f`  
**Verification:** `SOURCE-LEVEL ONLY`

**Failure path:** Saved-download swipe deletion stores an owner-tagged pending-removal snapshot and exact live token, then the Snackbar resolves through `DownloadViewModel.restoreDownloadUndoFromUi()` or `commitDownloadUndoFromUi()`. `DownloadRepository.restoreUndo()` and `commitUndo()` both remove `pendingRemovalSnapshots[token]` before their fallible Room transaction and reinsert it on exception. If `DownloadViewModel.onCleared()` runs while that snapshot is temporarily absent, `abandonPendingUndoSnapshots()` cannot inventory the token and therefore publishes no `scheduleAbandonedUndoConvergence()` successor. If the in-flight restore/commit then fails, its catch re-inserts the snapshot after lifecycle teardown while the live pending-removal token is still registered. The UI owner is gone, but `reconcileAbandonedUndoItem()` refuses to consume pending-removal debt while that stale live token remains. The Download row stays absent and the linked child can remain `CANCELLATION_REQUESTED` until process restart clears the false-live process state.

**Why this is a defect:** temporary snapshot removal is observable authority state because lifecycle abandonment uses the same map as its successor-publication inventory. A resolver failure can therefore resurrect a dead owner and suppress the only same-process recovery path for durable nonterminal debt. Startup repair does not close ordinary live-process lifecycle correctness.

**Dedup:** distinct from `BUG-UNDO-01`, where lifecycle abandonment observes/transfers the token and the successor's first read/write fails, and from `BUG-UNDO-02`, where a stronger rollback-capable transaction prematurely destroys pending-cancellation authority. No canonical `TASKS.md`/`TASKS_DELTA.md` entry owns this pending-removal resolver-vs-lifecycle visibility race.

**Ownership / attribution:** incomplete closure / remediation follow-up in live Undo-authority handoff remediation.

Required result:
- represent resolver claim and lifecycle abandonment with an exact token state that remains visible across fallible persistence;
- prevent failed restore/commit from reinserting a token as live after its owner is cleared;
- publish/retain a token-scoped same-process successor whenever teardown wins the race;
- preserve exact-token sibling isolation and startup recovery across process death.

Focused verification requirements:
- real Saved-download UI/ViewModel/Room race with restore and commit paused after snapshot claim, lifecycle clear, then first/later persistence failure;
- ViewModel cancellation variant, success-vs-teardown control, successor read/write failure, sibling-token isolation, and process-death boundaries;
- verification must exercise actual lifecycle + Room + reconciliation wiring. Current verification is `SOURCE-LEVEL ONLY`.

## Ready-to-merge `REVIEW_LESSONS.md` entry

### BUG-UNDO-03 — temporary owner-map absence is a lifecycle-visible authority mutation

- **Reviewed checkpoint:** `15a9231a02a1c5687663f071d851e23c6ad9bd9f`
- **Why previous reviews missed it:** the prior Undo reviews examined deliberate owner abandonment, successor retry, and stronger-transition rollback, but treated the common `remove -> fallible operation -> reinsert on failure` pattern as local exception safety. They did not treat the temporary map absence as externally observable to a concurrent lifecycle handoff that uses that same map as the source of truth for successor creation.
- **Concrete blind spot / incorrect stopping assumption:** review assumed restoring the snapshot in the resolver catch restored pre-call semantics. That is false once `onCleared()` can run during the absence: lifecycle teardown may already have concluded that the owner has no token to transfer. Reinsertion then restores data but resurrects authority that no longer has an owner.
- **Relevant v4 items:** first authoritative observation, carrier-creation gap, helper-internal throwable window, semantic preservation, first-write fault injection, recovery semantic identity, post-commit barrier, expected-identity mutability, concurrency/sibling isolation, cross-attempt matrix, and CLEAN gate. They were previously applied to release-before-write and successor-write failures, but not to temporary removal/rollback patterns inside process-local owner registries.
- **General lesson:** any process-local map/set/lease used by lifecycle revocation or recovery discovery is an authoritative registry. Temporarily removing an entry to claim exclusive work is a semantic authority transition if another actor can observe the absence. A fallible operation may not simply reinsert the old entry unless it proves the original owner is still alive; otherwise it can resurrect dead privilege and suppress recovery.
- **Concrete proposed checklist improvement:** whenever an authority registry uses `remove/claim -> fallible work -> reinsert/restore on failure`, race every lifecycle stop/revocation/recovery inventory between claim and rollback. Require an explicit `RESOLVING` or equivalent state visible to the revoker, or atomic synchronization proving rollback cannot resurrect a dead owner.
- **Suggested checklist wording:** “For every process-local authority/owner registry, enumerate temporary claim patterns that remove or hide an entry before fallible work. Race lifecycle teardown, revocation, recovery discovery, and sibling cleanup after the hide but before success/failure rollback. PASS requires that the revoker can still discover/transfer the exact authority, or that a failed claimant proves the original owner remains live before restoring it. Never allow rollback/reinsertion to resurrect privilege after its lifecycle owner was abandoned.”
- **False-positive guard:** do not report a defect when temporary absence is protected by a mutex/atomic state machine shared with all revocation and recovery observers, when failure restoration occurs only after proving the exact owner is still live, or when the hidden entry is purely advisory and cannot gate destructive work, retry, recovery, or semantic authority. Require a concrete interleaving where the observer acts on absence and later reinsertion changes correctness.
- **Disposition: PROPOSED**
