## `BUG-LOG-02` — P2 — Clear Download Logs can delete a newly claimed live execution's log after a stale idle observation

- Provisional ID: `BUG-LOG-02`
- Severity: **P2**
- Reviewed checkpoint SHA: `5221f50075173c82d9a3b68a673096a5850ad09f`
- Evidence: **SOURCE-LEVEL ONLY**
- Attribution: pre-existing baseline defect discovered after the ledger split; correctness and dedup were decided before attribution.

### Scope / invariant

The user-facing **Clear Download Logs** operation deliberately refuses to run while a Download or Terminal execution is active. Once that idle-only policy is the safety condition for destructive log deletion, the implementation must preserve it through the destructive commit: either hold an authority/lock that prevents a new execution from acquiring a log until deletion finishes, or revalidate the authoritative active-execution state at the deletion boundary and abort if the world changed. A point-in-time idle observation is not authority to delete logs created by a later execution.

This invariant is distinct from `BUG-LOG-01`. `BUG-LOG-01` already owns the non-atomic relationship mutation in log deletion/Undo and explicitly notes that Delete All splits `LogDao.deleteAll()` from `DownloadDao.removeAllLogID()`. The defect here remains even if those two Room statements are made one transaction: a new execution may be claimed and create its log **after the idle observation but before that transaction starts**, in which case a transaction containing `DELETE FROM logs` still deletes the live generation's log.

### Complete concrete production-reachable failure path

1. Logging is enabled (`log_downloads=true`) and at least one Download is queued but not yet Active. This is ordinary production state; `DownloadWorker` continuously observes queued work and can claim an eligible Download asynchronously.
2. The user opens Folder settings and invokes **Clear Download Logs**.
3. `FolderSettingsFragment.clearDownloadLogs()` calls `hasActiveDownloads()`. That helper independently queries `downloadViewModel.getActiveDownloadsCount()` and `terminalDao.getActiveTerminalsCount()` and returns a Boolean snapshot. There is no Download-worker execution lock, per-Download side-effect lease, Room transaction spanning the check and delete, scheduler fence, or maintenance token retained after the read.
4. At this instant both counts can legitimately be zero, so `clearDownloadLogs()` proceeds.
5. Before the subsequent IO block executes `db.logDao.deleteAll()`, the already-running/eligible `DownloadWorker` observes the queued Download and takes the normal production admission path. `claimDownloadThroughProductionAdmission()` publishes a fresh exact `executionId` and transitions that Download into the running ownership set/Active state under the worker's own execution synchronization. The Folder-settings coroutine does not participate in that synchronization, so this claim is not excluded by the earlier idle read.
6. `DownloadAttemptRunner.run()` reaches `prepareYtdlpPhase()`. With logging enabled, that function first validates exact Download ownership, then under `withOwnedExecutionSideEffect(downloadItem)` inserts a fresh `LogItem` through `LogRepository.insert()`, assigns the returned ID to `downloadItem.logID`, and subsequently persists the owned running Download row via `downloadDao.updateIfExecutionOwnedAndRunning(...)`. The log is therefore the current execution's real diagnostic carrier, not stale historical data.
7. The Folder-settings IO block now runs `db.logDao.deleteAll()`. `LogDao.deleteAll()` is an unconditional `DELETE FROM logs`; it has no execution identity predicate and no final active-work revalidation. It therefore deletes the just-created live Log row.
8. The same maintenance block then calls `db.downloadDao.removeAllLogID()`, an unconditional `UPDATE downloads SET logID=null`. It can detach the live Active Download from the exact log ID that `prepareYtdlpPhase()` just published. The ordering can also interleave more narrowly: if `deleteAll()` wins after log insert but before the worker's Download-row update, the worker may later persist a `logID` that points at a row the maintenance operation already deleted.
9. The active yt-dlp attempt continues. `createYtdlpProgressCallback()` routes log writes through `LogRepository.update(redactedLine, runtime.logId)`. `LogRepository.update()` wraps the DAO operation in `runCatching` and discards failure, so loss of the current Log row does not force the Download attempt to stop or reconstruct its diagnostic carrier. The execution can therefore continue while its log silently disappears or its `Download.logID` becomes null/dangling depending on the interleaving.
10. There is no startup reconciliation that reconstructs a deleted Log row from the live/finished Download execution, and retry/re-entry does not restore the lost log content for this attempt. A later Download retry may create a different log for a different attempt, but the destroyed execution log and its diagnostic identity are gone.

### Correctness impact

This is a destructive concurrency violation of the UI's own safety contract. The operation is presented as unavailable while downloads are running, yet a normal queued-to-Active transition in the check/delete window can cause the clear operation to destroy the **current** execution's diagnostic record. The result is not merely stale UI: an active or subsequently failed Download can lose the log required to diagnose the exact attempt, and progress logging silently tolerates the missing carrier.

The impact is substantive reliability/data-integrity loss because:

- the removed row contains execution-specific diagnostics that cannot be recomputed after the fact;
- the current Download/log relationship can be nulled or become dangling depending on the interleaving;
- the active execution can continue, so the failure can remain latent until the user needs the log after a later error;
- process restart does not reconstruct the lost row or content.

P2 is appropriate because the defect irreversibly destroys correctness-relevant diagnostic state for a production execution under an ordinary user action/race, but does not by itself corrupt downloaded media or create a security boundary failure.

7. **Recovery semantic identity — FAIL:** there is no durable record saying which active execution log was accidentally consumed and no way to reconstruct its prior content/ID relationship.

### Concurrency / lock-order trace

- Download claim/log writer side: queue admission -> `claimDownloadThroughProductionAdmission()` -> exact execution publication -> `DownloadAttemptRunner` -> `prepareYtdlpPhase()` -> `withOwnedExecutionSideEffect()` -> `LogRepository.insert()` -> `downloadDao.updateIfExecutionOwnedAndRunning()`.
- Maintenance side: preference action -> `clearDownloadLogs()` -> `hasActiveDownloads()` count snapshot -> coroutine context switch -> `LogDao.deleteAll()` -> `DownloadDao.removeAllLogID()` -> export-cache cleanup.
- Shared synchronization: **none**. The maintenance path neither enters `withDownloadWorkerExecutionLock` nor takes an exact per-Download side-effect lease, nor does it establish a global maintenance barrier respected by admission.
- Therefore there is no deadlock issue to resolve first; the defect is absence of a common serialization authority.

### Dedup evidence

That finding covers single-log Undo relationship loss and explicitly includes the generic Delete All split between `LogDao.deleteAll()` and `DownloadDao.removeAllLogID()` as a process-death/persistence-fault problem.
- This finding does **not** re-record that split-write defect. It requires a later generation to become Active after `hasActiveDownloads()` returned false and shows that an otherwise successful Clear Logs operation can destroy that generation's live diagnostic carrier.
- `TASKS_DELTA.md` contains no `BUG-LOG-*` entry owning this stale-idle/new-log race.
- All ten pre-existing `review-runs/findings/` files were inventoried. Their recorded new defects are `BUG-UNDO-01` through `BUG-UNDO-06`, `BUG-LOWQUALITY-02`, `BUG-SCHEDULER-07`, `BUG-HARDSUB-05`, and `BUG-OBSERVE-RETRY-01`; none owns Download-log maintenance versus a newly claimed execution.
- Adjacent default-video-folder migration was rejected as an already-owned canonical defect rather than recorded again.

### Required result

1. Treat Clear Download Logs as destructive maintenance requiring continuous authority, not a preflight Boolean. Serialize the final active-work revalidation and log deletion against Download/Terminal execution admission/log creation, or establish a maintenance barrier that all new execution/log writers must respect.
2. At the destructive boundary, re-read authoritative execution state under that shared barrier and abort if any Download/Terminal became active after the UI check.
3. Preserve generation identity: do not allow an unconditional historical purge to delete a log created after the maintenance operation's authorized snapshot. A generation/snapshot cutoff is acceptable only if it is durable/authoritative and correctly fences references.
4. Independently satisfy existing `BUG-LOG-01` by making Log deletion and Download-reference disposition atomic. Fixing only that transaction is insufficient for this finding.
5. Do not silently swallow a live log update failure as a substitute for recovery; if a supposedly live log carrier disappears, surface/reconcile that invariant violation.

### Focused tests / verification

- **Deterministic stale-idle race:** pause `clearDownloadLogs()` immediately after `hasActiveDownloads()` returns false; claim a queued Download through the real production admission path, enable logging, let `prepareYtdlpPhase()` insert and publish its log; resume Clear Logs. Assert the current execution's Log row and exact `Download.logID` survive or the maintenance operation aborts.
- **Insert/delete/publish interleavings:** deterministically exercise (a) log insert -> clear delete -> Download logID publish and (b) clear delete -> log insert -> global `removeAllLogID`; assert no active Download is left with a missing/null current log and no active Log is orphaned by maintenance.
- **Terminal sibling:** repeat with a Terminal execution becoming active after the initial check; destructive maintenance must revalidate/fence the same authority class advertised by `hasActiveDownloads()`.
- **First-write fault injection:** fail `removeAllLogID()` immediately after `deleteAll()` commits and verify existing `BUG-LOG-01` transactional requirements; then separately verify the new-execution barrier so transactionality alone cannot make this test pass falsely.
- **Process death:** kill after live Log deletion and before reference cleanup, then restart; assert the design either prevented deletion or has an exact durable recovery carrier capable of restoring semantic identity (not merely nulling the reference).
- **Regression guard:** verify a truly idle log-clear still clears historical logs and export cache, while a Download that becomes Active after the dialog/check causes the operation to abort or exclude its generation.

# Ready-to-merge `TASKS_DELTA.md` entry

## P2 — BUG-LOG-02 — Fence Clear Download Logs against executions claimed after the idle check

- **Reviewed checkpoint SHA:** `5221f50075173c82d9a3b68a673096a5850ad09f`
- **Evidence:** `SOURCE-LEVEL ONLY`
- **State:** Proposed

**Failure path:** `FolderSettingsFragment.clearDownloadLogs()` first calls `hasActiveDownloads()`, which reads active Download/Terminal counts but retains no execution lock, lease, transaction, or maintenance barrier. If the snapshot is idle, the coroutine later runs unconditional `LogDao.deleteAll()` followed by global `DownloadDao.removeAllLogID()`. Between the idle snapshot and those destructive writes, the production `DownloadWorker` can claim a queued item, publish a fresh exact execution, and in `prepareYtdlpPhase()` insert a new `LogItem` and associate its ID with the running Download. The stale maintenance authorization can then delete that live log and/or null its current reference. Depending on interleaving, the Active Download can be detached from its new log, point to a log already deleted, or leave the newly created log orphaned. Progress logging subsequently goes through `LogRepository.update()`, which swallows DAO update failure, so the execution can continue without reconstructing the lost diagnostic carrier. Restart/retry does not restore the exact prior attempt log/content.

This is distinct from canonical `BUG-LOG-01`: that defect owns the generic non-atomic Log-delete / Download-reference cleanup and Undo relationship loss. Even if `deleteAll()` and `removeAllLogID()` are made one Room transaction, a Download claimed after the stale idle check but before the transaction can still have its current log consumed by the purge.

**Correctness impact:** an ordinary Clear Download Logs action can irreversibly destroy diagnostic state belonging to a Download that is actually running, despite the UI contract explicitly refusing destructive maintenance when work is active. A later failure may therefore have no exact attempt log available for diagnosis; the lost row/content cannot be reconstructed after restart.

**Required result:** serialize destructive log maintenance with Download/Terminal execution admission/log creation, or carry an authoritative maintenance barrier/snapshot through the destructive commit. Revalidate active execution state at the deletion boundary under that shared authority, preserve generation identity so logs created after maintenance authorization cannot be consumed, and independently retain the `BUG-LOG-01` requirement that Log deletion/reference disposition be transactional.

**Verification:** add deterministic production-wiring tests for stale-idle -> claim -> log insert/publish -> clear, both insert/delete/reference interleavings, Terminal sibling admission, first-write fault injection, and process death. A fix passes only if a newly active generation's current log survives or log clearing aborts; merely wrapping the two DELETE/UPDATE statements in one transaction is insufficient.

# Ready-to-merge `REVIEW_LESSONS.md` entry

### 2026-08-31 — `BUG-LOG-02` — An idle preflight is not destructive-maintenance authority

- **Reviewed checkpoint SHA:** `5221f50075173c82d9a3b68a673096a5850ad09f`
- **Ledger defect entry:** `BUG-LOG-02` (proposed)
- **Production-reachable failure path:** Folder settings observes zero active Download/Terminal work, releases that observation, and later performs unconditional Log-table deletion/reference clearing. In the gap, `DownloadWorker` can claim a queued exact execution and `prepareYtdlpPhase()` can create/publish its current Log. The stale maintenance decision then deletes or detaches the live generation's diagnostic carrier.
- **Blind spot:** earlier review focused on atomicity *inside* the delete sequence (`BUG-LOG-01`) and on active-writer protection for filesystem cache cleanup, but did not carry the same authority analysis backward to the idle predicate that decides whether DB-log destruction may start at all.
- **Relevant v4 items:** first authoritative observation; carrier-creation gap; persistence barrier and first-write fault injection; multi-ledger/process-death durability; retry/reconfigure/raw-requeue inventory; cross-attempt matrix; expected-identity mutability; concurrency/sibling isolation/lock order; candidate-rejection proof; terminal fault matrix.
- **Why earlier review missed it:** the presence of `hasActiveDownloads()` looks like explicit concurrency protection, and `BUG-LOG-01` already called out Delete All. Treating that Boolean check as a sufficient guard obscured the interval between the read and the destructive commit. Reviewing the two DAO writes alone also misses the later-generation writer that can enter *before* them.
- **General lesson:** whenever destructive maintenance is allowed only under an idle/no-owner predicate, review the predicate as a lease-acquisition problem. A correct observation that becomes stale one instruction later is not authority. The review must prove that no new protected owner can be created until destruction commits, or that the destructive boundary revalidates under a shared exclusion mechanism.
- **Proposed checklist improvement:** make idle-gated maintenance an explicit concurrency subcase under first-authoritative-observation and carrier-creation-gap review, and require a generation-aware matrix for resources that can acquire new owners between UI preflight and destruction.
- **Suggested wording:** `For any destructive maintenance path gated by "no active work" / "idle" / zero-count checks, identify what prevents a new writer/owner from being admitted after the check and before the first destructive commit. If nothing does, inject a new-generation admission at that exact gap and trace whether the maintenance path can consume the newer generation's state. A Boolean preflight is not an authority lease.`
- **False-positive guard:** do not report a stale-idle race when the preflight and destructive operation execute under the same transaction/lock/lease that every competing owner must acquire, when admission is durably disabled before the check and re-enabled only after commit, or when deletion is explicitly generation/snapshot bounded so resources created after authorization are provably excluded.
- **Disposition:** PROPOSED
