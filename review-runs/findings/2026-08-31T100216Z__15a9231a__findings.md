## BUG-SCHEDULER-07 — Observe or durably recover AlarmReceiver-to-WorkManager handoff failure

- **Severity:** P2
- **Reviewed checkpoint SHA:** `15a9231a02a1c5687663f071d851e23c6ad9bd9f`
- **Verification:** `SOURCE-LEVEL ONLY`
- **Attribution:** pre-existing baseline defect discovered post ledger split; not a remediation regression

### Scope / invariant

Once a one-shot daily start or end AlarmManager callback fires, the callback is the current execution carrier for the user's scheduler boundary. Before that callback releases authority, either the corresponding WorkManager worker must be durably accepted or an exact durable recovery responsibility must exist that can recreate the handoff. Merely invoking an asynchronous enqueue method is not the carrier-creation barrier.

### Concrete production-reachable failure path

1. In Download settings, enabling `use_scheduler` or changing `schedule_start` / `schedule_end` calls `AlarmScheduler.schedule()`.
2. `AlarmScheduler.schedule()` arms one one-shot exact start alarm targeting `ScheduleAlarmReceiver` and one one-shot exact end alarm targeting `CancelScheduleAlarmReceiver` using `setExactAndAllowWhileIdle()`.
3. At the start boundary, `ScheduleAlarmReceiver.onReceive()` constructs a `OneTimeWorkRequest<DownloadWorker>` and calls `WorkManager.enqueueUniqueWork(...)`. At the end boundary, `CancelScheduleAlarmReceiver.onReceive()` analogously constructs a `OneTimeWorkRequest<CancelScheduledDownloadWorker>` and calls `enqueueUniqueWork(...)`.
4. Both receivers discard the returned WorkManager `Operation` and immediately return from `onReceive()`. They do not await acceptance, use `goAsync()` to retain the receiver while observing acceptance, persist a handoff/recovery record, or arm a replacement alarm on asynchronous enqueue failure.
5. WorkManager enqueue is an asynchronous command. Its returned `Operation` has `IN_PROGRESS`, `SUCCESS`, and `FAILURE` states; `Operation.getResult()`/`await()` is the acceptance/failure observation boundary. Therefore a production enqueue can fail after the receiver has invoked it and returned.
6. If that happens, the exact AlarmManager callback has already fired and is one-shot, but no worker has been accepted. There is no same-boundary successor or durable recovery owner in either receiver.
7. **Start failure:** queued work that depended on the daily start boundary remains without the `DownloadWorker` that should begin it. No normal application-start path in `App.onCreate()` reconstructs the consumed daily start alarm/receiver handoff from `use_scheduler` merely because this enqueue failed.
8. **End failure:** `CancelScheduledDownloadWorker` never runs, so the intended end-boundary cancellation/requeue path is not invoked. A live Download can continue its native/filesystem work beyond the configured scheduler window until some independent stop/terminal condition occurs.
9. Reconfiguring the scheduler or another queue action can happen to arm alarms again, but that is a new external action, not recovery of the failed authoritative boundary.

### Why this is a correctness/reliability defect

The daily scheduler exposes an explicit start/end execution window. Its one-shot AlarmManager callbacks are used as reliable boundary triggers, but each callback converts that authority into a WorkManager carrier with an unobserved asynchronous operation. An enqueue failure therefore silently turns a configured scheduler boundary into best-effort behavior: the start may never launch the queued work, or the end may fail to stop/requeue current work. The defect requires no malformed state, unsupported configuration, or speculative future platform behavior; WorkManager explicitly models enqueue failure as a terminal `Operation.State.FAILURE`.

This is distinct from:

- `BUG-SCHEDULER-01`, which owns lack of next-day re-arming and overnight-window calculation;
- `BUG-SCHEDULER-03`, which owns successor alarms for individually scheduled AlarmManager work;
- `BUG-SCHEDULER-04`, which owns the end worker cancelling future delayed WorkManager carriers after that worker actually exists;
- `BUG-SCHEDULER-05`, which owns the API 24–30 exact-alarm capability false negative;
- `BUG-SCHEDULER-06`, which owns due-time authority revalidation when claiming a scheduled Download.

None of those closes failure between a successfully delivered daily AlarmManager callback and durable acceptance of the first WorkManager carrier.

### BUG-SCHEDULER-07 — Observe or durably recover AlarmReceiver-to-WorkManager handoff failure

**State:** Open  
**Reviewed checkpoint:** `15a9231a02a1c5687663f071d851e23c6ad9bd9f`  
**Verification:** `SOURCE-LEVEL ONLY`

**Failure path:** enabling the daily Download scheduler or changing its start/end times calls `AlarmScheduler.schedule()`, which arms one-shot exact start and end alarms. When the start alarm fires, `ScheduleAlarmReceiver` calls `WorkManager.enqueueUniqueWork(...)` for a `DownloadWorker`; when the end alarm fires, `CancelScheduleAlarmReceiver` does the same for `CancelScheduledDownloadWorker`. Both receivers discard the returned WorkManager `Operation` and return immediately. WorkManager defines enqueue as asynchronous and exposes `Operation.FAILURE`; therefore an enqueue can fail after invocation without ever accepting the worker. At that point the one-shot alarm callback has already been consumed, but neither receiver has a durable handoff record, retry owner, replacement alarm, or startup reconciliation for the failed boundary. A failed start handoff can leave eligible queued work without its daily-window worker; a failed end handoff can leave live Download/native/filesystem execution continuing beyond the configured end because the cancellation/requeue worker never exists.

**Why this is a defect:** the scheduler promises explicit start/end boundaries but treats asynchronous WorkManager method invocation as durable successor creation. A real scheduler-acceptance failure silently downgrades a one-shot exact boundary into best-effort behavior. This is distinct from `BUG-SCHEDULER-01` (daily recurrence/midnight calculation), `BUG-SCHEDULER-03` (individual scheduled successor alarms), `BUG-SCHEDULER-04` (what the end worker cancels after it exists), `BUG-SCHEDULER-05` (pre-31 capability false negative), and `BUG-SCHEDULER-06` (due-time authority when claiming a row).

**Ownership / attribution:** pre-existing baseline defect discovered post ledger split; not a remediation regression.

Required result:

- make terminal WorkManager acceptance the receiver handoff barrier, or durably record exact handoff responsibility before the one-shot callback releases authority;
- recover enqueue failure and process death by retrying/re-arming/reconciling under an exact scheduler-boundary generation, with exactly-once/idempotent start/end semantics;
- reconcile durable boundary debt on startup and prevent obsolete retries from regaining authority after scheduler disable/reconfigure;
- preserve downstream Download leases and the separate scheduler invariants already owned by `BUG-SCHEDULER-01/04/05/06`.

Focused verification requirements:

- production receiver -> WorkManager tests forcing asynchronous enqueue failure for both start and end callbacks;
- process death between callback delivery, recovery publication, and WorkManager acceptance;
- duplicate delivery/retry and disable/reconfigure races proving exactly one current-generation carrier;
- real downstream worker wiring, not a helper-only assertion that `enqueueUniqueWork()` was invoked.

### 2026-08-31 — `BUG-SCHEDULER-07` — One-shot callback releases authority before async carrier acceptance

- **Reviewed checkpoint SHA:** `15a9231a02a1c5687663f071d851e23c6ad9bd9f`
- **Ledger defect entry:** proposed `TASKS_DELTA.md` / `BUG-SCHEDULER-07`
- **Production-reachable failure path:** scheduler settings -> `AlarmScheduler.schedule()` arms one-shot exact alarms -> `ScheduleAlarmReceiver` / `CancelScheduleAlarmReceiver` receives the authoritative boundary -> receiver invokes `WorkManager.enqueueUniqueWork(...)` -> returned asynchronous `Operation` is discarded -> enqueue fails before WorkManager accepts the worker -> receiver has already returned and the one-shot alarm is consumed -> no durable boundary recovery owner -> start work is lost or end cancellation/requeue is lost.
- **Why earlier reviews missed it:** scheduler reviews followed the logic on either side of the handoff but treated the `enqueueUniqueWork()` call itself as creation of a durable successor. That stopping assumption exposed recurrence, window arithmetic, cancellation-domain, and due-time defects while skipping the narrow but authoritative interval between a one-shot callback being consumed and WorkManager reporting enqueue success. Similar async-carrier defects elsewhere were reviewed from a preceding durable state transition; this receiver path has no explicit app ledger row, which made the carrier-creation gap easier to overlook.
- **Checklist coverage at discovery time:** v4 already requires first authoritative observation, carrier-creation gap, helper-internal throwable window, persistence barrier/first-write fault injection, post-commit barrier, outer result, retry/re-entry, terminal matrix, and CLEAN gate. Those items were relevant but not applied deeply enough to platform callbacks whose lifetime ends before an asynchronously requested successor is durably accepted. Review traced the downstream worker after assumed enqueue success rather than fault-injecting the enqueue operation itself before leaving `BroadcastReceiver.onReceive()`.
- **General lesson:** whenever a one-shot callback, lease, message, alarm, broadcast, or other ephemeral carrier hands authority to an asynchronous scheduler, queue, IPC, or executor, invocation is not successor creation. The original carrier may be released only after successor acceptance is proven or durable exact recovery responsibility is published.
- **Proposed checklist improvement:** add an ephemeral-carrier handoff row to the carrier-creation and post-commit review: identify whether the source callback/message is replayable, identify the asynchronous successor acceptance signal, fault-inject acceptance failure and process death between invocation and acceptance, and require a durable/idempotent retry owner before the source carrier is acknowledged or consumed.
- **Suggested checklist wording:** "For every one-shot or ephemeral production carrier (AlarmManager/receiver callback, message acknowledgement, notification action, broadcast, lease callback, IPC request, etc.) that hands work to an asynchronous scheduler or queue, distinguish successor invocation from successor acceptance. Identify the terminal acceptance signal, inject failure/process death after the source carrier is consumed but before acceptance, and prove either the source remains replayable or an exact durable recovery carrier already exists. Do not mark the handoff CLEAN merely because the enqueue/send API was called. Retry must be generation-bound and idempotent so duplicate callback delivery cannot create duplicate privileged work."
- **False-positive guard:** require (1) a production-reachable one-shot/ephemeral authority carrier, (2) a successor API whose acceptance can fail asynchronously or after the source callback returns, (3) no existing durable recovery/replay mechanism that is guaranteed to repair that exact failed handoff, and (4) a material semantic consequence such as lost required work, continued revoked work, stale persistent state, or incorrect terminal behavior. A fire-and-forget notification or optional telemetry event is insufficient.
- **Disposition:** `PROPOSED`
