## BUG-UNDO-06 — Peer Fragment creation can rotate a shared Undo owner away from an already-published Snackbar

**Severity:** P2  
**Reviewed checkpoint:** `206c145f0cf8ff8462ec18cf7781dbbc2e1b0903`  
**Verification:** `SOURCE-LEVEL ONLY`  
**Attribution:** remediation regression / incomplete closure in the live Undo-authority remediation; correctness was established before attribution.

### Scope / invariant

A published Undo Snackbar must retain an exact resolver authority until that Snackbar is explicitly resolved, abandoned, or superseded by a stronger durable action. Creating another Fragment view must not silently change the identity required by an already-live Snackbar callback, and lifecycle abandonment must abandon the owner that actually belongs to the disappearing view rather than whichever owner ID happens to be globally current at that instant.

### Concrete production-reachable failure path

1. `DownloadQueueMainFragment` constructs a `ViewPager2` backed by six child Fragments: Active, Queued, Scheduled, Cancelled, Errored, and Saved. The Errored and Saved pages are ordinary peer views within this pager.
2. `ErroredDownloadsFragment.onCreateView()` obtains `DownloadViewModel` with `ViewModelProvider(requireActivity())`, so it uses the Activity-scoped shared ViewModel, then immediately calls `downloadViewModel.beginUndoPresentationOwner()`.
3. `SavedDownloadsFragment.onCreateView()` obtains the same Activity-scoped `DownloadViewModel` and also calls `beginUndoPresentationOwner()`.
4. `DownloadViewModel.beginUndoPresentationOwner()` delegates to the shared repository. `DownloadRepository.beginUndoPresentationOwner()` only executes `undoOwnerId = UUID.randomUUID().toString()` under `undoAuthorityLock`. It does **not** abandon or transfer the previous owner, does not associate the new owner with a specific Fragment/view, and does not rewrite already-live token authorities.
5. In Errored, a left swipe calls `deleteDownloadForUndo()`. `DownloadRepository.deleteForUndo()` registers the exact removal token under `currentUndoOwnerId()`, durably inserts a `PendingUndoCarrier`, publishes the snapshot, and the Fragment shows an indefinite Snackbar. `onShown()` calls `acknowledgeUndoPublication()`, promoting that token to `LIVE_UI`. At this point token T is an actually published, user-actionable Snackbar capability owned by owner A.
6. While that Snackbar is still live, creation/recreation of a peer Activity-scoped download Fragment can call `beginUndoPresentationOwner()` again. For example, navigating the ViewPager so a peer page view is instantiated or recreated causes the same shared ViewModel/repository to replace global `undoOwnerId` A with B. Token T remains stored in `undoAuthorities[T]` with `ownerId=A` and state `LIVE_UI`; A is not added to `abandonedUndoOwners` and no recovery handoff is scheduled.
7. The old Snackbar is now semantically broken even if its view/callback still exists. Pressing Undo calls `restoreDownloadUndoFromUi()` -> `acceptRemovalUndoResolution(T, RESTORE)`. Dismissing it normally calls `commitDownloadUndoFromUi()` -> `acceptRemovalUndoResolution(T, COMMIT)`. `acceptUndoResolution()` reads `currentUndoOwnerId()` (now B) and rejects T because `authority.ownerId != ownerId`. The UI callback therefore returns without restoring or committing the exact carrier.
8. If the old Errored view is then destroyed, its `onDestroyView()` calls `abandonPendingUndoCapabilitiesForView()`. That method does not carry a view-specific owner ID; it delegates to `abandonCurrentUndoOwner()`, which snapshots the repository's **current** global `undoOwnerId` B. It marks B abandoned and selects only token authorities whose `ownerId == B`. Token T still belongs to A, so the disappearing Errored view cannot abandon its own token.
9. Same-process recovery also cannot take over T. `LowQualityRedownloadRepository.reconcileAbandonedUndoDebt(T)` checks `DownloadRepository.isProcessLocalPendingUndoAuthority(T)`. That helper returns true for `LIVE_UI` based only on the token state; it does not verify that A is still the current owner or that an actual Fragment/Snackbar still owns A. Recovery therefore returns false and preserves the carrier as supposedly live.
10. The durable removal carrier (and, when linked, its low-quality pending state) can remain unresolved for the rest of the process. A cold process restart clears the process-local authority map and startup abandoned-Undo reconciliation can eventually consume the durable carrier, but process death is not a valid semantic resolution for a Snackbar whose live authority was lost merely because a peer Fragment view was created.

The same owner-rotation defect applies to pending-cancellation Undo tokens on any peer view using the shared Activity-scoped repository: the resolver predicate is token-owner equality against the single mutable global `undoOwnerId`, not against a stable per-view owner capability.

### Why this is substantive

This is more than a cosmetic Snackbar issue. A user can be shown an Undo action that has already lost the authority required for its callback to execute. After peer-view rotation, both RESTORE and COMMIT callbacks can become no-ops for the exact durable token. For linked low-quality work, the token can keep a child in a pending cancellation/removal state and keep the parent from ordinary convergence while recovery deliberately refuses to consume what it still classifies as `LIVE_UI`. For unlinked removal, the durable snapshot can remain unresolved until restart. The persistent state and the actual reachable UI authority therefore diverge.

### Dedup / candidate-rejection discipline

- **Not `BUG-UNDO-01`:** that finding starts after deliberate owner abandonment and covers failure of the first convergence attempt. Here the owner is never correctly abandoned; a peer view silently replaces the globally current owner first.
- **Not `BUG-UNDO-02`:** that finding concerns a stronger rollback-capable Room transition releasing process-local authority before durable commit. This path needs no stronger Room transition and no persistence failure.
- **Not `BUG-UNDO-03`:** that finding concerns a resolver temporarily removing/restoring a snapshot while lifecycle abandonment races it. Here the Snackbar remains published and unresolved; a different Fragment's owner initialization invalidates its resolver identity.
- **Not `BUG-UNDO-04`:** that finding concerns losing the publication continuation before a Snackbar is shown. Here `onShown()` has already promoted the token to `LIVE_UI`; the defect occurs afterward when a peer view rotates the shared owner.
- **Not `BUG-UNDO-05`:** that finding concerns the producer window between durable removal commit and process-local snapshot registration. Here the durable carrier and process-local snapshot are both present and correctly published before owner rotation.
- A rejection would require proof that no second Activity-scoped download Fragment can call `beginUndoPresentationOwner()` while another Activity-scoped Fragment has a live Snackbar, or that `beginUndoPresentationOwner()` transfers all authorities owned by the previous view, or that callbacks resolve against a stable owner captured by the Snackbar. The production code provides none of those barriers: the pager contains multiple peer Fragments, both Errored and Saved use the Activity owner, and the repository stores only one mutable global current owner ID.

### Required result

- Replace the single mutable repository-wide `undoOwnerId` with an exact per-view/per-presentation owner capability, or make owner rotation atomically transfer/abandon the previous owner's outstanding authorities before installing the new owner.

## Ready-to-merge `TASKS_DELTA.md` entry

### BUG-UNDO-06 — Keep published Undo authority stable across peer Fragment owner creation

**State:** Open  
**Reviewed checkpoint:** `206c145f0cf8ff8462ec18cf7781dbbc2e1b0903`  
**Verification:** `SOURCE-LEVEL ONLY`

**Failure path:** `DownloadQueueMainFragment` hosts multiple peer download Fragments in a `ViewPager2`. `ErroredDownloadsFragment` and `SavedDownloadsFragment` both acquire the same Activity-scoped `DownloadViewModel` and call `beginUndoPresentationOwner()` from `onCreateView()`. The shared `DownloadRepository.beginUndoPresentationOwner()` does only `undoOwnerId = UUID.randomUUID()` and does not transfer or abandon authorities belonging to the previous view. If Errored has already published a removal Snackbar, its exact token remains `LIVE_UI` with owner A. Creation/recreation of a peer Activity-scoped Fragment replaces the repository's current owner with B. The old Snackbar's Undo and dismissal callbacks later call `acceptUndoResolution()`, which requires `authority.ownerId == currentUndoOwnerId`; both are rejected because A != B. If the old view is destroyed, `abandonPendingUndoCapabilitiesForView()` abandons the globally current B rather than the old view's A, so the old token is not transferred to recovery. `reconcileAbandonedUndoDebt()` then refuses to consume it because `isProcessLocalPendingUndoAuthority()` still treats its `LIVE_UI` state as positive authority. The durable Undo carrier can remain unresolved until process death/startup reconciliation.

**Why this is a defect:** an actually shown Undo control can lose the capability required to execute solely because another peer Fragment view is created. Durable removal/cancellation state can remain pending while same-process recovery is blocked by stale live-owner metadata. View creation is not a stronger semantic action and must not revoke or orphan an existing user's exact Undo authority.

**Ownership / attribution:** remediation regression / incomplete closure in the live Undo-authority remediation; the defect is distinct from `BUG-UNDO-01` through `BUG-UNDO-05` because it occurs after successful Snackbar publication and is caused by cross-view owner rotation rather than publication loss, resolver failure, stronger-transition rollback, or producer/carrier gaps.

Required result:

- use stable per-view/per-presentation owner capabilities or atomically transfer/abandon prior owner authorities before owner replacement;
- never let peer Fragment creation invalidate an existing Snackbar's RESTORE/COMMIT resolver identity;
- make view destruction abandon its own captured owner ID rather than a mutable repository-global current owner;
- make recovery liveness depend on a reachable exact owner, not only a `LIVE_UI` enum state;
- preserve exact first-selected intent and stronger-operation semantics across multi-view handoff;
- add production Fragment/ViewPager + Room tests covering peer creation after `onShown`, Undo, dismissal, old-view destruction, two simultaneous owners, linked pending-cancellation state, and restart recovery.

### 2026-09-01 — `BUG-UNDO-06` — Shared current-owner slots cannot represent multiple live UI capabilities

- **Reviewed checkpoint SHA:** `206c145f0cf8ff8462ec18cf7781dbbc2e1b0903`
- **Ledger defect entry:** proposed `TASKS_DELTA.md` / `BUG-UNDO-06`
- **Production-reachable failure path:** `DownloadQueueMainFragment` ViewPager peer pages -> Errored/Saved both use `ViewModelProvider(requireActivity())` -> each view creation calls `beginUndoPresentationOwner()` -> first page publishes exact `LIVE_UI` Undo token under owner A -> peer page creation overwrites shared repository `undoOwnerId` with B without handoff -> old Snackbar RESTORE/COMMIT is rejected by owner mismatch -> old view destruction abandons B rather than A -> abandoned-debt reconciler sees T as process-local `LIVE_UI` and refuses to consume it -> durable token remains unresolved until process restart.
- **Why earlier reviews missed it:** earlier Undo reviews treated lifecycle ownership largely as a single producer/view -> one owner -> one Snackbar -> abandonment sequence. The remediation added view-level handoff hooks to close the pre-publication and on-destroy gaps, but review did not redraw the ownership graph after noticing that multiple pager child Fragments obtain the same Activity-scoped ViewModel. `beginUndoPresentationOwner()` was therefore reviewed as a lifecycle reset primitive rather than as a mutation of a shared global capability namespace that can execute while another UI capability is still live.
- **Checklist coverage at discovery time:** v4 expected-identity mutability, concurrency/exact ownership, retry/re-entry, post-commit barrier, and candidate-rejection discipline were all relevant. They were not applied across **multiple simultaneous UI owners sharing one repository instance**. The checklist asks whether exact ownership is preserved but does not explicitly require enumerating the cardinality and scope of owners when lifecycle callbacks from sibling Fragments share an Activity/ViewModel/repository.
- **General lesson:** an ownership field that is semantically "current owner" is safe only if the architecture proves there can be at most one live owner. When multiple views, tabs, activities, workers, or nested lifecycle scopes share the state holder, reviewer must model ownership as a set/graph, not a scalar. Owner creation itself is an authority transition and must not silently invalidate previously issued capabilities.
- **Proposed checklist improvement:** add a shared-owner cardinality audit to the exact-ownership/concurrency step. For every mutable `currentOwner`, generation, lease, session ID, callback owner, or lifecycle token used to authorize durable actions, enumerate all production objects that can call begin/acquire/release and their actual ViewModel/service/repository scope. If two can coexist, require per-owner identity or an atomic transfer protocol and test cross-owner creation/destruction order.
- **Suggested checklist wording:** "Whenever correctness depends on a mutable 'current owner'/generation/session field, prove the architecture permits at most one live owner for the entire lifetime of every issued capability. Enumerate all Fragment/Activity/ViewModel/service/worker instances that share the state holder and build the owner-order matrix `owner A acquire -> capability A published -> owner B acquire -> capability A resolve -> A destroy -> B destroy` plus the reverse order. If A and B can coexist, a scalar current-owner field is not sufficient unless B acquisition atomically transfers or revokes A and every outstanding A capability is converged. Lifecycle release must carry the exact owner identity captured by that lifecycle, not reread a mutable global current owner."
- **False-positive guard:** require (1) two production-reachable owner instances/scopes that share the same state holder, (2) an outstanding capability whose resolver/recovery predicate depends on that mutable current-owner identity, (3) a concrete ordering where owner B acquisition occurs before capability A resolves, and (4) a materially incorrect durable/UI result such as rejected valid Undo, unresolved carrier, unauthorized action, or recovery suppression. Merely sharing a ViewModel without owner-sensitive durable semantics is insufficient.
- **Disposition:** `PROPOSED`
