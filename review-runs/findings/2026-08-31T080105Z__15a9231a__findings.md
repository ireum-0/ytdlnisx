## BUG-LOWQUALITY-02 — P2 — PREPARING commits before the WorkManager carrier is proven durable

- **Reviewed checkpoint SHA:** `15a9231a02a1c5687663f071d851e23c6ad9bd9f`
- **Verification:** `SOURCE-LEVEL ONLY`
- **Attribution:** pre-existing baseline defect discovered post ledger split; not a remediation regression.

### Scope / invariant

Once the user confirms selected low-quality re-download candidates and the durable operation leaves `AWAITING_SELECTION`, either the successor execution carrier must already be durably established or an independent same-process convergence owner must retain responsibility until carrier creation is proven. A durable `PREPARING` operation must not be left with neither a WorkManager carrier nor a retry owner merely because enqueue failed after the phase commit.

### Concrete production-reachable failure path

1. History UI exposes `redownload_low_quality`; `startLowQualityVideoScan()` enters the low-quality workflow through `LowQualityRedownloadViewModel.startOrReconnect()`.
2. When scanning reaches `AWAITING_SELECTION`, `HistoryFragment.showLowQualityCandidates()` gives the user `queue_selected_redownloads`; its positive action calls `LowQualityRedownloadViewModel.confirm(operationId)`.
3. The ViewModel delegates to `LowQualityRedownloadManager.confirm()`, which launches `confirmAndEnqueueLowQualityRedownload()` in the manager's serialized supervisor scope.
4. `LowQualityRedownloadRepository.confirmSelection()` executes a Room transaction, validates the active/nonterminal `AWAITING_SELECTION` operation and immutable candidate identity, marks unselected rows, and commits the operation phase transition `AWAITING_SELECTION -> PREPARING`.
5. Only after that transaction returns true does `confirmAndEnqueueLowQualityRedownload()` call `enqueueSuccessor(...)`.
6. `LowQualityRedownloadManager.enqueue()` creates a `OneTimeWorkRequest` and calls `WorkManager.enqueueUniqueWork(..., APPEND_OR_REPLACE, request)`, but discards the returned `Operation` completely.
7. AndroidX WorkManager defines enqueue/cancel commands as asynchronous operations and explicitly exposes terminal `SUCCESS` versus `FAILURE`; `Operation.getResult()`/`await()` is the completion barrier and reports failure as an exception. Therefore return from `enqueueUniqueWork()` is not proof that the enqueue command committed successfully.
8. If WorkManager enqueue fails asynchronously after the Room `PREPARING` commit, this code neither observes the failure nor installs a retry/convergence owner; `confirmAndEnqueueLowQualityRedownload()` returns true. If `enqueueUniqueWork()` instead throws synchronously after the Room commit, there is likewise no catch around the post-commit carrier creation and the manager coroutine simply terminates under the `SupervisorJob`, again without restoring `AWAITING_SELECTION` or scheduling convergence.
9. The durable low-quality operation is now `PREPARING`, so the selection dialog is dismissed and ordinary rendering shows indefinite preparation progress. No low-quality worker exists to advance the operation.
10. There is no same-process periodic/ledger convergence owner for normal `PREPARING` carrier debt. Recovery exists only on a later explicit low-quality feature re-entry (`startOrReconnect()` returns the active operation and `dispatchRecovery()` re-enqueues) or application startup (`App.onCreate` eventually calls `LowQualityRedownloadManager.reconcile()` after runtime readiness). Merely remaining on the current screen does not repair the committed state.

### Why this is a substantive correctness / reliability defect

The user-confirmed durable state says preparation is underway, but the only execution carrier can fail to be created after that state is committed. The caller neither receives nor records the asynchronous enqueue failure and no same-process owner guarantees convergence. The workflow can therefore remain indefinitely nonterminal at `PREPARING` until an unrelated explicit feature re-entry or process restart. This is not defensive future-proofing: WorkManager's public contract explicitly models enqueue as an asynchronous `Operation` with a terminal `FAILURE` state, and the production path makes durable application state depend on that command succeeding.

### First authoritative observation / carrier-creation gap / helper throwable window

- **Authoritative decision:** successful `confirmSelection()` transaction commits the user's confirmed selection and phase transition to `PREPARING`.
- **Carrier-creation gap:** the durable decision is committed before `enqueueUniqueWork()` is known successful.
- **Helper-internal throwable window:** both a synchronous enqueue throw and an asynchronous `Operation.State.FAILURE` occur after the application-side phase commit. Neither path has a recovery owner in `confirmAndEnqueueLowQualityRedownload()` or `enqueue()`.
- **Semantic preservation:** there is no rollback of `PREPARING`, no durable `enqueue_pending` carrier, and no terminal failure classification; the state continues to claim progress should occur.

### Persistence barrier / first-write fault injection

- **Room transition failure before commit:** safe for this invariant; `confirmSelection()` does not return true, so no enqueue is attempted and the operation remains `AWAITING_SELECTION`.
- **Room transition succeeds, WorkManager carrier creation fails:** defect path; `PREPARING` persists with no proven carrier.
- **Carrier failure reporting:** ignored because returned `Operation` is discarded.
- **Recovery-write failure:** there is no immediate recovery write at all on this path, so there is no second barrier to fault-inject until a later re-entry/restart invokes reconciliation.

### Recovery semantic identity / multi-ledger and process-death durability

The operation ID remains durable and recovery correctly reuses that same ID if recovery is eventually invoked. The defect is ownership/timing rather than identity corruption: no live owner is guaranteed to invoke that recovery after the failed confirmation enqueue. Process death preserves the `PREPARING` row; a later successful startup reconciliation can recreate the worker with `KEEP`, but startup normal low-quality reconciliation is itself gated behind successful optional runtime initialization. Cancellation debt has a separate runtime-independent startup owner, while ordinary `PREPARING` debt does not.

### Post-commit barrier / outer catch / final result

- `confirmAndEnqueueLowQualityRedownload()` returns `true` immediately after invoking the enqueue lambda and does not await WorkManager completion.
- `LowQualityRedownloadManager.confirm()` ignores that Boolean and has no outer catch that converts post-commit enqueue failure into a durable retry carrier or user-visible failure.
- A synchronous exception terminates only that manager child coroutine because the manager uses a `SupervisorJob`; it does not install successor ownership.
- An asynchronous WorkManager failure is completely unobserved.

### Filesystem / reference / cleanup authority

No candidate media deletion or filesystem mutation is required to trigger this defect. The failure occurs before preparation/queueing workers create replacement Downloads, so the primary incorrect durable effect is the stranded operation/selected-item ledger state rather than filesystem corruption.

**Verification:** `SOURCE-LEVEL ONLY`

**Failure path:** History `redownload_low_quality` -> scan reaches `AWAITING_SELECTION` -> user presses `queue_selected_redownloads` -> `LowQualityRedownloadViewModel.confirm()` -> `LowQualityRedownloadManager.confirm()` -> `LowQualityRedownloadRepository.confirmSelection()` commits the Room phase `AWAITING_SELECTION -> PREPARING` -> only afterward `LowQualityRedownloadManager.enqueue()` calls `WorkManager.enqueueUniqueWork(APPEND_OR_REPLACE, ...)`. The returned WorkManager `Operation` is discarded. WorkManager enqueue is an asynchronous command whose `Operation` can terminate in `FAILURE`; `getResult()`/`await()` is the success barrier. If that asynchronous operation fails after the Room commit, the manager returns from the confirmation path without noticing it. If enqueue throws synchronously after the commit, the child coroutine terminates without installing a convergence owner. In either case the durable operation remains `PREPARING` but no worker carrier is guaranteed to exist. The History UI leaves the selection phase and shows indefinite preparation progress; merely remaining in the app does not retry the carrier. A later explicit low-quality menu re-entry can recover through `startOrReconnect()`, and a later eligible startup reconciliation can recover after process restart, but neither is an owner retained by the failed confirmation transition.

**Why this is a defect:** the durable operation claims that a user-confirmed batch has entered executable preparation even though the sole execution carrier can fail to be persisted after that state commits. No same-process retry owner or durable enqueue-debt carrier bridges the two persistence domains, so a real WorkManager enqueue failure can strand the active operation indefinitely until an unrelated user re-entry or restart. This is distinct from `BUG-LOWQUALITY-01`, which owns Download/low-quality terminal atomicity and exact terminal semantic preservation, and from `BUG-UNDO-01..05`, which own pending Undo authority/lifecycle races.

**Ownership / attribution:** pre-existing baseline defect discovered post ledger split; not a remediation regression.

Required result:

- bridge the Room `PREPARING` commit and WorkManager enqueue with an exact-operation durable/live convergence protocol;
- observe/await the enqueue `Operation` or otherwise retain a retry owner until WorkManager persistence is acknowledged;
- handle both synchronous enqueue throws and asynchronous `Operation.State.FAILURE` without leaving unowned `PREPARING` state;
- preserve exact operation/selection identity and make cancellation supersede any pending carrier retry;
- ensure restart, feature re-entry, and same-process no-reentry cases all converge without duplicate worker generations.

Focused verification:

- inject synchronous and asynchronous WorkManager enqueue failure immediately after the `PREPARING` Room commit and verify same-process convergence with no manual screen/menu re-entry;
- process-kill at the commit/enqueue barrier and verify restart establishes one carrier for the same operation ID;
- race cancellation against pending enqueue recovery and prove no stale carrier appears after cancellation;
- assert Room phase/children, WorkManager unique-work state, UI/notification semantics, and worker generation identity together. Helper-only tests are insufficient.

### 2026-08-31 — `BUG-LOWQUALITY-02` — Durable phase commit outruns asynchronous carrier creation

- **Reviewed checkpoint SHA:** `15a9231a02a1c5687663f071d851e23c6ad9bd9f`
- **Ledger defect entry:** proposed `TASKS_DELTA.md` / `BUG-LOWQUALITY-02`
- **Production-reachable failure path:** History low-quality selection confirmation -> Room transaction durably advances `AWAITING_SELECTION -> PREPARING` -> manager calls WorkManager unique enqueue -> returned asynchronous `Operation` is ignored -> enqueue failure has no same-process convergence owner -> durable active operation remains `PREPARING` until explicit feature re-entry or later eligible startup reconciliation.
- **Why earlier reviews missed it:** earlier low-quality reviews followed the worker deeply once a carrier existed: immutable History identity, linked Download creation, terminal semantic preservation, cancellation, recovery, and Undo authority. The confirmation helper was treated as a simple handoff because the call to `enqueueUniqueWork()` was visually adjacent to the phase transition. Review stopped at the enqueue invocation rather than asking whether the external scheduler had actually acknowledged persistence and who owned the gap if that asynchronous command failed. Subsequent Undo-focused reviews further concentrated on authority loss after linked Downloads already existed, leaving the earlier `AWAITING_SELECTION -> PREPARING -> WorkManager` boundary comparatively under-examined.
- **Checklist coverage at discovery time:** v4 already contains `carrier-creation gap`, `helper-internal throwable window`, `persistence barrier and first-write fault injection`, `multi-ledger/process-death durability`, `post-commit barrier`, `retry/re-entry`, `cross-attempt matrix`, and `test/wiring evidence`. Those items were sufficient in principle but were not applied deeply enough to an API that *returns an asynchronous operation object*. The enqueue call itself was implicitly counted as carrier creation rather than treating successful completion of the WorkManager `Operation` as the authoritative carrier-persistence barrier.
- **General lesson:** invoking an external durable scheduler/database/service API is not the same as establishing its carrier when the API explicitly returns an asynchronous completion/failure handle. If application state commits first, the reviewer must identify an owner that survives until external persistence is positively acknowledged, and must inject failure into the returned operation after the local commit—not only synchronous exceptions at the call site.
- **Proposed checklist improvement:** refine the carrier-creation and post-commit steps with an asynchronous-command acknowledgement row. For every persistence/scheduling/cancellation API that returns `Operation`, `Future`, `Deferred`, callback, transaction token, or equivalent, record invocation, acknowledgement, asynchronous failure, owner lifetime between them, and recovery after process death. A returned handle that is discarded must trigger an explicit proof that success acknowledgement is semantically unnecessary.
- **Suggested checklist wording:** "When a durable transition depends on an external command that completes asynchronously, do not treat command invocation as carrier creation. Identify the API's success-acknowledgement boundary (`Operation`/Future/callback/etc.), fault-inject both synchronous invocation failure and asynchronous terminal failure after the local commit, and prove an exact durable or live convergence owner exists from the first local commit until external persistence is acknowledged. If the completion handle is intentionally ignored, require production proof that command failure cannot strand, misreport, or reinterpret durable application state. Include process death between invocation and acknowledgement."
- **False-positive guard:** require (1) a production-reachable local durable transition that occurs before external command success is acknowledged, (2) an API contract or implementation that admits asynchronous command failure, (3) no already-established durable/live owner guaranteed to retry or compensate without unrelated user action/restart, and (4) a materially incorrect durable state or lost requested operation when the external command fails. Merely ignoring a completion handle for best-effort telemetry/cleanup is insufficient.
- **Disposition:** `PROPOSED`
