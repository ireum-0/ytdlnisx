## BUG-UNDO-05 — lifecycle teardown can inventory Undo ownership before a committed pending-removal snapshot is published

- Severity: **P2**
- Evidence: **SOURCE-LEVEL ONLY**
- Reviewed checkpoint: `15a9231a02a1c5687663f071d851e23c6ad9bd9f`
- Attribution: **incomplete closure / remediation follow-up** in the live Undo-authority handoff remediation, classified only after correctness and dedup review.

### Scope / invariant

Once `deleteForUndo()` has durably converted a linked Download into exact pending-removal debt, the token must be continuously owned by either the still-live UI owner or an already-established recovery successor. The lifecycle abandonment inventory must not be allowed to run before the owner-tagged snapshot that it uses as its source of truth is published, then permanently miss a snapshot that appears afterward under an owner that has already been cleared.

### Concrete production-reachable failure path

1. `SavedDownloadsFragment` obtains `DownloadViewModel` with `ViewModelProvider(requireActivity())`, so the Undo repository owner is tied to the Activity ViewModel. A left swipe launches `SavedDownloadsFragment.lifecycleScope`, enters `withContext(Dispatchers.IO)`, and calls `downloadViewModel.deleteDownloadForUndo(itemID)`. The Snackbar is built only after that call returns.
2. `DownloadViewModel.deleteDownloadForUndo()` delegates to `DownloadRepository.deleteForUndo()`. The repository first creates an exact `PENDING_USER_REMOVAL:v1:...` token and immediately registers it in the process-global live-pending-removal token set.
3. `removeDownloadTransaction(... captureUndo = true ...)` then runs a Room transaction. For a linked live low-quality child, it commits `CANCELLATION_REQUESTED` with that exact pending-removal token, captures the Download/linked snapshot, deletes the primary Download row, and commits the transaction.
4. Critically, `pendingRemovalSnapshots[token] = snapshot.copy(ownerId = undoOwnerId)` does **not** happen in or immediately with that durable transaction. After the transaction returns, `removeDownloadWithSnapshot()` first performs synchronous recursive cache deletion via `deleteCache(...)`; only after that helper returns does `deleteForUndo()` publish the owner-tagged snapshot into `pendingRemovalSnapshots`.
5. This creates a legal post-commit carrier gap: durable pending-removal debt and `livePendingRemovalToken(token)` already exist, while `pendingRemovalSnapshots` still contains no entry from which lifecycle handoff can derive the owner or successor token. Cache deletion can make this gap materially long rather than a single instruction window.
6. If the Activity is permanently destroyed during that gap, AndroidX `FragmentActivity.onDestroy()` calls `super.onDestroy()` before `mFragments.dispatchDestroy()`. `ComponentActivity` handles `ON_DESTROY` by clearing its `ViewModelStore` when the Activity is not changing configurations. Therefore the activity-owned `DownloadViewModel.onCleared()` can run while the Fragment has not yet received its destroy dispatch and its `lifecycleScope` work can still be executing.
7. `DownloadViewModel.onCleared()` launches detached `repository.abandonPendingUndoSnapshots()`. That method inventories pending-removal ownership **only** from `pendingRemovalSnapshots.entries.filter { ownerId == undoOwnerId }`. The live pending-removal token set is not owner-tagged and is not independently inventoried. Because this token's snapshot has not yet been inserted, the handoff sees no owned removal entry, derives no successor token, schedules no `scheduleAbandonedUndoConvergence(token)`, and cannot remove/unregister this pending-removal authority.
8. The already-running IO deletion can then finish its non-suspending cache deletion and continue into `deleteForUndo()`, which inserts `pendingRemovalSnapshots[token] = snapshot.copy(ownerId = undoOwnerId)` **after** that `undoOwnerId`'s ViewModel has already been cleared. Fragment cancellation can prevent the handle/Snackbar from ever reaching the UI, but it does not retroactively rerun the completed owner inventory; the snapshot publication itself occurs before the surrounding `withContext` can return/cancel at its caller boundary.
9. The process now contains a pending-removal snapshot and live token tagged to a dead ViewModel owner, but no token-scoped successor. There is no second `onCleared()` for that owner.
10. The durable low-quality child remains `CANCELLATION_REQUESTED` with the exact pending-removal token and the primary Download row is absent. `LowQualityRedownloadRepository.reconcileAbandonedUndoItem()` explicitly refuses pending-removal recovery while `DownloadRepository.isLivePendingRemovalToken(token)` is true, so generic same-process reconciliation is blocked by the stale liveness marker.
11. Process restart eventually clears the process-local token/snapshot registries and can allow durable abandoned-debt reconciliation, but ordinary same-process execution has no guaranteed owner capable of resolving the exact token. The low-quality operation can therefore remain nonterminal until restart.

Supporting AndroidX reachability proof: current `androidx.fragment.app.FragmentActivity.onDestroy()` invokes `super.onDestroy()` before `mFragments.dispatchDestroy()`, while `androidx.activity.ComponentActivity` clears its `ViewModelStore` on `ON_DESTROY` when not changing configurations. This ordering is what permits the Activity ViewModel abandonment scan to race Fragment lifecycle work that has not yet received Fragment destroy dispatch.

### Why this is a substantive correctness defect

The remediation treats `pendingRemovalSnapshots` as the authoritative lifecycle ownership inventory, but publishes that inventory record only after the durable destructive transaction and an external filesystem cleanup. A lifecycle owner can therefore disappear in the carrier-creation gap and permanently miss responsibility that is published afterward under its dead identity. This is not merely a lost Snackbar: the same false-live token intentionally prevents low-quality abandoned-debt recovery, leaving durable nonterminal state without a live or successor owner.

### Dedup / candidate-rejection discipline

- **Not `BUG-UNDO-01`:** that defect starts after lifecycle handoff successfully observes and transfers an existing token, then the successor's first convergence read/write fails. Here lifecycle handoff never observes the token because its owner-tagged snapshot has not yet been published.
- **Not `BUG-UNDO-02`:** that defect concerns non-transactional owner release inside a rollback-capable stronger Room transition. This defect follows a successfully committed pending-removal transaction and a later owner-publication gap.
- **Not `BUG-UNDO-03`:** that defect temporarily removes an **already existing** snapshot during restore/commit and can reinsert it after teardown on resolver failure. `BUG-UNDO-05` occurs on the **initial creation path**, before the first snapshot is ever visible to lifecycle inventory, and requires no restore/commit failure.
- **Not `BUG-UNDO-04`:** that defect concerns queued pending-**cancellation** authority committed before Snackbar publication while a wider-lived Fragment ViewModel survives view destruction. `BUG-UNDO-05` concerns Saved pending-**removal** authority where the Activity ViewModel itself is permanently cleared before initial snapshot publication; the handoff runs but inventories too early and misses the future snapshot.
- The canonical `TASKS.md` + `TASKS_DELTA.md` registry contains no entry owning the invariant "a committed pending-removal carrier may not be published into the lifecycle owner inventory after that owner has already completed abandonment."
- Do not reject because Fragment lifecycle cancellation follows Activity destruction. AndroidX destruction order permits Activity ViewModel clearing before Fragment destroy dispatch, and the post-transaction `deleteCache()`/map publication sequence is non-suspending; cancellation does not provide an atomic barrier that couples committed Room state, owner inventory, cache cleanup, and snapshot publication.
- Do not reject because process restart can eventually recover. v4 requires same-process carrier ownership and cross-attempt closure; restart-only repair is insufficient for a supported lifecycle transition.

### Required result

## Ready-to-merge `TASKS_DELTA.md` entry

### P2 — BUG-UNDO-05 — Publish pending-removal ownership before lifecycle abandonment can miss the committed carrier

**State:** Open  
**Reviewed checkpoint:** `15a9231a02a1c5687663f071d851e23c6ad9bd9f`  
**Verification:** `SOURCE-LEVEL ONLY`

**Failure path:** Saved-download left swipe runs `deleteDownloadForUndo()` from Fragment lifecycle work against an activity-owned `DownloadViewModel`. `DownloadRepository.deleteForUndo()` registers a live pending-removal token, then a Room transaction can durably mark the linked low-quality child `CANCELLATION_REQUESTED` with that exact token and delete the primary Download. After commit, `removeDownloadWithSnapshot()` performs recursive cache cleanup, and only afterward does `deleteForUndo()` insert the owner-tagged `pendingRemovalSnapshots[token]`. During that post-commit/pre-snapshot window a permanent Activity destroy clears the Activity `ViewModelStore` before `FragmentActivity` dispatches Fragment destroy. `DownloadViewModel.onCleared()` therefore can run `abandonPendingUndoSnapshots()` while the Fragment deletion work is still in flight. The abandonment scan inventories pending-removal authority only from existing owner-tagged snapshots, so it misses this token and publishes no token-scoped successor. The in-flight delete can then finish its non-suspending cleanup and publish the snapshot under the already-cleared owner; its UI continuation may be cancelled before the Snackbar is created. The exact live removal token remains registered, so low-quality abandoned-debt reconciliation refuses to consume it. The Download row is absent while the linked child can remain nonterminal until process restart clears stale process liveness.

**Why this is a defect:** durable destructive state becomes visible before the carrier used to hand ownership across lifecycle teardown exists. A supported Activity-destruction ordering can therefore create a dead owner that is later published as live, with no same-process successor and with recovery explicitly blocked by the stale live token.

**Dedup:** distinct from `BUG-UNDO-01` (successor exists then first convergence fails), `BUG-UNDO-02` (owner release before rollback-capable stronger commit), `BUG-UNDO-03` (existing snapshot temporarily hidden during restore/commit then resurrected after failure), and `BUG-UNDO-04` (pending-cancellation token committed before Snackbar while wider-lived Fragment ViewModel survives view destruction). This is initial pending-removal snapshot publication after the activity owner has already completed abandonment.

**Ownership / attribution:** incomplete closure / remediation follow-up in live Undo-authority handoff remediation.

Required result:
- establish exact owner/successor visibility before or atomically with durable pending-removal publication;
- validate owner generation before late snapshot publication and transfer to same-process convergence when teardown already won;
- move/recover filesystem cleanup so it cannot widen an unowned post-commit carrier gap;
- preserve exact-token sibling isolation and restart semantics.

Focused verification requirements:
- real Saved Fragment/Activity ViewModel + Room race paused immediately after pending-removal commit and inside cache cleanup;
- permanent Activity destruction before snapshot insertion, then resume creation and prove no dead live owner and guaranteed same-process convergence;
- generic/token-scoped recovery, Activity recreation, sibling isolation, and process-death boundary coverage;
- current evidence remains `SOURCE-LEVEL ONLY` until actual lifecycle + Room wiring executes.

## Ready-to-merge `REVIEW_LESSONS.md` entry

### BUG-UNDO-05 — carrier publication must be reviewed on the creation side of lifecycle ownership, not only abandonment and resolution

- **Reviewed checkpoint:** `15a9231a02a1c5687663f071d851e23c6ad9bd9f`
- **Why previous reviews failed to find this defect:** prior Undo reviews concentrated on what happens once a token/snapshot already exists: successor first-write failure (`BUG-UNDO-01`), stronger-transition rollback (`BUG-UNDO-02`), resolver claim/rollback (`BUG-UNDO-03`), and post-commit Snackbar publication for pending cancellation (`BUG-UNDO-04`). That left an incorrect stopping assumption that `deleteForUndo()` returning a handle implied snapshot ownership had been established early enough for lifecycle handoff. The real ordering is Room commit -> cache cleanup -> owner-tagged snapshot insertion -> UI handle publication.
- **Concrete blind spot / incorrect stopping assumption:** lifecycle abandonment was treated as a consumer of a pre-existing owner inventory, but the review did not pair it with every producer of that inventory and ask whether the producer can cross the owner's destruction boundary before publishing its entry.
- **Relevant v4 items:** `carrier-creation gap`, `persistence barrier and first-write fault injection`, `post-commit barrier`, `filesystem/reference/cleanup authority`, `cross-attempt matrix`, `concurrency/sibling isolation/lock order`, and `terminal fault matrix` were all relevant. They did not expose this earlier because they were applied mainly after the snapshot/token was already considered created; the filesystem helper between durable commit and owner publication was not treated as part of the authority protocol.
- **General lesson:** whenever process-local authority is used to suppress recovery of a durable carrier, review both directions of the lifecycle handoff. It is insufficient to prove that an existing owner can be abandoned safely; every creation path must prove that durable state cannot commit, owner teardown complete, and only then publish a new process-local owner whose generation is already dead.
- **Concrete proposed checklist improvement:** add a mandatory producer-side authority-publication matrix for any process-local map/set/lease that gates durable recovery. Enumerate `pre-durable registration`, `durable commit`, every intervening external/filesystem helper, `owner-tag publication`, `UI capability publication`, and lifecycle teardown. Require a proof that teardown cannot fall between commit and owner publication without a successor.
- **Suggested checklist wording:** "For every durable carrier whose recovery is suppressed by process-local liveness, trace the *creation* ordering as well as abandonment: owner generation established -> process-local liveness registered -> durable carrier commit -> owner-tagged recovery inventory publication -> user/UI capability publication. Inject lifecycle teardown and cancellation at every boundary, including any filesystem/network/helper work between commit and publication. A carrier must never become durable before an observable exact owner/successor exists, and code must never publish a token as live after that owner generation has already been cleared."
- **False-positive guard:** do not report a mere transient publication window if production synchronization proves lifecycle teardown cannot overlap it, if cancellation atomically rolls back the durable carrier, or if a guaranteed exact-token successor is already published before the old owner can disappear. A short window is not itself a defect; the defect requires reachable durable state plus absence/staleness of ownership that changes recovery semantics.
- **Disposition:** PROPOSED
