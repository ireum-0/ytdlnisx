## `BUG-OBSERVE-RETRY-01` — Observe Retry Download decision can be lost before WorkManager carrier acceptance

- Provisional ID: `BUG-OBSERVE-RETRY-01`
- Severity: **P2**
- Verification: **SOURCE-LEVEL ONLY**
- Attribution: pre-existing baseline defect discovered post ledger split; not attributed to the current undo-owner remediation.

### Concrete production-reachable failure path

1. `NotificationUtil.showObserveRetryConfirmation()` presents a real user notification with explicit **Download** and **Ignore** actions. Both actions target `ObserveRetryDecisionReceiver`; the notification is not auto-cancelled by Android itself.
2. The user taps **Download**. `ObserveRetryDecisionReceiver.onReceive()` validates `sourceId`, URL, and action, then immediately cancels the notification before any durable decision or scheduler acceptance exists.
3. The receiver starts `goAsync()`, reloads the source, checks that retry-missing-downloads is still enabled and the source is not STOPPED, and intentionally does **not** add the URL to `retryPromptedLinks`: its own comment says Download is recorded only after the target has actually been inserted into the download queue.
4. It constructs a one-time `ObserveSourceWorker` carrying the exact confirmed URL and `ACTION_DOWNLOAD`, then calls `WorkManager.enqueueUniqueWork("OBSERVE$sourceId", REPLACE, request)`.
5. The returned WorkManager `Operation` is discarded. `pendingResult.finish()` runs in `finally` as soon as the enqueue call returns; there is no callback/future observation that proves the async enqueue completed successfully.
6. If WorkManager accepts the API call but the returned `Operation` later becomes failure, there is no accepted worker carrier. Because ACTION_DOWNLOAD intentionally created no durable retry-decision record before enqueue, no current-session owner remains that can replay that exact user decision. The notification has already been cancelled, so the user sees neither a retained action nor an error.
7. The normal worker path proves that this carrier is semantically meaningful rather than cosmetic: when the worker receives the matching confirmed URL plus `ACTION_DOWNLOAD`, it adds that otherwise-missing previous download to `toProcess` and later queues it. Without that exact input carrier, the explicit Download decision is not executed.
8. A later ordinary Observe Source run may discover the missing item and prompt again because `retryPromptedLinks` was deliberately not updated, but that is a future independent observation, not convergence of the already-committed user command. If the source interval is long, paused later, changed, or the item disappears from the source before the next run, the original explicit Download decision is permanently lost.

### Why this is a correctness/reliability defect

The user action is authoritative execution intent. The implementation destroys the only UI carrier before proving that the external scheduler accepted the worker that materializes that intent, while also deliberately withholding a durable decision record until the worker inserts the target. An asynchronous scheduler failure can therefore turn a confirmed user command into silent no-op with no same-process retry or failure state. This is stronger than a transient UI message failure: the requested download itself does not occur.

This is distinct from:

- `BUG-OBSERVE-03`, which owns loss of the recurring successor WorkManager carrier while durable ACTIVE Observe Source intent remains;
- `BUG-OBSERVE-04`, which owns pause/delete revocation races with already-running stale workers;
- `BUG-QUEUE-03`, which owns Download queue-row -> DownloadWorker carrier loss after the Download row is already durable;
- `BUG-KEYWORD-03`, which owns automatic-keyword durable QUEUED intent -> scheduler carrier loss;
- the current run's rejected automatic-keyword candidate, which is therefore not recorded again.

### Carrier / async-completion matrix

| Stage | Durable/user authority | Carrier/UI state | Failure consequence |
| --- | --- | --- | --- |
| notification displayed | user has not decided yet | actionable notification exists | safe |
| user taps Download | exact user decision exists semantically | receiver invoked | authority obtained |
| receiver cancels notification | no durable ACTION_DOWNLOAD record | UI carrier removed | only receiver coroutine remains |
| before `enqueueUniqueWork` | no durable ACTION_DOWNLOAD record | no worker carrier yet | synchronous exception is logged; decision lost |
| enqueue call returns, `Operation` pending | no durable ACTION_DOWNLOAD record | notification gone; receiver about to finish | async failure can still occur |
| `Operation` failure | no durable ACTION_DOWNLOAD record | no worker accepted; receiver finished | exact decision has no convergence owner |
| `Operation` success + worker runs | worker input is exact decision carrier | worker processes confirmed missing target | intended path |

### Cross-attempt / re-entry matrix

| Re-entry path | Exact user decision restored? | Notes |
| --- | --- | --- |
| same receiver attempt after async enqueue failure | **No** | receiver has finished and never observes the `Operation` |
| ordinary next Observe Source run | **No** | may independently rediscover and prompt again, but does not replay the prior click |
| manual Observe Run Now | **No** | new observation authority; may re-prompt only if conditions still hold |
| pause/stop before next run | **No** | prior Download decision can never materialize |
| source reconfiguration before next run | **No** | future observation semantics can differ from the clicked notification |
| process restart | **No** | there is no durable ACTION_DOWNLOAD decision to reconcile |
| restore | **No** | no durable decision carrier exists to restore |

### Concurrency / ownership

No AB/BA lock inversion is required. The defect is an ownership gap between three domains: notification action authority, BroadcastReceiver lifetime, and asynchronous WorkManager enqueue completion. `goAsync()` extends only the receiver lifetime until `pendingResult.finish()`; the implementation finishes without binding that lifetime to the returned WorkManager `Operation` or first persisting a replayable decision.

### Candidate-rejection proof

- Do not reject because the URL can be prompted again later: a later prompt is a new observation and may never occur; it does not execute or report failure of the original explicit user command.
- Do not reject as `BUG-OBSERVE-03`: that defect has durable ACTIVE source intent and loses a recurring successor carrier. Here the exact one-shot ACTION_DOWNLOAD decision is intentionally not durable before carrier acceptance.
- Do not reject because `enqueueUniqueWork()` was called: the asynchronous returned `Operation` is the completion channel, and this code neither observes it nor establishes another durable convergence owner.
- Do not broaden this finding to ACTION_IGNORE without separate proof. ACTION_IGNORE durably updates `retryPromptedLinks`/`ignoredLinks` before enqueue, so its core semantic decision survives scheduler failure; the defect confirmed here is specifically the Download branch.

### Required result

- Preserve the exact user ACTION_DOWNLOAD decision until WorkManager carrier acceptance is known, either by awaiting/observing the enqueue `Operation` before destroying the only actionable carrier, or by first persisting an exact replayable pending-decision record with a convergence owner.
- On synchronous or asynchronous enqueue failure, do not silently consume the notification/action; surface failure or durably retry the same exact decision.
- If a durable pending-decision record is used, bind it to source ID, canonical URL, and a configuration/generation identity so stale notification decisions cannot later authorize a semantically different source configuration.
- Clear/terminalize the pending decision only after the confirmed target is durably inserted into the download queue or an explicit authoritative refusal is persisted.
- Add production-path tests that force synchronous enqueue throw and asynchronous `Operation` failure after the notification action is received, proving the exact Download decision remains actionable/replayable and is not silently lost. Add source pause/reconfigure and process-restart cases to prove stale decisions do not gain new authority.

### Verification evidence

`SOURCE-LEVEL ONLY`. No executed receiver + real/fake WorkManager asynchronous-failure test was found or run in this review.

### BUG-OBSERVE-RETRY-01 — Preserve Observe Retry Download decisions until scheduler carrier acceptance

**State:** Open  
**Reviewed checkpoint:** `5221f50075173c82d9a3b68a673096a5850ad09f`  
**Verification:** `SOURCE-LEVEL ONLY`

**Failure path:** the Observe Source missing-download notification gives the user explicit Download/Ignore actions backed by `ObserveRetryDecisionReceiver`. When the user taps Download, the receiver cancels the notification immediately, reloads the source, intentionally does not persist the URL into `retryPromptedLinks` because Download is supposed to be recorded only after the worker inserts the target, builds an `ObserveSourceWorker` carrying the exact confirmed URL/Download decision, and calls `WorkManager.enqueueUniqueWork(...)`. The returned asynchronous WorkManager `Operation` is discarded and the `goAsync()` receiver is finished in `finally`. If enqueue later completes as failure, no worker carrier exists, no durable ACTION_DOWNLOAD decision exists, and the only actionable notification has already been removed. The worker path shows that the lost carrier is the authority that admits the otherwise-missing prior item into `toProcess` and ultimately the download queue.

**Why this is a defect:** an explicit user command can be silently consumed without executing the requested download, reporting scheduler failure, or leaving a same-process/durable convergence owner. A later Observe run may independently rediscover and re-prompt the item, but that is not recovery of the original command and may never happen after pause, source change, long intervals, or source membership change. This is distinct from `BUG-OBSERVE-03` (recurring ACTIVE source successor carrier), `BUG-OBSERVE-04` (revocation race), `BUG-QUEUE-03` (durable Download row -> DownloadWorker carrier), and `BUG-KEYWORD-03` (durable keyword QUEUED intent -> worker carrier).

**Ownership / attribution:** pre-existing baseline defect discovered post ledger split; not a remediation regression.

Required result:

- retain the exact ACTION_DOWNLOAD authority until scheduler acceptance is proven, or persist an exact replayable pending-decision carrier before removing the UI carrier;
- handle both synchronous enqueue exceptions and asynchronous WorkManager `Operation` failure without silently losing the command;
- bind any persisted decision to source/configuration generation plus canonical URL and reject stale decisions after reconfiguration/revocation;
- clear the decision only after durable queue insertion or an authoritative terminal refusal;
- add receiver-to-WorkManager production-path tests for async enqueue failure, synchronous throw, pause/reconfigure, retry, and process restart.

### 2026-09-01 — `BUG-OBSERVE-RETRY-01` — Notification decision destroyed before asynchronous carrier acceptance

- **Reviewed checkpoint SHA:** `5221f50075173c82d9a3b68a673096a5850ad09f`
- **Ledger defect entry:** `review-runs/findings/2026-08-31T175936Z__5221f500__findings.md` / proposed `TASKS_DELTA.md` `BUG-OBSERVE-RETRY-01`
- **Production-reachable failure path:** Observe Retry notification -> user taps Download -> receiver cancels notification -> no durable Download decision is written -> one-time `ObserveSourceWorker` is enqueued -> returned asynchronous WorkManager `Operation` is ignored -> receiver finishes -> async enqueue failure leaves neither worker nor UI/durable replay carrier -> exact user decision is lost.
- **Why earlier reviews missed it:** previous carrier reviews started from durable database intent (`BUG-QUEUE-03`, `BUG-KEYWORD-03`, `BUG-OBSERVE-03`) and asked whether WorkManager successfully carried that durable state. This path has the inverse shape: the authoritative state exists first only as a one-shot UI/user action, and the code destroys that UI carrier before the asynchronous external carrier is proven. Because there is intentionally no database write in the Download branch, ledger-centered searches did not expose the gap.
- **Checklist coverage at discovery time:** v4 carrier-creation gap, helper throwable window, persistence barrier, retry/re-entry inventory, concurrency/exact ownership, candidate-rejection discipline, and test/wiring evidence are all relevant. They were not applied deeply enough to ephemeral authorities such as notification actions and BroadcastReceiver lifetimes, nor to asynchronous APIs whose function call returning is earlier than operation completion.
- **General lesson:** authoritative intent need not begin in Room. Any one-shot UI action, notification action, callback, activity result, broadcast, or IPC request can be the sole semantic carrier. Code must not destroy that carrier until a durable or externally accepted successor carrier exists, and asynchronous acceptance must be followed to completion rather than inferred from the enqueue method returning.
- **Proposed checklist improvement:** add an ephemeral-authority handoff audit. For every one-shot user/system callback that launches asynchronous durable work, identify when the original UI/callback carrier becomes unrecoverable, when the successor carrier is actually accepted, what async completion channel reports failure, and what exact replay owner exists in the gap.
- **Suggested checklist wording:** "When authoritative intent originates in a one-shot UI action, notification action, BroadcastReceiver, activity result, callback, or IPC request, treat that ephemeral event as a semantic carrier. Trace `authority obtained -> original carrier destroyed/acknowledged -> durable state write -> asynchronous external enqueue -> enqueue completion -> worker/consumer start`. Do not equate an async API call returning with carrier acceptance. If the original carrier is destroyed before acceptance, require a durable exact replay record or an owner that observes completion and restores/reports the failed action."
- **False-positive guard:** require (1) a production-reachable authoritative one-shot action, (2) destruction/acknowledgement of its only original carrier, (3) a successor API whose acceptance can fail after the call returns or throw before acceptance, (4) no durable/replay owner for the exact action in that gap, and (5) a material semantic effect that fails to occur. Harmless analytics/events or actions that are durably represented before enqueue do not qualify.
- **Disposition:** `PROPOSED`
