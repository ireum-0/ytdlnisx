## BUG-UNDO-04 — view-lifecycle cancellation can strand a durable pending-cancellation token before Snackbar publication

- Severity: **P2**
- Evidence: **SOURCE-LEVEL ONLY**
- Reviewed checkpoint: `15a9231a02a1c5687663f071d851e23c6ad9bd9f`
- Attribution: **remediation regression** (classified only after correctness and dedup review; the exact live-token/abandoned-Undo authority protocol is remediation-era code).

### Scope / invariant

Once a user action durably creates an Undoable cancellation carrier, there must be a continuously owned path from that durable commit to one of two outcomes: (a) the exact Undo capability is actually published to a live UI owner, or (b) ownership is durably/process-locally transferred to a recovery executor that will finalize the abandoned carrier. A view-lifecycle coroutine must not be the only bridge between durable carrier creation and publication of the Snackbar that owns that carrier.

### Concrete production-reachable failure path

1. `QueuedDownloadsFragment` creates `DownloadViewModel` with `ViewModelProvider(this)`, so the ViewModel is scoped to the Fragment, not to the Fragment's view lifecycle.
2. The queued-item delete confirmation launches a coroutine in `viewLifecycleOwner.lifecycleScope`.
3. That coroutine calls `withContext(Dispatchers.IO) { downloadViewModel.beginUndoableCancellation(item.id) }` and waits for the returned pending token. The Snackbar and both of its resolution callbacks are constructed **only after** this suspend call returns to the view-lifecycle coroutine.
4. `DownloadViewModel.beginUndoableCancellation()` reaches `DownloadRepository.beginUndoableCancellation()`. For a linked low-quality queued/waiting item that is eligible to remain Undo-pending, the repository creates an exact `PENDING_USER_CANCELLATION:v1:...` token, registers `livePendingCancellationOwners[token] = undoOwnerId`, then performs the durable Room mutations that cancel the Download and mark the linked low-quality item `CANCELLATION_REQUESTED` with that exact token. The token is returned only after this durable work succeeds.
5. There is therefore a normal lifecycle window after the Room transaction has committed but before the caller has resumed on Main and constructed/shown the Snackbar. Destroy the Fragment **view** in that window, for example by a configuration change or navigation that destroys the view while retaining the Fragment/ViewModel scope. Android's `LifecycleCoroutineScope` contract cancels the scope when that lifecycle is destroyed, so the continuation that would publish the Snackbar can be cancelled and never execute.
6. The committed token nevertheless remains in the process-global live-owner map. The ViewModel's abandonment transfer is only invoked from `DownloadViewModel.onCleared()`. A Fragment-scoped ViewModel is retained across configuration changes, and `onCleared()` is called only when its `ViewModelStoreOwner` is permanently destroyed; destroying/recreating only the view does not supply the required ownership handoff.
7. The recreated/new view has no code that reconstructs a Snackbar or recovers the exact pending token from durable state. Thus the process says the token still has a live Snackbar owner even though no Snackbar/action callback exists.
8. `LowQualityRedownloadRepository.reconcileAbandonedUndoItem()` explicitly refuses to consume a pending user-cancellation item while `isLivePendingUserCancellation(item)` is true and no stronger operation authority exists. The same-process recovery path therefore preserves the stranded carrier instead of converging it.
9. The linked child can remain durably `CANCELLATION_REQUESTED` and the low-quality operation can remain nonterminal for the lifetime of the retained ViewModel/process. Returning to the queue screen does not recreate the lost Undo capability. A later process restart may clear the process-local live-owner map and permit startup recovery, but restart is not a valid publication/convergence barrier for a user action that already committed.

### Why this is a correctness/reliability defect

The app commits cancellation semantics and marks an exact token as having live user-controlled Undo authority, but the only UI carrier for that authority can be cancelled before it is ever presented. Recovery then intentionally refuses to act because the stale process-local owner map claims the token is still live. This is not cosmetic Snackbar loss: it can leave low-quality operation state nonterminal and can prevent the operation from naturally completing/reconnecting until a later owner clear or process restart. The durable state and actual authority therefore disagree.

- `BUG-UNDO-02` is different: it covers a stronger rollback-capable Room transition deleting process-local owner identity before the stronger durable commit.
- `BUG-UNDO-03` is different: it covers `restoreUndo()`/`commitUndo()` temporarily removing an already-published snapshot while `onCleared()` races, then restoring it into a dead owner after failure.

### Direct platform contract used in reachability proof

AndroidX documents `LifecycleCoroutineScope` as cancelled when its Lifecycle is destroyed. AndroidX also documents that ViewModels are retained as long as their `ViewModelStoreOwner` remains alive and that a `ViewModelStore` is retained across configuration changes; `onCleared()` is for permanent owner destruction. Those contracts make view-scope cancellation without ViewModel abandonment a supported production lifecycle, not a hypothetical unsupported sequence.

### Required result

Make post-commit Undo publication an explicit ownership protocol. The durable pending token must not be classified as live Snackbar authority until publication is actually established, or the caller must install a guaranteed post-commit/NonCancellable handoff that transfers the exact token to abandoned-Undo convergence whenever the UI publication scope is cancelled or otherwise fails before the Snackbar callback owner exists. A recreated view may alternatively reconstruct the exact durable capability, but reconstruction must preserve the immutable token and prove singular ownership. Do not rely on eventual `ViewModel.onCleared()` or process restart.

### BUG-UNDO-04 — close the post-commit gap between pending-cancellation creation and Snackbar authority publication (P2)

- **Reviewed checkpoint:** `15a9231a02a1c5687663f071d851e23c6ad9bd9f`
- **Verification:** `SOURCE-LEVEL ONLY`
- **Failure path:** `QueuedDownloadsFragment` performs queued-item Undoable cancellation in `viewLifecycleOwner.lifecycleScope`. It first awaits `downloadViewModel.beginUndoableCancellation()` on IO; only after that suspend call returns does it create/show the Snackbar and install Undo/dismiss callbacks. For a low-quality-linked queued/waiting Download, the repository can already have committed the Download cancellation and linked `CANCELLATION_REQUESTED` exact token and registered that token as live Snackbar authority. If the Fragment view lifecycle is destroyed after this durable commit but before the caller resumes/publishes the Snackbar, the lifecycle scope is cancelled and the UI capability is never created. The Fragment-scoped ViewModel can survive configuration/view recreation, so `onCleared()` does not necessarily run to transfer ownership. The recreated view does not reconstruct the exact token. Same-process low-quality recovery sees the stale live-token entry and intentionally refuses to consume the carrier. The linked operation can therefore remain nonterminal until later ViewModel destruction or process restart.
- **Correctness impact:** durable state claims a live user Undo owner that does not exist, causing lost Undo capability and potentially stranded low-quality operation state. Outcome/convergence can depend on an unrelated later process restart.
- **Dedup:** distinct from `BUG-UNDO-01` (handoff after `onCleared()`), `BUG-UNDO-02` (pre-commit authority release inside rollback-capable stronger transition), and `BUG-UNDO-03` (restore/commit snapshot temporarily removed then resurrected into a dead owner). This defect is the carrier-creation/publication gap before any Snackbar owner exists and without ViewModel clearing. No canonical `TASKS.md`/`TASKS_DELTA.md` entry owns this invariant.
- **Attribution:** remediation regression.
- **Required result:** after durable pending-token commit, guarantee exactly one continuous owner through Snackbar publication or token-scoped abandoned convergence; view-scope cancellation before publication must transfer the exact token instead of leaving stale live-owner metadata. Do not rely on ViewModel clear/restart.
- **Focused verification:** real Fragment/Room lifecycle test latched after durable commit and before Snackbar publication; destroy/recreate only the view while retaining ViewModel; prove exact owner transfer/reconstruction, no stale live map, same-process convergence, and restart-independent semantics.

## Ready-to-merge `REVIEW_LESSONS.md` entry

### BUG-UNDO-04 — durable capability creation was reviewed, but UI capability publication was treated as immediate

- **Reviewed checkpoint:** `15a9231a02a1c5687663f071d851e23c6ad9bd9f`
- **Why previous reviews missed it:** prior Undo reviews concentrated on repository transactions, live-token identity, `onCleared()` abandonment, failed convergence, and races while resolving an already-created Snackbar capability. They implicitly treated the successful return of `beginUndoableCancellation()` as equivalent to successful publication of that capability to the user.
- **Concrete blind spot / incorrect stopping assumption:** the review stopped at the repository/ViewModel boundary and did not trace the returned exact token through the caller's lifecycle-bound coroutine until the Snackbar action/dismiss owner was actually installed. It also conflated the Fragment's view lifecycle with the wider Fragment `ViewModelStore` lifetime, so `onCleared()` appeared to cover lifecycle loss when it does not cover ordinary view destruction/configuration retention.
- **Relevant v4 items:** scope/invariant, first authoritative observation, carrier-creation gap, post-commit barrier, recovery semantic identity, cross-attempt matrix, expected-identity mutability, test/wiring evidence, and CLEAN gate were all directly relevant. They did not expose the issue earlier because "carrier created/returned" was treated as the end of carrier creation instead of distinguishing durable carrier creation from **consumer capability publication** under a different lifecycle owner.
- **General lesson:** when a durable operation creates a token/handle that must be delivered to UI or another consumer, successful persistence and successful function return do not prove the consumer owns it. Every suspension, dispatcher hop, lifecycle boundary, callback registration, and UI publication between commit and usable capability is a separate handoff window. Producer lifetime and consumer lifetime must be compared explicitly.
- **Concrete proposed checklist improvement:** add a producer-to-consumer publication audit for every durable token/handle/capability. Identify the lifecycle/scope of the producer, returned value, consumer callback/UI, and recovery owner; fault/cancel each boundary after durable commit but before consumer registration; require an exact successor owner or reconstructable immutable identity.
- **Suggested checklist wording:** “For every durable token, handle, lease, Undo capability, notification action, or callback authority returned across a coroutine/lifecycle boundary, distinguish **carrier creation** from **consumer publication**. After the durable commit, enumerate every dispatcher hop, suspension/resumption, lifecycle cancellation point, callback registration, and UI/notification publication before the consumer can act. At each point, cancel/destroy the consumer scope and prove the exact immutable carrier is either already usable by that consumer or atomically transferred to a recovery owner. Compare producer and consumer lifetimes explicitly; a wider ViewModel/service lifetime does not imply a view/callback lifetime. Do not treat successful return as publication proof.”
- **False-positive guard:** reject only when publication is synchronous within the same non-cancellable ownership boundary as the durable commit, or when cancellation before publication is proven to invoke an exact token-scoped compensating/recovery handoff, or when the consumer can deterministically reconstruct the same immutable capability without broadening authority or duplicating ownership.
- **Disposition: PROPOSED**
