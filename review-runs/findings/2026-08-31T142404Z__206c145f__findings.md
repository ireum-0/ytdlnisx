## BUG-HARDSUB-05 — P2 — Do not report Hard-sub Scan Now started before WorkManager accepts its carrier

### Concrete production-reachable failure path

`ProcessingSettingsFragment` exposes the user-facing `hard_sub_scan_now` preference. Its click handler calls `HardSubScanWorker.enqueue(requireContext())` and immediately shows the `hard_sub_scan_started` toast. `HardSubScanWorker.enqueue()` builds a one-time constrained request and calls `WorkManager.enqueueUniqueWork(UNIQUE_WORK_NAME, ExistingWorkPolicy.REPLACE, request)`, but discards the returned WorkManager `Operation` and returns `Unit` immediately.

The WorkManager enqueue call is asynchronous. Therefore invocation is not proof that the unique work was durably accepted. If enqueue acceptance fails asynchronously after `enqueue()` returns, the UI has already told the user that the scan started, but there is no accepted `HardSubScanWorker` generation, no durable scan-operation row, no retry/convergence owner, and no callback that can replace the false-start indication with failure. The manual scan request is simply lost.

This is production reachable without malformed state: the Settings action is a normal supported entry point, and the code path contains no acceptance observer or durable handoff carrier. A process death after the UI call but before scheduler acceptance has the same semantic result: the requested scan has no app-owned durable intent from which startup can reconstruct it.

### Correctness impact

The action's explicit semantics are to start a current hard-sub eligibility scan. The implementation reports that action as started before its external execution carrier is established. On enqueue failure, no scan occurs and the user receives a false-success/start indication. Because hard-sub eligibility is itself durable and can already be stale across later subtitle/source changes (`BUG-HARDSUB-04`), losing an explicitly requested rescan can leave those stale exclusions/results in place while the UI claims the corrective scan began.

This is a substantive reliability/state-reporting defect rather than defensive hardening: there is a concrete user request, a fallible asynchronous carrier boundary, an unconditional success-facing result, and no same-process or restart recovery owner for the lost request.

- `TASKS.md` contains `BUG-HARDSUB-01`, which owns ambiguous/non-authoritative subtitle lookup semantics inside an executing scan, not scan dispatch acceptance.

- Existing `review-runs/findings/` inventory contains the previously recorded Undo findings, low-quality enqueue finding, and daily scheduler alarm enqueue finding; none owns the `hard_sub_scan_now -> HardSubScanWorker.enqueue()` carrier.
- No `BUG-HARDSUB-05` entry exists in `TASKS.md` or `TASKS_DELTA.md`.

### Ownership / attribution

Pre-existing production defect on the pinned checkpoint, discovered during post-split scheduled review. It is not attributed to the current `206c145f` Undo/low-quality carrier remediation commit; `HardSubScanWorker.kt` and `ProcessingSettingsFragment.kt` are outside that commit's changed-file set.

### Required result

- Treat the WorkManager `Operation` returned by `enqueueUniqueWork()` as the carrier-acceptance boundary for the explicit Hard-sub Scan Now request.
- Do not show `hard_sub_scan_started` until enqueue acceptance succeeds; on acceptance failure, surface a truthful failure result.
- If the product contract requires the scan request to survive transient scheduler failure or process death, establish a durable scan-request/generation carrier before dispatch and provide same-process/startup convergence until WorkManager accepts that exact generation.
- Preserve `ExistingWorkPolicy.REPLACE` semantics deliberately: replacing an existing generation must not let completion/failure from the superseded request report success/failure for a newer Scan Now generation.
- Add focused production-path tests for synchronous enqueue throw, asynchronous `Operation` failure, successful acceptance, repeated Scan Now/REPLACE ordering, process death between request and acceptance if durable recovery is adopted, and a control proving the accepted worker still scans and hands any resulting queued Downloads to the separately governed Download carrier path.

## Mandatory v4 review sections

### Scope / invariant

Invariant: an explicit user-facing request must not be reported as started unless its execution carrier has been accepted, or an app-owned durable successor exists that guarantees convergence to an accepted carrier or truthful failure.

### First authoritative observation

The user click on `hard_sub_scan_now` is the authoritative request to perform a new hard-sub scan under current settings/source state.

### Carrier-creation gap

The gap is `HardSubScanWorker.enqueue()` invocation -> asynchronous completion of the returned WorkManager `Operation`. No durable app-owned scan request exists in this interval, and the returned operation is discarded.

### Helper-internal throwable / async-completion window

The helper returns immediately after `enqueueUniqueWork()`. A synchronous exception can propagate to the preference callback, but asynchronous scheduler acceptance failure occurs after return and is invisible to both helper and caller. The caller nevertheless shows the started toast immediately.

### Semantic preservation

`requested` and `accepted` are collapsed into the same `Unit` return / success-facing toast. The distinction is correctness-relevant because only accepted work has an execution carrier.

### Persistence barrier / first-write fault injection

There is no app-owned durable scan-operation write before dispatch. Therefore the relevant first external persistence boundary is WorkManager's enqueue acceptance itself. Inject asynchronous failure of that operation: current code has no failure path, no retry carrier, and still reports started.

### Recovery semantic identity

None exists for the lost Scan Now generation. A later manual Scan Now is a new request, not recovery of the original request. An unrelated future app launch does not reconstruct the lost scan request from durable app state.

### Multi-ledger / process-death durability

No scan-specific ledger is created. Existing per-History hard-sub flags are eligibility/result state, not proof that a new scan request is pending. Process death before WorkManager acceptance therefore loses the request without a durable generation to distinguish it from no request.

### Post-commit barrier

Not applicable before carrier acceptance. Once WorkManager accepts the request, worker-internal persistence/terminal semantics are separately governed by existing hard-sub and Download defects.

### Outer catch / final result

There is no caller-side async completion handler. The final user-visible result is the unconditional started toast, regardless of asynchronous enqueue failure.

### Filesystem/reference/cleanup authority

Not reached when the worker carrier is lost.

### Retry / reconfigure / raw-requeue inventory

- Subtitle-language reconfiguration then Scan Now: same vulnerable dispatch path.
- Automatic later worker execution: no durable scan request exists to trigger it.

### BUG-HARDSUB-05 — Do not report Hard-sub Scan Now started before WorkManager accepts its carrier

**State:** Open  
**Reviewed checkpoint:** `206c145f0cf8ff8462ec18cf7781dbbc2e1b0903`  
**Verification:** `SOURCE-LEVEL ONLY`

**Failure path:** `ProcessingSettingsFragment` handles the explicit `hard_sub_scan_now` action by calling `HardSubScanWorker.enqueue(requireContext())` and immediately showing the `hard_sub_scan_started` toast. `HardSubScanWorker.enqueue()` submits unique work with `ExistingWorkPolicy.REPLACE` but discards the returned WorkManager `Operation`. Because enqueue acceptance is asynchronous, a scheduler/database failure can occur after the helper returns. The UI has already reported that the scan started, yet no HardSubScanWorker generation was accepted, no durable scan-request record exists, and there is no same-process or startup convergence owner that retries the exact request. Process death in the request-to-acceptance window has the same lost-request result.

**Why this is a defect:** Scan Now is a concrete user-requested correctness operation over current subtitle/source eligibility. Invocation of a fallible async scheduler is not carrier acceptance. The implementation can silently lose the requested scan while reporting it as started, leaving current hard-sub eligibility state unchanged until the user happens to issue another request. A later scan is not necessarily semantically identical because subtitle settings and source metadata are mutable. This is distinct from `BUG-QUEUE-03`, which owns DownloadWorker carrier loss after scan-produced Download rows are already durable, and from `BUG-HARDSUB-04`, which owns stale exclusion invalidation inside later scans.

**Ownership / attribution:** pre-existing production defect discovered post ledger split; not a remediation regression.

Required result:

- observe the exact WorkManager enqueue `Operation` and report started only after acceptance;
- surface truthful failure when the carrier is rejected;
- if Scan Now must survive transient scheduler failure/process death, persist an exact scan-request generation and converge it until accepted or explicitly failed;
- bind `REPLACE` completion/reporting to the newly requested generation so an older/superseded generation cannot determine the new request's UI result;
- add production-path WorkManager tests for synchronous throw, asynchronous operation failure, success, repeated REPLACE requests, and restart/convergence if durable recovery is implemented.

### 2026-08-31 — `BUG-HARDSUB-05` — Explicit user action reports start before async carrier acceptance

- **Reviewed checkpoint SHA:** `206c145f0cf8ff8462ec18cf7781dbbc2e1b0903`
- **Ledger defect entry:** `review-runs/findings/2026-08-31T142404Z__206c145f__findings.md` / proposed `TASKS_DELTA.md` `BUG-HARDSUB-05`
- **Production-reachable failure path:** Processing settings `hard_sub_scan_now` click -> `HardSubScanWorker.enqueue()` -> `WorkManager.enqueueUniqueWork(REPLACE, request)` returns an asynchronous `Operation` -> helper discards it and returns -> UI immediately reports scan started -> async enqueue failure leaves no accepted worker and no durable retry/recovery owner.
- **Why earlier reviews missed it:** prior carrier reviews concentrated on workflows that first persisted an explicit Room ledger (`Queued` Downloads, date-fetch operations, keyword sync intent, scheduler alarms). That focus made the absence of a dedicated app ledger look like a reason to stop rather than a stronger signal: an explicit user action can still require carrier acceptance even when its only intended durable carrier is the external scheduler itself. Review also followed executing HardSubScanWorker semantics and scan-result flags more deeply than the pre-worker Settings-to-WorkManager handoff.
- **Checklist coverage at discovery time:** v4 carrier-creation gap, helper throwable window, semantic preservation, retry/re-entry, and test/wiring evidence all apply. They were not applied broadly enough to user-triggered `Unit` scheduling helpers with no preceding durable row. The missing question was whether the caller reports success/start before asynchronous external acceptance, even when no app-owned ledger exists.
- **General lesson:** every explicit action that delegates execution to a fallible asynchronous external carrier has an acceptance boundary. Lack of an app-owned durable operation row does not remove the boundary; it means the scheduler's acceptance result may be the only proof the request exists. `Unit`/fire-and-forget helpers must not collapse request submission and accepted execution when the caller exposes a success/start result.
- **Proposed checklist improvement:** add an async-carrier acceptance audit to every user-triggered or one-shot scheduling helper, regardless of whether a Room/domain ledger precedes it. Inventory returned `Operation`/Future/Task/Deferred/callback handles, determine the exact acceptance point, and compare it with UI success/reporting and restart recovery.
- **Suggested checklist wording:** "For every explicit user/system one-shot action that hands execution to WorkManager, AlarmManager, a service, executor, provider, or another asynchronous carrier, identify the carrier's actual acceptance/completion handle even when no app-owned durable ledger exists. Treat fire-and-forget `Unit` wrappers and ignored `Operation`/Future/Task results as a carrier-creation gap when the caller reports started/success. Prove either (a) the exact request is accepted before success is reported, or (b) a durable generation-specific owner survives failure/process death and converges to acceptance or truthful terminal failure."
- **False-positive guard:** require (1) a production-reachable explicit or one-shot request, (2) a documented/source-proven asynchronous acceptance/failure boundary, (3) caller behavior that reports start/success or otherwise drops ownership before that boundary, and (4) no separate durable owner that guarantees exact-request convergence. Background best-effort hints with no user-visible or semantic execution contract are insufficient.
- **Disposition:** `PROPOSED`
