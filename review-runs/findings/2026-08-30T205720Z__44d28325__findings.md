## BUG-UNDO-02 — rollback-capable stronger transition releases process-local Undo authority before durable commit

- Severity: **P2**
- Evidence: **SOURCE-LEVEL ONLY**
- Reviewed checkpoint: `44d2832532a24a6aa13a27838208c07a729c9bf0`
- Attribution: **remediation regression** (classified only after correctness/dedup review; the affected exact-owner/live-token machinery is part of the remediation-era Undo convergence work).

### Scope / invariant

If a stronger action supersedes a still-live Undoable cancellation, loss of the exact process-local Undo owner must become externally observable only after the stronger durable transition commits, or the exact previous owner must be restored on transaction rollback. A failed Room transaction must not silently change the semantic authority of the durable state it rolled back to.

### Concrete production-reachable failure path

1. A Download has a live Undoable cancellation. Durable low-quality state is `CANCELLATION_REQUESTED` with an exact pending-cancellation token, and `livePendingCancellationOwners[token]` records the repository/ViewModel owner that is still allowed to restore it.
2. A stronger repository action such as `moveToSaved(id)` runs inside `database.withTransaction`. The production path also reaches the same linked-state helper from save/upsert handling.
3. `markLinkedDownloadSaved()` observes the linked `CANCELLATION_REQUESTED` row and, for a pending user-cancellation item, calls `releaseLivePendingCancellationToken(ledgerItem.reasonCode)` **before** the durable cancellation write `ledgerDao.markCancelledByDownloadId(...)` and any later operation-terminalization writes complete.
4. `releaseLivePendingCancellationToken()` removes the entry from the process-global `ConcurrentHashMap`. That mutation is not governed by Room and therefore cannot be rolled back with the surrounding SQL transaction.
5. Inject a Room/SQLite failure at `markCancelledByDownloadId`, `finishOperation`, or another later write in the same transaction. Room rolls back the Download/ledger writes, leaving the prior durable `CANCELLATION_REQUESTED` token intact and the stronger save transition uncommitted.
6. The process-local exact owner nevertheless remains deleted. The pre-existing Snackbar/Undo handle still refers to the same durable token, but `undoPendingCancellation()` now reads `liveOwner == null`; its `canRestore` predicate requires `liveOwner == undoOwnerId`, so it cannot restore the original status and falls through to committing/finalizing the pending cancellation.
7. Same-process reconciliation likewise sees durable pending state without a live owner and may converge it as abandoned. A later restart also treats the durable pending carrier as having no process-local owner. Thus a transient persistence failure in an action that did **not** commit can irreversibly change the semantics of the still-durable Undo operation.

Source anchors on the pinned checkpoint:
- `DownloadRepository.moveToSaved()` executes inside `database.withTransaction`, sets Saved and calls `markLinkedDownloadSaved()`.
- `markLinkedDownloadSaved()` releases the live token before `markCancelledByDownloadId()` / possible `finishOperation()`.
- `releaseLivePendingCancellationToken()` directly removes the token from `livePendingCancellationOwners`.
- `undoPendingCancellation()` permits restoration only when `liveOwner == undoOwnerId`; otherwise the exact pending carrier falls through to commit/finalization.

### Why this is a correctness defect

The failed stronger transaction is durably rolled back but its non-transactional authority side effect is not. The observable state therefore no longer represents the pre-transaction semantics: a still-live Undoable cancellation can become effectively abandoned/non-restorable solely because an unrelated stronger persistence attempt failed. This is state/semantic corruption, not defensive hardening.

### Dedup / ownership evidence

- `TASKS.md` and `TASKS_DELTA.md` were searched as the effective canonical registry before classification; no existing entry owns the invariant "rollback of a stronger Room transition must restore process-local pending-cancellation owner identity".
- Existing `review-runs/findings/...__44d28325__findings.md` owns `BUG-UNDO-01`, but that defect is different: it covers deliberate ViewModel lifecycle abandonment followed by a failed convergence read/write and loss of a same-process recovery owner. `BUG-UNDO-02` instead covers **premature irreversible live-owner destruction inside a Room transaction that subsequently rolls back**. The stronger action itself does not durably commit, yet Undo authority is lost.

### BUG-UNDO-02 — rollback-capable stronger transition can destroy live Undo authority before durable commit (P2)

- **Reviewed checkpoint:** `44d2832532a24a6aa13a27838208c07a729c9bf0`
- **Verification:** `SOURCE-LEVEL ONLY`
- **Failure path:** a live pending-cancellation token is durably `CANCELLATION_REQUESTED` and owned by the active repository/ViewModel. `moveToSaved`/linked save processing executes in `database.withTransaction`; `markLinkedDownloadSaved` calls `releaseLivePendingCancellationToken(token)` before `markCancelledByDownloadId` and possible operation-terminalization writes. If a later DAO/SQLite write throws, Room rolls the durable transition back but cannot roll back the process-global owner-map deletion. The old pending token therefore remains durable while its exact live owner is gone. The existing Undo path requires `liveOwner == undoOwnerId` to restore; after this failed stronger action it instead falls through toward committing/finalizing cancellation. Same-process reconciliation/restart can likewise treat the rolled-back pending carrier as abandoned.
- **Correctness impact:** a persistence attempt that fails and durably rolls back can still make an otherwise-live Undo irreversible. Durable state and semantic authority diverge, allowing unexpected cancellation/finalization after a failed save/stronger transition.
- **Dedup:** distinct from `BUG-UNDO-01`, which covers deliberate ViewModel owner abandonment followed by failed convergence. This defect is transaction atomicity: non-transactional exact-owner authority is destroyed before a stronger durable transition commits and is not restored on rollback. No `TASKS.md`/`TASKS_DELTA.md` entry owns this invariant.
- **Attribution:** remediation regression.
- **Required result:** release the exact live owner only after durable stronger-transition commit, or compensate rollback by restoring the same immutable token/owner identity before Undo/recovery can observe the state.
- **Focused verification:** real Room/repository fault injection after every in-transaction live-token release; prove durable rollback plus exact owner preservation, successful Undo restoration, reconciliation non-consumption while owner is live, and post-commit release on successful stronger transition.

## Ready-to-merge `REVIEW_LESSONS.md` entry

### BUG-UNDO-02 — non-transactional authority side effects hidden inside Room transactions

- **Reviewed checkpoint:** `44d2832532a24a6aa13a27838208c07a729c9bf0`
- **Why previous reviews missed it:** prior Undo reviews treated durable Room state and process-local live-owner bookkeeping as adjacent but mostly separate recovery concerns. The code was syntactically inside `withTransaction`, which made the stronger transition look atomic, while the in-memory owner-map deletion was not actually governed by that transaction.
- **Concrete blind spot / incorrect stopping assumption:** review stopped after confirming that Download/ledger writes would roll back together and that successful stronger transitions revoked old Undo authority. It did not fault-inject every later persistence call **after each non-transactional authority mutation inside the transaction** and ask whether rollback restores the exact pre-transaction semantic capability.
- **Relevant v4 items:** semantic preservation, persistence barrier/first-write fault injection, recovery semantic identity, post-commit barrier, expected-identity mutability, cross-attempt matrix, and concurrency/sibling isolation were all relevant. They did not expose the issue earlier because they were applied primarily to durable writes and external post-commit work, not to in-memory authority maps mutated within a Room transaction body.
- **General lesson:** lexical placement inside a database transaction does not make process memory, files, native signals, WorkManager operations, notifications, locks, leases, or capability-token maps transactional. Any such side effect that changes semantic authority must either occur after commit or have exact rollback compensation.
- **Concrete proposed checklist improvement:** for every transaction, inventory all side effects not governed by the same transactional substrate and fault-inject each later persistence barrier after each side effect. Verify that rollback restores not only values but the exact prior authority/identity before any retry, Undo, recovery, or sibling path can observe it.
- **Suggested checklist wording:** “For every Room/DB transaction, enumerate non-transactional side effects performed inside its body (in-memory owner/lease/token maps, files, process signals, WorkManager enqueue/cancel, notifications, external services). After each such side effect, fault-inject every remaining persistence call. If the DB transaction rolls back, prove the side effect is compensated to the exact immutable prior identity before any retry/recovery/Undo path can observe the rolled-back durable state. Otherwise move the side effect behind a post-commit barrier.”
- **False-positive guard:** reject only when the side effect is provably advisory/idempotent and cannot affect authorization, semantic decisions, cleanup, retry, or recovery, or when every rollback path restores the exact immutable prior identity before it can be observed.
- **Disposition: PROPOSED**
