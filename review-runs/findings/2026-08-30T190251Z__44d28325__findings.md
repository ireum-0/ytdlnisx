## BUG-UNDO-01 — Keep a same-process recovery owner after lifecycle abandonment convergence fails

**Severity:** P2  
**Reviewed checkpoint:** `44d2832532a24a6aa13a27838208c07a729c9bf0`  
**Verification:** `SOURCE-LEVEL ONLY`  
**Attribution:** incomplete closure / remediation follow-up in the live Undo-authority remediation.

### Concrete production-reachable failure path

`DownloadViewModel.onCleared()` launches a detached IO coroutine and calls `DownloadRepository.abandonPendingUndoSnapshots()`. This is the lifecycle handoff used when the UI owner capable of resolving a Snackbar disappears.

For a linked queued/waiting low-quality Download with a live pending cancellation token, `beginUndoableCancellation()` has already durably changed the Download to `Cancelled` and the linked child to `CANCELLATION_REQUESTED` with an exact `PENDING_USER_CANCELLATION:v1:...` reason, while the process-local map identifies the live Undo owner. During `abandonPendingUndoSnapshots()`, the repository first removes that owner from `livePendingCancellationOwners`, then performs only a best-effort lookup and `runCatching { commitPendingCancellation(...) }`. The analogous pending-removal path removes the in-memory snapshot and unregisters its live token before `runCatching { commitRemovalSnapshot(snapshot) }`.

If the first convergence persistence attempt throws after ownership has been released, the exception is swallowed. For pending cancellation, the durable Download remains `Cancelled` and the linked child remains nonterminal `CANCELLATION_REQUESTED` with the exact token; for pending removal, the Download row remains absent and the linked child remains token-owned `CANCELLATION_REQUESTED`. The original Snackbar owner is gone and the in-memory removal snapshot, if applicable, has already been discarded.

The repository does contain a runtime-independent *algorithm*, `LowQualityRedownloadRepository.reconcileAbandonedUndoDebts()`, that can consume these now-abandoned durable carriers, but the normal lifecycle handoff does not invoke or schedule it after its best-effort write fails. The production call found in `App.onCreate()` invokes `LowQualityRedownloadManager.reconcileCancellationDebt()` only as startup reconciliation. `LowQualityRedownloadManager.reconcile()` does not call `reconcileAbandonedUndoDebts()`, and `abandonPendingUndoSnapshots()` does not call `LowQualityRedownloadLedger.scheduleCancellationConvergence()` or create another WorkManager/process-local retry owner for this failure.

Therefore a transient Room/read/write failure during ViewModel abandonment can leave the live application process with durable abandoned Undo debt and no guaranteed same-process actor that will retry it. Cold process restart can repair the state through startup cancellation reconciliation, but requiring an app restart is not a valid recovery barrier for a lifecycle event that can occur during ordinary navigation.

### Why this is substantive

This is not merely delayed cleanup. A pending linked child is intentionally nonterminal and participates in the low-quality execution/admission guards. Once the Snackbar owner is gone, keeping `CANCELLATION_REQUESTED` indefinitely can leave the low-quality parent nonterminal and the affected Download non-runnable/removed even though there is no longer any user-visible Undo authority. The operation can remain stuck until process restart after a routine transient persistence failure.

The current remediation explicitly distinguishes live Undo authority from abandoned debt, so releasing the owner is a semantic handoff. A handoff whose first recovery write can fail must itself leave a durable or live retry carrier. Swallowing that failure without scheduling the already-existing abandoned-debt reconciler violates that invariant.

### Dedup / candidate-rejection discipline

- Not `BUG-CANCEL-04`: that defect owns preservation of Cancel/Pause semantics in pre-write execution-recovery carriers; this path begins after an item-level Snackbar cancellation/removal token is already durably committed and concerns lifecycle ownership transfer plus failure of the first abandoned-debt convergence write.
- Not the existing low-quality cancellation/native convergence defects: those schedule operation cancellation convergence after `operation.cancelRequested` or native quiescence failure. Here the parent need not have `cancelRequested=true`, and the missing carrier is specifically the abandoned Undo token after its process-local owner has been released.
- Not rejected because startup can repair it: v4 requires recovery-write failure and same-process/cross-attempt behavior. Startup-only repair leaves an ordinary live-process lifecycle path indefinitely stuck.
- Not rejected because `reconcileAbandonedUndoDebts()` exists: an uninvoked helper is not a recovery carrier. The production abandonment path neither calls nor schedules it after the swallowed failure.

### Checklist-v4 execution summary

- **Scope/invariant:** once live Snackbar ownership is abandoned, each durable pending Undo token must either converge immediately or remain owned by a guaranteed retry carrier.
- **First authoritative observation:** exact live-owner map + durable `CANCELLATION_REQUESTED` token identifies whether Undo is still privileged.
- **Carrier-creation gap:** live owner is removed before convergence succeeds; no successor retry carrier is published.
- **Helper-internal throwable window:** pending-item lookup, `commitPendingCancellation()`, and `commitRemovalSnapshot()` are fallible after ownership release.
- **Semantic preservation:** token identity is preserved durably, but executor identity is not.
- **Persistence barrier / first-write fault injection:** first post-abandon convergence write can fail; current code swallows it.
- **Recovery semantic identity:** `reconcileAbandonedUndoDebts()` can derive exact token semantics, but is not scheduled by this path.
- **Multi-ledger/process-death durability:** Download + low-quality child survive; pending-removal Download may already be absent; startup can recover from the child token.
- **Post-commit barrier:** owner release is process-local and occurs before durable child terminalization.
- **Outer catch/final result:** `runCatching` consumes the convergence exception and `onCleared()` has no result channel/retry publication.
- **Filesystem/reference/cleanup authority:** no primary media filesystem mutation is required; pending-removal row deletion/snapshot loss is enough.
- **Retry/reconfigure/raw-requeue:** normal queue/reconfigure admission is fenced by linked `CANCELLATION_REQUESTED` debt; no guaranteed re-entry repairs it.
- **Expected-identity mutability:** exact token remains immutable, which makes safe recovery possible but does not create an executor.
- **Concurrency/sibling isolation:** ownership maps are token-scoped; primary failure needs no sibling race. A fix must retry only the exact abandoned token/operation.
- **Test/wiring evidence:** source and recent test diffs cover normal abandonment transfer and startup reconciliation, but no executed production-path first-abandon-write failure with same-process convergence was found.
- **CLEAN gate:** failed because first recovery-write failure lacks a live same-process successor carrier.

### BUG-UNDO-01 — Keep abandoned Download Undo debt owned after lifecycle convergence failure

**State:** Open  
**Reviewed checkpoint:** `44d2832532a24a6aa13a27838208c07a729c9bf0`  
**Verification:** `SOURCE-LEVEL ONLY`

**Failure path:** `DownloadViewModel.onCleared()` calls `DownloadRepository.abandonPendingUndoSnapshots()`. The repository releases/removes the exact process-local pending cancellation/removal Undo owner first, then performs only best-effort `runCatching` convergence. If the pending-item read or first commit throws, the exception is swallowed. The durable low-quality child remains `CANCELLATION_REQUESTED` with the exact pending token (and for removal the Download row is already absent), but the Snackbar owner and any in-memory removal snapshot are gone. `reconcileAbandonedUndoDebts()` can consume this state, yet this lifecycle path neither invokes nor schedules it after failure; production startup is the guaranteed caller of `reconcileCancellationDebt()`. The live process can therefore strand the operation until application restart.

**Why this is a defect:** releasing live Undo authority is a semantic ownership handoff. A transient failure at the first successor write cannot leave a nonterminal durable token without a same-process executor. The stuck child fences linked operation/admission state and can leave the parent nonterminal despite there being no longer any user-visible Undo authority. Startup-only repair does not close an ordinary lifecycle persistence-fault path.

**Ownership / attribution:** incomplete closure / remediation follow-up in the live Undo-authority remediation; distinct from execution-level `BUG-CANCEL-04` and operation/native cancellation convergence.

Required result:
- publish a token-scoped same-process recovery owner whenever lifecycle abandonment releases live Undo authority;
- retry exact abandoned-debt convergence across first read/write failure until terminal/resolved or superseded by stronger durable authority;
- preserve startup recovery across process death and sibling/live-token isolation.

Focused verification requirements:
- real ViewModel lifecycle + Room test for first pending-cancellation commit failure and pending-removal commit failure after owner release;
- first pending-item read failure and subsequent recovery-write failure;
- live sibling token isolation, process death at each handoff boundary, restart exact-once convergence, and manual retry/reconfigure fencing until resolution;
- verification must exercise actual ViewModel/Room/manager reconciliation wiring. Current verification is `SOURCE-LEVEL ONLY`.

## Ready-to-merge `REVIEW_LESSONS.md` entry

### Lesson proposal — BUG-UNDO-01 lifecycle abandonment is itself a recovery-carrier handoff

**Reviewed checkpoint:** `44d2832532a24a6aa13a27838208c07a729c9bf0`

**Why previous reviews missed it:** recent review work correctly added exact live Snackbar ownership and a startup-independent abandoned-debt reconciliation algorithm, then stopped after proving normal owner abandonment and cold-start recovery. That treated “the durable token is recoverable later” as sufficient and did not fault the first convergence read/write *after* the process-local owner had already been released during ordinary process survival.

**Concrete blind spot / incorrect stopping assumption:** the review conflated existence of a recovery helper with existence of an active recovery carrier. `reconcileAbandonedUndoDebts()` is semantically capable of repair, but lifecycle abandonment uses `runCatching` and does not schedule that helper when its first attempt fails.

**Relevant v4 items:** carrier-creation gap, helper-internal throwable window, persistence barrier and first-write fault injection, recovery semantic identity, recovery-write failure, multi-ledger/process-death durability, outer catch/final result, cross-attempt matrix, and CLEAN gate. These items were relevant but were applied primarily at worker/native and startup boundaries, not at UI-owner-to-recovery-owner lifecycle handoffs.

**General lesson:** whenever process-local privileged authority is deliberately dropped because a UI/lifecycle owner disappears, that drop is a semantic publication boundary. A durable token being *recognizable* by a future reconciler is insufficient; if the process remains alive, failure of the first convergence attempt must leave another guaranteed executor or retry trigger.

**Proposed checklist improvement:** explicitly treat lifecycle abandonment, owner-map removal, lease release, and in-memory snapshot disposal as carrier handoff points. Fault both the first durable-state read and first durable write after release and prove same-process progress without relying on process restart.

**Suggested wording:** “For every lifecycle/owner-abandonment path that releases process-local authority before durable convergence, identify the successor executor before accepting the release. Inject failure in the first post-release read and write. PASS requires that the same live process retains or schedules an exact retry carrier; cold-start discoverability alone is insufficient unless process death is the only reachable reason the prior owner can disappear.”

**False-positive guard:** do not require a persistent retry worker when the same transaction atomically removes the old owner and reaches a durable terminal state, when a continuously running process-global reconciler is already provably subscribed to the exact debt, or when the owner can disappear only because the entire process has died and startup is therefore guaranteed before any further app action. Require a new defect only when ordinary process survival can lose the executor while durable nonterminal state remains.

**Disposition:** PROPOSED
