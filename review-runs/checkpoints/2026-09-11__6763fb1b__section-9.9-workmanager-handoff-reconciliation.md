## Exact current producer -> scheduler trace

### 1. Ordinary queue publication persists runnable state first

`DownloadViewModel.queueDownloads()` sets each item to `Queued` or `Scheduled`, then `persistQueuedItems()` durably writes the row before scheduler submission. Existing rows use the exact lease/lock plus `updateForQueueIfSnapshot(...)`; new rows are inserted/updated directly.

After persistence, the normal branch calls:

`DownloadRepository.startDownloadWorker(queued, context)`.

The scheduler-window branch likewise persists the rows before `AlarmScheduler.schedule()`.

### 2. Direct WorkManager submission does not observe acceptance

`DownloadRepository.startDownloadWorker()` builds `OneTimeWorkRequest<DownloadWorker>` requests and directly calls `WorkManager.enqueueUniqueWork(...)` for:

- immediate work, using a unique name containing the request UUID;
- future scheduled groups when alarm-based scheduling is disabled, using `scheduledDownload-<startTime>`.

The returned `Operation` is neither retained nor awaited. No `Operation.result` listener/future is consumed. The helper then returns `Result.success(message)`.

Therefore a caller-visible successful `startDownloadWorker()` result proves only that the enqueue API call returned synchronously; it does not prove asynchronous WorkManager acceptance.

### 3. The same gap spans retry/resume/requeue producers

Exact-current `DownloadViewModel` paths that durably make a row runnable before calling the same helper include:

- `queueDownloads(...)`;
- `retryFailedDownload(...)` after successful Error -> Queued snapshot transition;
- `resumePausedDownloadAndWait(...)` after `resumePausedIfExecutionOwned(...)`;
- `reQueueDownloadItemsAndWait(...)` after requeue CAS;
- schedule reset/reschedule helpers after their durable row transitions.

Several of these callers ignore the helper result entirely; the main queue path folds a result that is already nominally successful despite unobserved asynchronous enqueue completion.

### 4. Startup recovery does not discover an ordinary orphan Queued/Scheduled row

`App.onCreate()` launches `DownloadExecutionRecovery.reconcile(...)` and `WorkManagerHandoffRecovery.reconcile(...)`.

`DownloadExecutionRecovery.reconcile()` discovers:

- Active/PostProcessing rows;
- committed History-replacement rows;
- exact recovery-journal rows;
- native-process rows/markers;
- primary-success and producer-finality debt.

It does not enumerate arbitrary `Queued` or `Scheduled` rows merely because they are runnable.

`DownloadExecutionRecovery.hasRecoveryResponsibility()` likewise does not treat an ordinary Queued/Scheduled row as recovery debt.

Thus the concrete process-death/failure state is reachable:

`Room Queued/Scheduled committed -> direct enqueue requested -> WorkManager Operation fails or process dies before acceptance is established -> no accepted worker -> restart`

and startup has no exact ordinary Download handoff carrier from which to reconstruct the missing scheduler responsibility.

### 5. Worker-side queue recovery cannot repair a worker that was never accepted

Once a `DownloadWorker` actually starts, `observeQueuedDownloadsAfterRecovery()` reconciles execution debt and observes due `Queued`/`Scheduled` rows. `claimDownloadForWorkerAndRead()` then uses a transactional exact snapshot claim and fresh execution ID.

That is useful idempotence/ownership protection after a worker exists, but it is not recovery from a failed scheduler handoff: if no WorkRequest was accepted, this code never runs.

## Exact boundary already implemented correctly elsewhere

- durable Room `WorkManagerHandoffCarrier` before handoff;
- exact persisted WorkRequest UUID/generation;
- actual `Operation.result` observation;
- durable retry advancement to a new request UUID;

Its current kinds include hard-sub scan, scheduler START/END boundaries, and Observe retry Download. It does **not** own ordinary Download queue submissions from `DownloadRepository.startDownloadWorker()`.

## Scheduler-boundary reconciliation

The alarm-mediated scheduler START/END handoff is `CLEAN/PRESERVED` for WorkManager acceptance at this exact boundary:

- `AlarmScheduler` creates a durable scheduler-boundary carrier before publishing the alarm;
- alarm publication failure falls back to `WorkManagerHandoffRecovery.ensureConvergence(...)`;
- `ScheduleAlarmReceiver` uses `goAsync()` and awaits `enqueueAndAwait(...).await()`;
- `WorkManagerHandoffRecovery` observes `Operation.result` and retains/retries exact durable responsibility.

This does not close the separate ordinary Download handoff root, because direct immediate submissions and direct future scheduled submissions inside `startDownloadWorker()` bypass this carrier.

The direct future-scheduled `scheduledDownload-<startTime>` path is therefore another subcase of `BUG-DOWNLOAD-HANDOFF-01`, not a new `BUG-SCHEDULE-01` root. `BUG-SCHEDULE-01` continues to own scheduler recurrence/disable/alarm/generation semantics outside this ordinary Download-row -> WorkManager acceptance gap.

## Priority and semantic-carrier consequence

For direct requests, priority item IDs and `continueAfterPriorityIds` are carried only inside the WorkRequest input. If that WorkRequest is never accepted, the durable Download rows survive but the exact priority-only scheduling intent is not represented by an app-owned handoff carrier.

A future generic resubmission could therefore recover runnable rows without necessarily preserving the original trigger semantics. Any repair must preserve the request semantics that matter, not merely cause some worker to exist.

This is additional evidence for the same `BUG-DOWNLOAD-HANDOFF-01` root; it does not increment the count.

## Stable correction boundary for `BUG-DOWNLOAD-HANDOFF-01`

A future repair of this root must ensure that every durable ordinary Download transition relying on WorkManager has, before the producer returns success, one of:

1. confirmed WorkManager acceptance; or
2. an exact durable app-owned handoff/retry responsibility discoverable after process death.

The correction should use the smallest compatible mechanism, preferably reusing/extending the existing `WorkManagerHandoffRecovery` architecture rather than creating an unrelated journal.

Required properties:

- do not hold a Room transaction while waiting for WorkManager completion;
- persist exact request/generation identity before or atomically with exposing recoverable handoff responsibility;
- observe actual `Operation.result` or equivalent acceptance evidence;
- on failure, retain deterministic retry/compensation responsibility;
- startup must enumerate every surviving ordinary Download handoff carrier;
- repeated recovery must be idempotent and exact-row claim semantics must remain preserved;
- an already-valid active worker/generation must not be cancelled/replaced by stale recovery;
- pause/cancel/remove/supersession must revoke or supersede a pending handoff without allowing the stale request to reclaim the row;
- priority IDs and `continueAfterPriorityIds` semantics must survive retry/process death where they are semantically required;
- scheduled direct submissions must preserve their timing/group semantics and not let `REPLACE` discard a valid accepted generation without successor responsibility;
- existing scheduler START/END handoff behavior and `DownloadExecutionRecovery` execution/finality closures must remain intact.
