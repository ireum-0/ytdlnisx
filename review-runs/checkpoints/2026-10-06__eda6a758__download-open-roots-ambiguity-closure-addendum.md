# 1. BUG-FORMAT-BG-01 + BUG-FORMAT-BG-02 — handoff authority derives from actual successful transition

## Exact-current ambiguity

Current producer source at `eda6a758...` does:

```
allProcessing = current Processing ids
ids = selectedItems ?: allProcessing
moveProcessingToSavedCategory()
WorkRequest Data:
  ids
  other_ids_in_bundle = allProcessing - ids
```

The existing correction boundary already requires replacing the broad Processing sweep with an exact,
guarded transition over the captured bundle. However, it did not explicitly state whether a captured row
that loses the transition race/refuses the exact guarded mutation may still remain in the subsequent
format-handoff payload.

That is not safe.

A row that did not successfully enter the lifecycle state owned by this background-format operation
cannot remain part of its worker/completion authority merely because it was present in the earlier UI
snapshot.

## Normative set algebra

Define one immutable capture event:

- `C` = exact Processing bundle captured for this operation.
- `S_requested` = caller selection when nonempty, otherwise `C`.
- `S` = `S_requested ∩ C`. A stale/unrelated selected ID outside `C` is not authorized by this capture.
- `T` = exact subset of `C` whose guarded lifecycle transition to the background-format-owned state
  actually succeeds.
- `W` = `S ∩ T`: exact worker refresh target.
- `O` = `T - W`: exact captured-and-transitioned nonselected bundle members carried for completion UI.

Required invariants:

1. `T ⊆ C`.
2. `W ⊆ T`.
3. `O ⊆ T`.
4. `W ∩ O = ∅`.
5. `W ∪ O = T`.
6. No ID in `C - T` may be carried as worker target or completion-bundle mutation authority.
7. No ID outside `C` may enter `T`, `W`, or `O`.

The implementation may represent these sets through affected-row results, a transaction return value,
typed transition results, or an equivalent exact carrier. Architecture is not prescribed.

## Coupling rule between BG-01 and BG-02

BG-01 remains the owner of exact lifecycle target/refusal semantics.

BG-02's durable handoff payload must be built from **the exact successful transition result `T`**, not
from the pre-transition request alone.

If the BG-01 transition and BG-02 durable handoff staging are implemented in one transaction, that
transaction must durably establish the exact `T/W/O` relationship.

If they are implemented through an equivalent multi-step protocol, process death or failure between steps
must not leave:
- a row in the background-format-owned durable state but absent from recoverable handoff responsibility; or
- a refused/nontransitioned row present in worker/completion authority.

## Closure rejection

Reject BG-01/BG-02 closure if any of the following remains:

- worker `ids` are derived from raw `selectedItems` after some selected row failed exact transition;
- `other_ids_in_bundle` is derived from raw `C-S` after some captured row failed exact transition;
- a stale selected ID outside the captured Processing set is admitted;
- an affected-row count is checked but exact transitioned identities are not knowable/recoverable;
- handoff recovery reconstructs the original requested set instead of the exact successfully transitioned set;
- a refused row can later be pulled into Processing by a completion notification generated by this batch.

## Required deterministic race

Capture A/B, select A, then before transition:
- C enters Processing;
- B advances to a protected/newer state;
- A remains eligible.

Expected exact sets:
- `C={A,B}`
- `S={A}`
- `T={A}`
- `W={A}`
- `O={}`

C is untouched. B is not moved and is absent from completion authority.

Also test stale selection containing D where D is not in `C`: D must not enter `S/T/W/O`.

# 2. BUG-FORMAT-BG-03 — ALREADY_SATISFIED requires semantic freshness, not nonempty cached formats

## Exact-current ambiguity

Current worker source has:

```
if (d.allFormats.isNotEmpty()) {
    count++
    return@forEach
}
```

The prior hardening supplement requires `ALREADY_SATISFIED with fresh proof`, but did not explicitly
forbid treating the existing `allFormats.isNotEmpty()` check as that proof.

Nonempty cached formats establish only that some format data exists. They do not establish that the
current background refresh intent is already satisfied under the current source/configuration authority.

## Normative ALREADY_SATISFIED contract

An item may be classified `ALREADY_SATISFIED` only when fresh exact state proves all material obligations
of the current requested refresh are already true.

At minimum the proof must establish:

1. exact current Download row still represents the same source identity intended by this refresh;
2. current format data is nonempty **and semantically current for the present refresh authority**, not
   merely leftover from an earlier fetch;
3. current selected `format` is valid/derived under the current format-selection inputs applicable to
   that Download type;
4. any Result-side format projection that is part of the same semantic refresh is already consistent, or
   the implementation explicitly proves that no Result-side publication is required for this item;
5. no newer configuration/source/retry/execution authority requires refusal or recomputation;
6. no outstanding exact refresh generation/residual debt says the item still requires work.

A durable generation/fingerprint is one acceptable proof mechanism. A fresh recomputation/comparison
against current authoritative inputs is another. The review contract does not require a particular
storage design.

## Explicit non-proof

The following facts alone are insufficient to classify `ALREADY_SATISFIED`:

- `allFormats.isNotEmpty()`;
- an existing selected `format`;
- a Result row existing for the URL;
- a prior success notification;
- the row being Saved/Processing;
- an old request having once completed.

## Closure rejection

Reject closure if:
- the existing nonempty-`allFormats` fast path is merely renamed as ALREADY_SATISFIED;
- progress increments for a skipped item without fresh semantic proof;
- an item can be called already satisfied after source/configuration changed;
- Download and Result projections can disagree while the item is classified satisfied;
- a retry/residual owner still exists but the worker silently skips the item as satisfied.

# 3. BUG-FORMAT-BG-04 — stale-publication fingerprint includes row-local and external format authority

## Exact-current evidence

The current worker obtains formats and selection through:

```
resultRepo.getFormats(d.url)
vm.getFormat(d.allFormats, d.type)
```

The format decision is not a pure function of fields in the Download row.

Exact current production dependencies include:

### Extractor/input source selection
`ResultRepository.getFormats()` reads:
- `formats_source`;

and may choose NewPipe vs yt-dlp/fallback behavior.

### Audio/video format-selection preferences
`FormatUtil` reads or derives from SharedPreferences including at least:
- `format_id`;
- `format_id_audio`;
- `video_quality`;
- `audio_language`;
- `audio_codec`;
- `video_codec`;
- `audio_format`;
- `video_format`;
- `preferred_format_size`;
- `use_format_sorting`;
- `format_importance_audio`;
- `format_importance_video`;
- `prefer_container_over_codec_audio`;
- `prefer_drc_audio`.

### Command-type selection authority
`DownloadViewModel.getFormat(..., DownloadType.command, url)` uses:
- preferred command-template rows from `CommandTemplateDao`;
- URL-regex matching;
- fallback first template;
- `lastCommandTemplateUsed` when a default synthetic template is needed.

Therefore a Download-row-only fingerprint is not sufficient for all types.

## Normative fetch/publication authority image

For each requested item, define one exact **refresh authority image** sufficient to prove whether the
external fetch result and selected format are still applicable at publication.

The image must cover two classes independently.

### A. Row-local authority

At minimum classify:
- Download id;
- canonical/source URL identity;
- type;
- operationId / retryAttempt / retryStrategy where relevant;
- executionId / live execution state;
- format/allFormats state as required for current publication semantics;
- issue/finality/barrier state;
- any row-local preference object that actually participates in selection for the type.

Fields such as path/container/incognito that do not determine the fetched/selected format still must be
preserved by narrow publication and never overwritten from the pre-fetch object.

### B. External selection/extractor authority

The implementation/reviewer must inventory every external mutable input actually read by the final
format-fetch/selection path for each supported type, including:
- extractor source preference;
- audio/video format ordering and codec/language/container/quality preferences;
- sorting-policy preferences;
- applicable command-template identity/content/preference ordering;
- any later-added mutable global setting consumed by `getFormats`, `getFormat`, or their production
  helpers.

The inventory must be recomputed from exact final source. The explicit list above is a minimum current
inventory, not permission to ignore newly introduced inputs.

## Required behavior when authority image changes during fetch

If a material fetch/selection input changes between the authoritative pre-fetch image and final
publication, production must do one of:

1. recompute the affected selection using the exact fresh authoritative inputs when the fetched raw
   format data remains valid; or
2. refuse the publication and feed a truthful non-success/retry classification into BG-03; or
3. refetch when the changed input invalidates the raw fetched format set itself.

It may not silently publish a selection computed under stale global preferences/template/extractor
authority.

## Important distinction

Not every mutable field must invalidate raw fetched formats.

The final implementation/review must explicitly distinguish:
- inputs that invalidate **raw fetched format data**;
- inputs that leave raw data usable but invalidate **selected format choice**;
- unrelated fields that publication does not own and must merely preserve.

This avoids both stale publication and unnecessary broad refusal.

## Closure rejection

Reject closure if:
- the publication fingerprint/check guards only Download row fields while mutable SharedPreferences or
  command-template/extractor inputs still influence the result;
- a global preference change during fetch can be overwritten/ignored without recompute or refusal;
- command-template changes can leave a stale command format published;
- `formats_source` changes while an old-source fetch result is published as current without proof;
- the implementation snapshots preferences in a long-lived helper and then treats that cached snapshot as
  current authority without generation/revalidation;
- newly introduced mutable inputs to the fetch/selection call graph are omitted from the final-SHA
  inventory.

## Mandatory additional races

In addition to the existing BG-04 matrix:
- audio/video format preference changes during external fetch;
- `formats_source` changes during fetch;
- command template/preferred-template changes during command refresh;
- one unrelated field such as incognito/path changes: fetched data may remain usable, but narrow
  publication must preserve the newer unrelated value.

# 4. BUG-SCHEDULER-RESTORE-01 — validate and converge the final effective merged scheduler image

## Remaining ambiguity

Portable/merge restore may restore only a subset of scheduler keys.

Validating each incoming key independently is insufficient because executable scheduler authority is the
combined durable image:

```
(use_scheduler, schedule_start, schedule_end)
```

The correction contract must therefore define validation/convergence over the **effective post-overlay
image**, not merely the keys present in the backup payload.

## Normative effective-image rule

For every restore mode that can alter scheduler settings:

1. read the exact pre-restore authoritative scheduler image;
2. parse the incoming restore scheduler keys;
3. overlay only present incoming keys onto the pre-restore image according to the restore mode's ordinary
   semantics;
4. produce one candidate effective image:
   `E = (enabled, start, end)`;
5. validate `E` as one scheduler-domain object before it becomes executable authority;
6. create/retain the exact durable scheduler transition/recovery owner for `E`;
7. publish the durable preference image for `E`;
8. converge external AlarmManager/WorkManager ownership to exactly `E`;
9. resolve the durable transition only after exact external convergence.

For a merge restore, a missing scheduler key means "retain the currently authoritative value" unless the
existing restore product contract explicitly defines otherwise. It must not become an implicit blank,
default, or partially validated temporary authority.

For reset/authoritative restore, use that mode's defined reset defaults/source image, then validate the
final complete effective image by the same scheduler-domain contract.

## Atomic semantic generation

The three scheduler values are one semantic configuration generation for external-effect purposes.

Even if SharedPreferences stores them as separate keys, no external scheduler effect may be published
from a transient partially-overlaid image such as:
- new `schedule_start` + old/unvalidated `schedule_end` when that combination was never the final
  effective restore image;
- restored `use_scheduler=true` before the final validated start/end image exists;
- restored start/end while stale enabled state drives an intermediate alarm generation.

Implementation may use staging, a transaction-like coordinator, or another durable generation carrier,
but the external effect must converge from one validated complete `E`.

## Validation requirements

The effective image must establish:
- `enabled` is Boolean;
- start is exact valid `HH:mm`;
- end is exact valid `HH:mm`;
- all three values used for publication belong to the same effective restore generation.

Invalid incoming scheduler data must fail before executable scheduler authority changes. A partial merge
must not corrupt previously valid retained values.

## Closure rejection

Reject closure if:
- validation is performed only on scheduler keys present in the payload;
- missing merge keys are silently replaced with defaults/blanks without the ordinary merge contract
  requiring that behavior;
- external publication can observe a transient mixed old/new scheduler image;
- separate preference callbacks independently schedule intermediate generations during restore;
- enabled is restored before final start/end validation and can publish using stale times;
- start/end are restored while old enabled state can publish an unintended intermediate owner;
- merge and reset converge different semantic images for the same final persisted settings;
- process death can leave a partially overlaid image that startup interprets as a completed scheduler
  generation without an exact durable transition owner.

## Mandatory partial-restore cases

Add explicit production-path coverage for:
- payload contains only `schedule_start`;
- only `schedule_end`;
- only `use_scheduler`;
- start+end but not enabled;
- enabled+start but not end;
- enabled+end but not start;
- all three keys;
- invalid one-key overlay against otherwise valid retained settings;
- valid one-key overlay preserving the other two exact retained values;
- process death between overlay staging and final external convergence.

Each case must prove the final effective image and exact external owner agree.

# Final review disposition

With this addendum, the previously identified four design ambiguities are closed at the review-contract
level:

1. BG-01/BG-02 handoff payload authority is bounded by the exact successfully transitioned set.
2. BG-03 ALREADY_SATISFIED requires fresh semantic proof; nonempty cached formats alone are insufficient.
3. BG-04 freshness covers both row-local and external mutable fetch/selection authority.
4. Scheduler Restore validates and converges one complete effective post-overlay scheduler image.

This addendum does not select an implementation architecture where multiple safe designs remain
equivalent. It removes only choices that could preserve the known correctness failures.

No implementation source, prompt, private handoff, Master Plan, ledger, canonical finding count, severity,
or finding status is changed by this checkpoint.
