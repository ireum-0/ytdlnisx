## Final finding/disposition update

### `BUG-LOCALADD-HANDOFF-01 / L2` — NEW P2 subfinding, OPEN

Current producer ordering is:

`expanded URI set -> session UUID -> LocalAddStorage.saveEntries() -> SharedPreferences.Editor.apply() returns -> WorkRequest(sessionId) -> WorkManager.enqueue()`.

`saveEntries()` therefore does not establish a durable input carrier before scheduler publication. `apply()` only makes the session visible in-process and asynchronously starts the disk write. A process crash/termination before the preference write becomes durable can leave a WorkManager request whose only input is `sessionId` while the referenced entry payload is absent after restart. `LocalAddWorker` then loads an empty entry list and returns `Result.success()`, clearing progress rather than reconstructing the user request.

The same storage primitive is also used when the worker publishes unresolved `pending` candidates/open-session state before returning success, so pending user resolution state likewise lacks an acknowledged durable barrier.

This is a newly confirmed failure mode inside the already-counted canonical root `BUG-LOCALADD-HANDOFF-01`; it does not create a separate canonical P2 root.

- Severity: P2.
- Violated invariants: v6 #1 durable carrier crossing, #7 asynchronous request is not completion, #10 multi-ledger/process-death durability, and recovery discoverability from surviving carriers.
- Affected production files: `app/src/main/java/com/ireum/ytdl/ui/downloads/HistoryFragment.kt`, `app/src/main/java/com/ireum/ytdl/util/LocalAddStorage.kt`, `app/src/main/java/com/ireum/ytdl/work/LocalAddWorker.kt`.
- Concrete reproduction: persist LocalAdd entries with `apply()`; let `apply()` return; publish/accept worker keyed only by sessionId; terminate process before SharedPreferences disk commit; restart worker; session payload is absent; worker observes empty list and succeeds.
- Disposition: `NEW subfinding / P2 / OPEN / canonical root count unchanged`.

## Why previous reviews missed it

Earlier reviews identified the DB/input-to-WorkManager handoff and the lack of orphan-session enumeration, but treated `LocalAddStorage.saveEntries()` as if returning meant the input payload had crossed a durable boundary. The abstraction name (`saveEntries`) hid the fact that its only persistence primitive is asynchronous `SharedPreferences.apply()`. The previous matrix started at “session input persisted” rather than opening the storage helper and proving disk durability before scheduler acceptance.

## Checklist gap

The v6 async-request rule was applied to WorkManager enqueue/cancel operations but not symmetrically to application-local persistence APIs that are themselves asynchronous and whose return value does not mean persistent durability.

## Proposed checklist change

For every scheduler/worker handoff whose request contains only a locator/key into another store, require an explicit `payload construction -> persistence API -> durable completion/acknowledgement -> scheduler request -> scheduler acceptance` row. Open the persistence helper and classify `apply`, async datastore/file writes, callbacks/futures, or ignored status results as non-barriers until completion is proven. On restart with only the scheduler carrier surviving, prove the exact keyed payload is present or a durable reconciler can reconstruct it. Apply the same rule to worker-success publication of follow-up/pending user state.
