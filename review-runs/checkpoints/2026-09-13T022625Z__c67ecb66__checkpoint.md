## Open candidate confirmed

`BUG-CLEANUP-01` residual: `CleanUpLeftoverDownloads.doWork()` catches cleanup failure and returns `Result.retry()` only while `runAttemptCount < MAX_ATTEMPTS - 1`; on the final allowed attempt it returns `Result.failure()` before `scheduleSuccessor()` is reached. Therefore a persistent cleanup failure terminates the current unique chain with no next occurrence. WorkManager chain semantics propagate failure to dependents, and there is no in-process periodic reconciler; `CleanupScheduleCoordinator.reconcile()` is invoked at application startup only. If the process stays alive after the final failure, the selected daily/weekly/monthly preference remains enabled but no future cleanup occurrence is scheduled.

Concrete reproduction model:
1. Configure DAILY (or WEEKLY/MONTHLY).
2. Force cleanup body to throw on all three attempts.
3. Attempt 0 -> retry; attempt 1 -> retry; attempt 2 -> `Result.failure()`.
4. No call to `scheduleSuccessor()` occurs on attempt 2.
5. Unique chain has no unfinished next occurrence; persisted cadence remains enabled.
6. Keep app process alive: no startup `reconcile()` occurs, so the recurring schedule stops indefinitely.

This is the same existing P2 root, not a new finding. Current tests cover eventual-success retry but do not cover retry exhaustion followed by continued cadence.

## Exact upstream semantic basis

- Android Developers WorkManager docs: chains proceed to dependents on `Result.success()`; `Result.failure()` causes dependents to fail; retry retries the same request.
- Android Developers `ExistingWorkPolicy.APPEND_OR_REPLACE`: appends to unfinished leaves, but failed/cancelled prerequisites are dropped only when a new append operation is actually issued.
- Android Developers WorkManager cancellation contract: cancellation is best-effort and executing work may continue; cancellation is not itself a synchronous semantic barrier.
- Android Developers `CoroutineWorker`: stopped work has its future cancelled; WorkManager ignores its result.
