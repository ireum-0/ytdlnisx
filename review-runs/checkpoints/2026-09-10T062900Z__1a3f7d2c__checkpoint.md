## Review scope completed

### Ordinary Download queue handoff

Full path re-traced on the pinned production SHA:

`DownloadViewModel.queueDownloads/persistQueuedItems -> durable Queued/Scheduled row -> DownloadRepository.startDownloadWorker -> WorkManager.enqueueUniqueWork -> DownloadWorker admission -> Download execution recovery/startup`

Confirmed:

- Runnable Download rows are persisted before `startDownloadWorker()` publishes their WorkManager trigger.
- `startDownloadWorker()` calls `enqueueUniqueWork(...)` for immediate and non-alarm scheduled triggers but does not observe/await the returned WorkManager `Operation`.
- `App.onCreate()` runs DownloadExecutionRecovery, Terminal recovery, WorkManagerHandoffRecovery, low-quality, automatic-keyword and History-date reconciliation, but does not enumerate arbitrary ordinary `Queued`/due `Scheduled` rows and reconstruct a missing DownloadWorker request.
- WorkManagerHandoffRecovery has no ordinary Download-queue carrier kind.

Disposition: NEW `BUG-DOWNLOAD-HANDOFF-01`, P2, OPEN.

Concrete failure: durable Queued row Q -> enqueue request issued -> asynchronous enqueue failure/process death before accepted request is durable -> Q survives without a WorkManager request -> restart has no Q->request reconciliation owner -> runnable Q can remain ownerless indefinitely.

### HardSub generation / publication

Full path re-traced:

`ProcessingSettingsFragment Scan Now -> HardSubScanWorker.enqueueWithGeneration -> WorkManagerHandoffRecovery.prepareHardSub -> REPLACE unique work -> HardSubScanWorker -> History candidate state + replacement Download publication -> Download queue`

Confirmed:

- Repeated Scan Now creates a new exact handoff generation; UI only fences late result presentation.
- Accepted non-Observe WorkManager handoff carriers are deleted immediately after enqueue acceptance.
- `HardSubScanWorker` receives handoff/request input from the request builder but does not read/validate that generation before `resetHardSubDoneForRescan`, History hard-sub state mutation, marker check, or replacement Download insertion.
- Pending marker prevention is a separate `countPendingByPlaylistMarker(marker)` read followed by `downloadDao.insert(downloadItem)`.
- `DownloadItem` has no unique index on `playlistURL`/the History-redownload marker.

Disposition: NEW `BUG-HARDSUB-GENERATION-01`, P2, OPEN.

Concrete failure: old scan generation remains executing while newer REPLACE generation is prepared/accepted -> both reach the same History marker before cancellation is observed -> both read zero pending marker -> both insert distinct queued replacement Downloads -> superseded generation publishes durable work after successor generation exists.
