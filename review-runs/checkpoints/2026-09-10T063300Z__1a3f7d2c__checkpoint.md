## NEW P2 — BUG-DOWNLOAD-HANDOFF-01

Violated invariant: a durable runnable ordinary Download row must retain exactly one discoverable execution-trigger obligation until exact WorkManager acceptance or durable revocation/terminalization. Asynchronous enqueue invocation is not acceptance.

Production path:

`DownloadViewModel queue/requeue/resume/retry producer -> persist Queued/Scheduled row -> DownloadRepository.startDownloadWorker -> WorkManager.enqueueUniqueWork -> DownloadWorker -> startup/recovery`

Evidence:

- Queue path persists runnable rows before calling `startDownloadWorker`.
- `startDownloadWorker` issues WorkManager `enqueueUniqueWork` but does not await/observe the returned `Operation`.
- Startup reconciliation does not enumerate arbitrary ordinary `Queued` / due `Scheduled` rows and reconstruct their missing exact DownloadWorker carrier.
- WorkManagerHandoffRecovery owns explicit hard-sub/schedule-boundary/Observe-retry carrier kinds, not the ordinary queue.

Concrete reproduction:

`Q durable Queued -> enqueue issued -> async enqueue failure or process death before accepted request is durable -> Q survives -> restart -> no Q->worker reconciliation owner -> Q remains runnable but ownerless`.

Affected files/path:

- `app/src/main/java/com/ireum/ytdl/database/viewmodel/DownloadViewModel.kt`
- `app/src/main/java/com/ireum/ytdl/database/repository/DownloadRepository.kt`
- `app/src/main/java/com/ireum/ytdl/App.kt`
- ordinary `DownloadWorker` admission/recovery boundary

Disposition: NEW / P2 / OPEN.

Checklist gap: one-shot WorkManager producer enumeration did not include the ordinary Download queue because dedicated recovery subsystems were reviewed more deeply than the generic queue trigger.

Proposed checklist change: mandatory matrix for every WorkManager producer: `durable semantic intent -> exact request identity -> request -> acceptance -> worker admission -> completion/restart reconciliation`; require a durable obligation to survive until acceptance.
