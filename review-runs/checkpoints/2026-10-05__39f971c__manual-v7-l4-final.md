## BUG-HISTORY-05 L4 deep trace

### Producer / relation meaning

PlaylistItemCrossRef has composite primary key:
(playlistId, historyItemId).

Each row therefore represents one durable set-membership fact:
History H belongs to Playlist P.

Playlist queries and History filters consume this relation directly. It is not disposable cache or a derived sidecar.

### Dedupe authority

HistoryRepository.getDuplicateGroups() groups downloaded History rows by HistoryDuplicateIdentity and orders each group by time then id.

HistoryViewModel.deleteDuplicates() converts those groups to candidate IDs and delegates to HistoryKeywordAssignmentRepository.deleteDuplicateHistoryGroups().

The repository correctly treats those candidates only as hints:
- rereads current History rows;
- recomputes exact duplicate identity;
- regroupes current rows;
- selects the earliest retained row;
- rechecks retained/duplicate identity before final History deletion.

### Destructive gap

For every current duplicate, production currently:
1. copies keyword assignments to retained;
2. materializes retained keywords;
3. calls deletePlaylistItemsByHistoryIds(duplicate.id);
4. deletes duplicate keyword assignments;
5. rechecks History duplicate identity;
6. deletes duplicate History.

There is no playlist membership transfer before step 3.

Therefore:
- retained-only memberships survive;
- shared retained+duplicate memberships survive only because the retained row already owns them;
- duplicate-only memberships are irreversibly lost.

### Existing narrow correction

PlaylistDao already provides:
- getPlaylistItemsForHistory(historyItemId);
- insertPlaylistItems(items);
- deletePlaylistItemsByHistoryIds(ids).

Because PlaylistItemCrossRef uses (playlistId, historyItemId) as its primary key and insertPlaylistItems uses OnConflictStrategy.REPLACE, retargeting duplicate memberships to retained naturally computes a set union:
- duplicate-only membership becomes retained membership;
- shared membership remains one row;
- retained-only membership is unchanged.

No schema/migration or new DAO API is needed on current source evidence.

### Required in-transaction ordering

For each duplicate that still passes current identity checks:

1. read current duplicate playlist memberships inside the existing transaction;
2. construct equivalent refs with historyItemId=retained.id;
3. insert them before any duplicate ref deletion;
4. copy/materialize keyword assignments as today;
5. delete duplicate playlist refs;
6. delete duplicate assignments;
7. keep the current final retained/duplicate identity recheck;
8. delete duplicate History.

Equivalent ordering between relationship transfer and assignment copy is acceptable only while all operations remain inside the same Room transaction and no destructive duplicate relation deletion can occur before its retained replacement is durable within that transaction.

Across multiple duplicates, repeated transfer must converge to the exact union of every retained/duplicate playlist membership.

### Rollback contract

Any transfer/materialization/final-delete failure must roll back the whole graph.

Required failure cells remain:
- injected PlaylistItemCrossRef insertion failure: retained History, duplicate History, both assignment sets and both original membership sets unchanged;
- injected final History delete failure after provisional transfer: no retained union or partial assignment merge survives;
- no partial transfer may commit for an earlier duplicate when a later duplicate in the same transaction fails.

### Acceptance matrix

Required relationship fixtures remain:
- retained A, duplicate B => retained A+B;
- retained A+C, duplicate B+C => retained A+B+C exactly once;
- retained none, duplicate B => retained B;
- retained A, duplicate none => retained A;
- retained plus multiple duplicates with disjoint/overlapping memberships => exact whole-group union;
- rerun after convergence => idempotent/no additional effect.

Authority/staleness:
- changed duplicate URL identity => no transfer, no deletion;
- changed duplicate type identity => no transfer, no deletion;
- current final HISTORY-04 identity recheck remains intact.

The prior symmetric shared-playlist fixture is insufficient by itself because it cannot reveal duplicate-only relation loss.
