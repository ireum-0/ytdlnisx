### Existing P2 root expanded — BUG-CANCEL-02 Terminal subcase

This is a **newly confirmed subcase of an existing finding root**, not a new finding ID.

Canonical BUG-CANCEL-02 owns the invariant:
once durable cancellation wins, stale worker success-side effects must be vetoed at the same commit/effect boundary.

The same root exists in the pinned Terminal production path.

#### Concrete Terminal production sequence

1. `TerminalDownloadWorker` completes native execution and persists `TerminalExecutionRecovery.Phase.NATIVE_FINISHED`.
2. Provider publication and semantic Terminal commit have not necessarily completed yet.
3. User cancellation enters `TerminalCancellationCoordinator.cancel()`.
4. `WorkManagerHandoffRecovery.cancelTerminalDispatch()` first durably supersedes the exact TERMINAL_DISPATCH carrier.
5. It then attempts exact WorkManager cancellation and returns a separate `workManagerCancellationAcknowledged` flag.
6. `TerminalCancellationResult.rowDeletionAuthorized` does **not** require that acknowledgement. It is only `dispatchSuperseded && executionConverged`.
7. `TerminalExecutionRegistry.cancel()` calls `TerminalExecutionRecovery.convergeTerminal(... STOPPED)`.
8. For `NATIVE_FINISHED`, convergence can terminalize the execution witness without proving that post-native provider publication has stopped.
9. On convergence the process-local Terminal execution token is removed.
10. `TerminalViewModel` or `CancelTerminalNotificationReceiver` can delete the Terminal row even when WorkManager cancellation was not acknowledged.
11. The already-running worker has no durable-cancellation recheck between `markNativeFinished()` and `FileUtil.moveFile()`.
12. If the WorkManager cancellation failed, or the worker remains in its asynchronous unwind window, provider/file publication can continue after durable cancellation has won.
13. The later `TerminalExecutionRecovery.markCommitting()` check can fail because the witness is already STOPPED, but it occurs **after** publication side effects can exist.

#### Authority/destructive effect

A user-cancelled Terminal can still publish destination output after the cancellation owner has durably won.

The worker may later fail semantic commit, but that does not safely undo an already-created provider/file output.

This is the same root as BUG-CANCEL-02:
durable cancellation is not revalidated at the irreversible success-side effect boundary.

#### Cache-maintenance amplification

The same cancellation sequence can remove both live-cache protection signals before the worker is necessarily quiescent:

- row deletion lets `FolderSettingsFragment.hasActiveDownloads()` report no active Terminal;
- `TerminalExecutionRegistry.cancel()` removes the active token;
- `TerminalCacheOwnership.isLiveOwnedRoot()` depends on that active token and then returns false.

`AppCacheManager.delete(TERMINAL_CACHE)` can therefore see a still-owned staging root as unowned.

`CacheMaintenanceAuthority` only serializes maintenance against the short execution-admission window. It does not cover the entire Terminal publication lifetime or cancellation convergence.

A user clear-cache action after Terminal cancellation can consequently delete exact staging/control files while the old worker is still unwinding publication.

This is recorded as a destructive consequence of the BUG-CANCEL-02 Terminal subcase, not double-counted as a separate BUG-CACHE finding.

#### Supporting production evidence

The repository's own `DownloadWorkerCleanupProductionWiringTest` documents that WorkManager cancellation can mark WorkManager state while an already-running worker is still unwinding its finally/cleanup path.

The Terminal cancellation contract is less strict for row retirement because row deletion authorization ignores `workManagerCancellationAcknowledged`.

#### Required correction

Keep remediation under the existing cancellation root:

- durable STOPPED cancellation must veto Terminal provider/file publication before irreversible publication side effects;
- do not retire publication/live-cache ownership merely because native execution is quiescent;
- do not treat Terminal row deletion as proof that publication ownership has ended;
- retain a live/cache owner through the full staging/publication lifetime until publication is quiescent or exact recovery ownership has taken over;
- if provider side effects may already have started, preserve exact publication journal/recovery state and fence generic cleanup;
- WorkManager cancellation acknowledgement alone should not be treated as publication quiescence either; the exact worker/effect owner must converge.

#### Required regression

Pause a real Terminal worker after `markNativeFinished()` and before/during publication, then:

- issue Terminal cancellation;
- inject failed or not-yet-quiescent WorkManager cancellation;
- prove durable cancel prevents any new destination publication;
- prove row/token/cache ownership are not retired before publication quiescence/recovery handoff;
- invoke TERMINAL_CACHE deletion and prove staging/journal/manifest remain protected;
- cover partial publication;
- cover unknown provider reservation;
- cover all output physically published before cancellation but before semantic commit;
- restart/reconcile and prove no post-cancel duplicate or replay.
