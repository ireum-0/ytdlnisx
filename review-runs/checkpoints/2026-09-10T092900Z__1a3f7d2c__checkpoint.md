## Confirmed finding

### NEW P2 — BUG-DUPLICATE-ADMISSION-01

Invariant: when duplicate prevention is enabled, duplicate determination and publication of a runnable Download must share one authoritative admission boundary. Once two producers resolve to the same semantic media/configuration identity, a stale pre-insert snapshot must not let both publish independent runnable rows.

Current production evidence:

1. `ObserveSourcesRepository.insert()` calls raw-URL `checkIfExistsWithSameURL(item.url)` and then performs a separate insert. The source entity has only an auto-generated id and no canonical URL uniqueness constraint.
2. `ObserveSourceWorker` fetches through `AutomaticKeywordNormalizer.canonicalPlaylistUrl(item.url)`, so distinct supported YouTube playlist URL spellings can converge to the same canonical playlist while retaining different source IDs.
3. `ObserveSourcesRepository.observeTask()` uses unique WorkManager name `OBSERVE<sourceId>`, so two such source rows are independent producer namespaces and can overlap.
4. Each `ObserveSourceWorker` snapshots pending Downloads and later `getActiveAndQueuedDownloads()` into process-local collections. `url_type`/`config` duplicate checks use that stale snapshot plus History. Only after `!isDuplicate` does the worker call `downloadRepo.insert(it)` and append the result to its own in-memory list.
5. `DownloadItem` has indexes only on status, downloadStartTime, and orderPosition. There is no semantic media/configuration unique admission key.
6. `DownloadDao.insert()` ultimately performs `@Insert(onConflict = REPLACE)` on `DownloadItem`; new Observe rows use `id=0`, so two independently inserted semantically identical candidates receive different generated primary keys rather than conflicting.

Concrete reproduction:

- create/retain two user Observe source rows whose raw URLs differ but canonicalize to the same supported YouTube playlist;
- both source-specific workers overlap on newly observed video V;
- W1 and W2 each snapshot no pending/active/history duplicate for V;
- both evaluate duplicate prevention as false;
- both insert id=0 Download rows for V/configuration;
- SQLite allocates distinct ids; both rows are runnable and may produce duplicate work/output/history effects.

## Why prior reviews missed it

Previous duplicate work concentrated on semantic identity normalization (F19) and producer-specific recovery/handoff. Those checks answer what should compare equal and whether a worker is recoverable, but they do not prove that check + publication is one shared admission transaction. In-process snapshots are locally updated after insert, which makes a single worker look closed, while two independent source workers retain independent snapshots.

## Checklist gap

The v6 concurrency and identity rules are sufficient in principle, but the operational duplicate module did not force an `identity resolved -> shared admission reservation -> publication` audit across competing producers. Per-producer duplicate snapshots could therefore be mistaken for authoritative exclusion.

## Proposed checklist change

For every duplicate-prevention policy, enumerate all concurrent producers that can target the same semantic identity and require an atomic/durable admission primitive shared by them. Inject `W1 snapshot -> W2 snapshot -> W1 insert -> W2 insert` and its cross-process/restart equivalents. A process-local snapshot, post-insert local list update, or auto-generated primary key is not duplicate-admission closure. Intentional redownload/bypass must use a distinct explicit authority rather than weakening normal admission.
