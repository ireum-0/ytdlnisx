## Open findings / candidates

### New root: destructive download/cache maintenance authority (P2)

1. `CleanUpLeftoverDownloads` takes Error/Cancelled row snapshots and later `deleteKnownUserRemoval` deletes by captured IDs without exact current status/execution/retry-generation CAS. A concurrent retry can make the row live after the snapshot and before deletion.
2. Periodic cleanup/manual Clear Cache use `activeCount == 0` as a gate, but no shared admission/maintenance lease exists before recursive `DOWNLOAD_TEMP` deletion. A new generation may start after the gate.
3. Move Cache has no active gate and moves artifacts selected by ownership-marker provenance without proving that the owning generation is no longer live.

### New root: recurring scheduling arithmetic (P2)

- `AlarmScheduler.scheduleRecurring` requires `sameDay` relative to the original scheduled day even when the configured recurring interval window crosses midnight. Example: 23:00–03:00, 2-hour interval; the 01:00 occurrence is within the interval but rejected by `sameDay`.

### New root: Observe durable handoff (P2)

- Manual Observe source edits update Room without co-updating WorkManager.
- Recurring worker commits the next-run DB state/clears execution token before `enqueueUniqueWork`; process death between those effects leaves DB schedule state without the successor work.

### New root: automatic-keyword rule durable handoff (P2)

- Rule update/enable state and periodic WorkManager schedule are separately committed. Repository mutation does not synchronously update/cancel the scheduler, so desired durable rule state and actual schedule can diverge.
