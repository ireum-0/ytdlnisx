## Revalidated open findings

### `BUG-LOCALADD-01` — existing P2 OPEN

`LocalAddStorageIdentityPolicy.relativePath()` still treats same-provider authority as enough to derive a tree-relative path by stripping `treeId` from `documentId`. Android's authoritative `DocumentsContract.Document.COLUMN_DOCUMENT_ID` contract says document IDs are provider-provided/interpreted opaque values and a document may be a child of multiple directories. Thus same provider plus textual prefix manipulation is not descendant proof. Distinct files can still collapse to one tree identity before final admission; the final transaction cannot repair an already-collapsed identity.

### `BUG-CLEANUP-01` — existing P2 OPEN

`CleanUpLeftoverDownloads.doWork()` calls `CleanupScheduleCoordinator.isCurrentOccurrence()` once before cleanup effects. `isCurrentOccurrence()` holds the coordinator lock only for the point check. The worker then performs foreground setup and destructive DB/cache cleanup outside that lock/lease. Concrete race remains: G worker checks true -> disable/reconfigure commits newer authority -> cancellation is requested -> already executing G continues destructive cleanup. WorkManager's cancellation contract is best-effort and already executing work may continue.

### `BUG-OBSERVE-HANDOFF-01` — existing P0 OPEN

`ObserveSourcesRepository.observeTask()` publishes ordinary work with only source ID. `ObserveSourceWorker.finishRunAndSchedule()` also publishes ordinary successor work with only source ID. Worker config-fingerprint rejection only runs when handoff fingerprint input is nonblank. Therefore the ordinary already-admitted worker still lacks an exact generation/config carrier that can prove stale execution exclusion after source reconfiguration.

## Exact upstream semantic basis used

- Android `DocumentsContract.Document.COLUMN_DOCUMENT_ID`: document ID is provided/interpreted by the provider, must be treated as opaque by clients, is unique within a provider, and one document may be a child of multiple directories.
- Android WorkManager: unique-work `REPLACE` cancels existing work; cancellation is best-effort and already executing work may continue; cancellation APIs expose completion futures/operations rather than turning the initiating call itself into application-level mutation authority.
- v6 core rules applied: positive live authority, discovery != mutation authority, async request != completion, identity/equality granularity, final mutation-boundary authority, semantic-contract consumer/effect closure, actual execution evidence requirement.
