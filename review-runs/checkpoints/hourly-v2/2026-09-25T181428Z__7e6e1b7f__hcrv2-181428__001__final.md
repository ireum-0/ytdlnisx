## Findings

### Existing P2 BUG-DUPLICATE-03 — new same-root recovery-identity residual

The generation-private archive is durable on app-owned storage under:

`download-archive-generations/<stableKey(downloadId, executionId)>.txt`

but the configured archive authority associated with that generation is not durable.

At initial `DownloadArchiveAuthority.prepare(context, downloadId, executionId)`:

1. `ConfiguredDownloadArchiveStore.resolve(context)` resolves the current configured authority;
2. a new `Generation` stores that authority only in memory as `configuredArchive`;
3. the private generation is seeded from that authority.

If the private generation already exists, `prepare()` does not re-seed it, but it still constructs the recovered `Generation` using a newly resolved **current** configured authority.

The durable recovery carriers do not bind the original configured archive identity:

- `DownloadPrimarySuccessAuthority` stores exact download/operation/execution identity, semantic fingerprint, `archiveDelta`, and phase, but no configured archive URI/raw authority identity;
- `DownloadProducerRecovery.Record` stores generation/execution/output identity and `archiveDelta`, but no configured archive authority identity;
- the private archive filename binds download/execution only.

After process death, `DownloadExecutionRecovery.finalizePrimarySuccessUnderLease()` calls:

`DownloadArchiveAuthority.promote(context, downloadId, executionId, fallbackDelta)`

which reconstructs through `prepare(context,...)` and therefore binds the surviving private archive to whatever `download_archive_path` is configured **at recovery time**.

Concrete failure sequence:

1. configured authority A is selected;
2. execution E seeds generation-private archive from A and later adds new archive entry C;
3. primary media success becomes durable and promotion/finalization remains pending;
4. process dies while private generation + durable primary-success authority survive;
5. before recovery convergence, configured archive preference changes from authority A to authority B;
6. recovery re-enters `prepare(context, downloadId, E)`;
7. the existing private file is reused, but `configuredArchive` is resolved as B;
8. recovery merges/promotes A-derived generation contents into B;
9. A can remain missing E's committed archive delta while B can inherit unrelated membership from A.

Process death therefore changes the authority to which the same exact generation is finalized. That violates the v6 recovery rule that recovery preserve the original semantic identity/authority rather than merely making progress.

This is within the existing BUG-DUPLICATE-03 root: its required result already demands an explicit provider-aware commit contract and safe recovery of authoritative archive synchronization.
