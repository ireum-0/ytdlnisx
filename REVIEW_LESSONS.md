# Review Lessons and Checklist Improvement Log

This file is an append-only meta-review ledger for correctness reviews of `checkpoint/pre-baseline-review`.

It does **not** define production truth and it does **not** replace the governing Review Checklist v4. Production correctness is always determined from the exact reviewed checkpoint SHA. This file records why a newly confirmed defect escaped earlier reviews and what general review rule could reduce the chance of the same class of miss recurring.

## Recording rule

Add one entry for every newly confirmed correctness defect discovered by a review run. The entry must be written only after the defect is independently confirmed on a production-reachable path and deduplicated against `TASKS.md` and `TASKS_DELTA.md`.

Do not write vague explanations such as "the review was incomplete" or "the file was overlooked." Identify the concrete review blind spot: an untraced outer catch, missing second-fault injection, reversed lock order, cross-domain identifier assumption, stale full-row writer, post-commit semantic reclassification, retry/re-entry gap, batch fault isolation gap, missing durable convergence carrier, restore normalization gap, platform capability/version mismatch, or another specific mechanism.

Checklist improvement proposals must be **generalizable**. Do not propose a rule that merely names the just-discovered function or patches one exact code path. State what invariant or review question would have exposed the defect class elsewhere too.

This log may recommend changes to Review Checklist v4, but it must not silently modify or supersede the checklist. Checklist changes require separate review and an explicit decision.

### 2026-08-23 — `BUG-SCHEDULER-05` — Pre-Android-12 exact-alarm capability false negative

- **Reviewed checkpoint SHA:** `dfa40697434b7d041bb0bc4f3d9cf2586dfb6d15`
- **Ledger defect entry:** `TASKS_DELTA.md` / `BUG-SCHEDULER-05`
- **Production-reachable failure path:** `DownloadSettingsFragment` permits `use_scheduler` on API 24–30 and calls `AlarmScheduler.schedule()` -> later queueing outside the window calls `AlarmScheduler.canSchedule()` -> helper returns false solely because `SDK_INT < 31` -> `DownloadViewModel` disables `use_scheduler`, does not persist the requested queue transition in that branch, and reports the exact-alarm permission failure.
- **Why earlier reviews missed it:** previous scheduler reviews concentrated on durable carrier identity, recurrence, alarm handoff, WorkManager cancellation domains, and stale ownership. The capability helper was treated as a trustworthy environment gate rather than reviewed as an authority function with version-dependent semantics. The inconsistency between callers also hid the defect: Settings explicitly treats the false value as permission-relevant only on API 31+, while the queue path treats the same false value as authoritative on every supported API level.
- **Checklist coverage at discovery time:** v4 already requires tracing production entrypoints and not stopping at helper names, but it does not explicitly require a platform-version truth table for capability/permission helpers. Retry/re-entry and carrier checks therefore focused on what happened after scheduling authority was granted, not whether the helper itself represented supported API bands correctly.
- **General lesson:** any platform capability or permission wrapper that gates a durable transition is itself an authoritative observation. Its truth value must be validated for every supported platform band, and all callers must assign the same semantic meaning to that value.
- **Proposed checklist improvement:** add a platform-capability/version matrix to the first-authoritative-observation and candidate-rejection steps whenever `Build.VERSION`, permission APIs, feature-detection helpers, or compatibility wrappers gate persistence, scheduling, destructive work, or terminal behavior.
- **Suggested checklist wording:** "For every platform capability/permission helper that gates a durable or user-requested operation, enumerate all supported API/version bands and permission states. Verify that each returned value matches the platform contract in that band, and compare all production callers for consistent interpretation. An API that does not exist on older supported versions must not be modeled as capability=false unless the underlying capability is actually unavailable there."
- **False-positive guard:** require (1) a supported runtime/API band, (2) a production-reachable caller whose behavior materially changes on the helper result, and (3) authoritative platform/library documentation or equivalent source proof that the helper's result misrepresents capability in that band.
- **Disposition:** `PROPOSED`

### 2026-08-23 — `BUG-ABI-01` — Published ABI lacks required FFmpeg runtime

- **Reviewed checkpoint SHA:** `dfa40697434b7d041bb0bc4f3d9cf2586dfb6d15`
- **Ledger defect entry:** `TASKS_DELTA.md` / `BUG-ABI-01`
- **Production-reachable failure path:** Gradle publishes `x86`, `x86_64`, `armeabi-v7a`, and `arm64-v8a` outputs -> the app-owned FFmpeg wrapper/runtime is authoritative because the library FFmpeg dependency is disabled -> only the arm64 app `jniLibs` tree contains `libffmpeg.so`/`libffprobe.so` and only arm64 assets contain `ffmpeg_payload.zip` -> non-arm64 startup derives an ABI-specific payload path, installation fails inside a swallowed `runCatching`, and startup continues -> `YoutubeDLCompat.resolveValidFfmpegLocation()` cannot authorize FFmpeg for yt-dlp while `DownloadWorker.resolveFfmpegRuntime()` falls back to the same nonexistent native `libffmpeg.so` candidate -> FFmpeg-required merge/post-processing fails, and a normal hard-sub request can burn zero media yet continue as an unburned successful download.
- **Why earlier reviews missed it:** earlier hard-sub and runtime reviews started from the assumption that a path returned by the runtime resolver corresponded to an executable packaged artifact. Review stopped at source-level resolver logic and runtime dependency repair rather than tracing the physical provenance of that executable through Gradle splits, app `jniLibs`, assets, and dependency packaging for every advertised ABI. The arm64 development path also masked the issue because it really does contain the expected files, making the resolver look valid when inspected on the dominant ABI alone.
- **Checklist coverage at discovery time:** the existing v4 items for first authoritative observation, helper-internal throwable windows, semantic preservation, filesystem authority, retry/re-entry, and test/wiring evidence all apply. They were not applied deeply enough across the build-artifact boundary: runtime availability was treated as an environmental premise instead of a capability whose backing files must be proven in each published artifact. The existing status note that per-ABI evidence remained necessary identified a verification gap but did not force the supported-ABI/package provenance matrix needed to expose deterministic absence.
- **General lesson:** any helper that returns a native executable, model, database seed, certificate, or other packaged runtime resource must be reviewed against the assembled artifact provenance for every published platform/ABI/build variant. Source code that names a path is not evidence that the artifact exists, and a fallback that returns an unusable path can turn a packaging omission into silent semantic downgrade.
- **Proposed checklist improvement:** add a packaged-resource provenance matrix whenever correctness depends on ABI-, architecture-, flavor-, or build-variant-specific files. Cross-check declared outputs, source-set contents, transitive dependency artifacts, installer/materialization logic, resolver fallbacks, and the terminal behavior when the resource is absent. Require one production-path verification per supported variant for resources that gate destructive or semantic post-processing.
- **Suggested checklist wording:** "When a production operation depends on a packaged native executable or other variant-specific runtime artifact, build a published-variant provenance matrix before accepting the resolver as authoritative: enumerate every advertised ABI/platform/flavor, prove which source set or dependency supplies the artifact and its required companions, trace installation/materialization failure, and verify the resolver cannot return an absent or unusable fallback. If a published variant lacks the resource, trace the real caller to its durable/terminal result and retry/restart behavior rather than classifying the gap as test coverage alone."
- **False-positive guard:** require (1) the affected ABI/platform/flavor is actually generated or otherwise production-supported, (2) the operation is reachable on that variant and materially requires the missing artifact, (3) repository/dependency evidence proves there is no alternate packaged supplier or runtime acquisition path that restores the same authority before use, and (4) the observed absence changes correctness or terminal semantics rather than only performance or an optional optimization.
- **Disposition:** `PROPOSED`

### 2026-08-23 — `BUG-HISTORY-04` — Destructive duplicate grouping trusts display title as identity

- **Reviewed checkpoint SHA:** `dfa40697434b7d041bb0bc4f3d9cf2586dfb6d15`
- **Ledger defect entry:** `TASKS_DELTA.md` / `BUG-HISTORY-04`
- **Production-reachable failure path:** History overflow menu -> destructive confirmation dialog -> `HistoryViewModel.deleteDuplicates()` -> `HistoryRepository.getDuplicateGroups()` -> downloaded History rows are grouped only by trimmed title and every non-oldest same-title row is selected -> keyword assignments are copied to the retained row -> `HistoryRepository.deleteRecords()` removes playlist cross-references and those History rows.
- **Why earlier reviews missed it:** previous History reviews concentrated on file-deletion authority, replacement identity, rollback/Undo, playback state, and cross-row reference safety. The duplicate-cleanup helper was implicitly treated as a benign classification step, so review did not ask whether its grouping key had enough authority to justify destructive record removal. Because titles are often unique in test fixtures, the helper also looks plausible under happy-path inspection even though title is mutable display metadata rather than media identity.
- **Checklist coverage at discovery time:** v4's first-authoritative-observation, semantic-preservation, expected-identity mutability, filesystem/reference authority, candidate-rejection proof, and post-commit checks all apply. They were not applied deeply enough to bulk classification helpers that manufacture a destructive target set before the repository mutation. The checklist says to prove authority at the mutation point, but it does not explicitly force reviewers to classify grouping/deduplication keys as identity claims and compare them against immutable provenance.
- **General lesson:** any grouping, deduplication, coalescing, or merge helper that feeds a destructive mutation is an authorization boundary. Display metadata, labels, names, titles, timestamps, or other collision-prone mutable fields cannot by themselves establish that two persistent records represent the same semantic entity.
- **Proposed checklist improvement:** add a destructive-grouping identity audit before any bulk delete/merge/replacement path. For every grouping key, enumerate realistic collisions and mutations, identify the immutable provenance needed to prove equivalence, and require revalidation of that provenance inside the same transaction/lock that performs destructive mutation.
- **Suggested checklist wording:** "When a bulk cleanup, deduplication, merge, or coalescing operation derives destructive targets from a grouping key, treat that key as an authorization claim. Prove that the key is collision-resistant for the semantic entity being destroyed, enumerate normal distinct records that can share it, and revalidate immutable provenance at the destructive boundary. Mutable/display fields such as title, name, label, timestamp, or formatted path are insufficient on their own. Also fault-inject between any pre-delete merge/copy step and the final delete to prove atomic or convergent behavior."
- **False-positive guard:** require (1) a production-reachable destructive bulk action, (2) two valid semantically distinct records that can satisfy the current grouping predicate without corruption or unsupported input, and (3) a concrete persistent mutation or loss that follows from that false grouping. Merely using a weak key for non-destructive UI grouping is not enough.
- **Disposition:** `PROPOSED`

### 2026-08-23 — `BUG-OBSERVE-04` — Observe Source revocation races with in-flight worker authority

- **Reviewed checkpoint SHA:** `dfa40697434b7d041bb0bc4f3d9cf2586dfb6d15`
- **Ledger defect entry:** `TASKS_DELTA.md` / `BUG-OBSERVE-04`
- **Production-reachable failure path:** Observe Sources pause/delete/delete-all UI -> `ObserveSourcesViewModel.stopObserving()` / `delete()` / `deleteAll()` -> WorkManager cancellation is requested but its asynchronous `Operation` is ignored -> STOPPED is written or the source row is deleted -> an already-running `ObserveSourceWorker` continues from a previously loaded `ObserveSourcesItem` snapshot -> stale ACTIVE state can still authorize `syncWithSource` History reconciliation, discovery/download side effects, and normal completion -> `finishRunAndSchedule()` can write the stale ACTIVE full row over STOPPED and enqueue a successor, or can perform post-delete side effects before the missing-row update becomes a no-op.
- **Why earlier reviews missed it:** earlier Observe Source reviews focused separately on snapshot completeness (`BUG-OBSERVE-01`), configuration writes that reset runtime counters/history (`BUG-OBSERVE-02`), and loss of recurring WorkManager carriers (`BUG-OBSERVE-03`). Cancellation helper calls were treated as an adequate lifecycle boundary, so the review did not build an authority-order graph between user STOP/delete, asynchronous WorkManager cancellation, the worker's stale full-row snapshot, destructive side effects, and successor scheduling. The stale-full-row checklist item was applied to UI/config writers but not symmetrically to a worker completing after a user-owned revocation.
- **Checklist coverage at discovery time:** v4 already requires filesystem/reference authority at the mutation point, retry/reconfigure inventory, expected-identity mutability, concurrency/exact ownership, stale full-row writer review, and candidate-rejection proof. Those items were relevant but were not applied deeply enough to cancellation as a revocation protocol: the review did not ask whether the cancellation request itself had completed, whether semantic authority was durably revoked independently of WorkManager transport state, or whether every later side-effect and completion write used an expected generation/status predicate.
- **General lesson:** lifecycle cancellation and semantic authority revocation are different operations. A cancellation API that is asynchronous or best-effort cannot be the sole correctness barrier when an in-flight actor already holds a mutable snapshot capable of destructive writes, queue creation, or self-rescheduling. Revocation must be represented durably and rechecked at every privileged side-effect boundary.
- **Proposed checklist improvement:** add a revocation-order matrix for stop/pause/delete/disable actions that race with workers or services. The matrix should record durable revocation write, cancellation request, cancellation completion, stale actor snapshot, each privileged side effect, completion write, successor creation, and restart behavior. Require expected-generation/status predicates or an equivalent lease so stale actors cannot restore revoked state.
- **Suggested checklist wording:** "For every user or system action that stops, pauses, deletes, disables, or otherwise revokes a background actor, distinguish semantic revocation from transport cancellation. If cancellation is asynchronous/best-effort, build the order `durable revoke -> cancellation request/completion -> stale actor side effects -> actor completion write -> successor enqueue`. Prove the stale actor checks current existence/status plus an exact generation/lease before every destructive, queueing, publishing, or rescheduling side effect, and prove its full-row completion cannot overwrite the revocation. Delayed or failed cancellation must not restore authority."
- **False-positive guard:** require (1) a production-reachable revocation action, (2) an actor that can already have loaded the pre-revocation state, (3) a concrete side effect or stale completion write reachable without a current-state/generation recheck, and (4) a materially incorrect post-revocation result such as destructive mutation, new work creation, or restoration of ACTIVE state. Merely allowing harmless cleanup after cancellation is insufficient.
- **Disposition:** `PROPOSED`

Open the ownership guard body: prove an already-owned call returns, queues, or otherwise cannot mutate concurrently; prove release is `finally`-safe; and prove completion is conditioned on the same still-current configuration generation. For A(old configuration) racing B(new configuration), execute or model both completion orders and prove stale A cannot overwrite the artifact or report current success after B has superseded it."
- **False-positive guard:** require (1) at least two production-reachable overlapping entrypoints or repeated invocations, (2) mutation of the same materialized runtime/artifact, (3) absence of an effective lock/queue/generation check at the mutation/commit boundary, and (4) a concrete completion order that changes durable or user-visible semantics. Concurrent read-only checks or provably idempotent same-generation work are insufficient.

### 2026-08-23 — `BUG-MIGRATION-01` — Default-video-folder migration deletes the old authority before durable reference publication

- **Reviewed checkpoint SHA:** `dfa40697434b7d041bb0bc4f3d9cf2586dfb6d15`
- **Ledger defect entry:** `TASKS_DELTA.md` / `BUG-MIGRATION-01`
- **Production-reachable failure path:** Folder settings -> migrate default video folder -> load video History rows -> select a path directly under the old default directory -> raw rename or copy / SAF copy creates the destination and removes the old source -> only afterward `historyDao.update(item.copy(downloadPath = updatedPaths))` publishes the new reference -> process death or Room failure before/at that write leaves History pointing to the now-missing old path with no durable old-to-new carrier; the same stale full-row write can also overwrite a concurrent History mutation.
- **Why earlier reviews missed it:** prior filesystem reviews concentrated on copy/delete correctness inside move helpers, SAF authority, retained-reference deletion, and live-cache ownership. The migration helper was read as a sequence of individually reasonable operations, and review stopped once the filesystem move itself returned a concrete destination. That missed the stronger cross-domain publication invariant: the destination is not semantically committed until the durable History reference is updated, while the helper irreversibly removes the old authority before that first persistence call. The later `HistoryDao.update()` wrapper also looked safer because it takes a reference-mutation lock and preserves materialized keywords, but opening it shows that it still performs a whole-row `@Update` and does not validate the migration's expected old path or protect unrelated fields from stale overwrite.
- **Checklist coverage at discovery time:** v4 carrier-creation gap, persistence barrier/first-write fault injection, multi-ledger/process-death durability, filesystem/reference authority, retry/restart, expected-identity mutability, stale full-row writers, concurrency, and terminal fault matrix were all directly relevant. They were not applied as one continuous filesystem-to-database commit protocol for this user-triggered migration; especially, first-write fault injection was previously focused on terminal Download/worker branches rather than migrations that make a destructive filesystem mutation before their first durable reference write.
- **General lesson:** any operation that relocates, replaces, renames, or publishes a referenced external artifact has a cross-domain commit point. A successful filesystem primitive is not completion if the durable History reference still points to the old artifact. Before the old authority is removed, the operation needs a durable recoverable mapping, atomic/compensating publication protocol, or another way to prove restart convergence. Reference-only mutations should also use field-owned/CAS writes rather than stale full-row updates.
- **Proposed checklist improvement:** add a referenced-artifact publication matrix for every move/rename/replace/import/export migration. Record old durable reference, new artifact creation, old artifact removal, first reference persistence, failure/process death at every boundary, durable recovery carrier, rerun behavior, destination collision identity, and concurrent reference/metadata mutation. Treat the first DB/reference write after a destructive filesystem step as a mandatory first-write fault-injection point even outside Worker terminal paths.
- **Suggested checklist wording:** "For every filesystem/provider move, rename, replacement, or migration of an artifact referenced by durable state, build the order `old durable reference -> new artifact creation -> old artifact removal -> new reference persistence`. Inject failure/process death before and after each boundary. The old authority must not be irreversibly removed before either the new reference is durably committed or a durable mapping/rollback carrier makes restart convergence deterministic. If the operation owns only a reference/path field, require an expected-old-identity/CAS or field-owned update; a stale full-row write must not overwrite concurrent state."
- **False-positive guard:** require (1) a production-reachable operation that changes the physical location/identity of an artifact already referenced by persistent state, (2) a boundary where the old artifact can become unavailable before the new reference or a recovery mapping is durably committed, and (3) a concrete restart/write-failure or concurrent-write ordering that leaves a stale/broken reference or loses a newer durable field. Pure copies that retain a valid old authority and have no destructive or reference-changing side effect are insufficient.
- **Disposition:** `PROPOSED`

### 2026-08-23 — `BUG-RUNTIME-01` — Bundled runtime replacement publishes destructively before verification

- **Reviewed checkpoint SHA:** `dfa40697434b7d041bb0bc4f3d9cf2586dfb6d15`
- **Ledger defect entry:** `TASKS_DELTA.md` / `BUG-RUNTIME-01`
- **Production-reachable failure path:** application startup or a production FFmpeg-resolution path -> `App.ensureRuntimeToolsInstalled()` -> revision mismatch makes `installBundledFfmpegPayload()` authoritative for replacement -> installer deletes the current live FFmpeg payload tree -> extracts/materializes the new revision directly into the same live path -> ZIP/filesystem or required-dependency copy failure is logged/swallowed rather than rolled back -> runtime resolvers accept directory existence or otherwise continue without a verified generation -> an FFmpeg-required yt-dlp/hard-sub operation can run against a missing/partial payload that replaced a previously usable runtime.
- **Why earlier reviews missed it:** the ABI review correctly traced whether each published package contained the runtime at all, but that review stopped once arm64 artifact provenance was established. The installer was then treated as a materialization helper whose `runtimeInstallLock` and revision marker implied safe publication. Opening the helper's mutation order shows a different invariant: it deletes the live known-good generation before staging/verifying the replacement, and nested dependency-copy catches can let the outer operation write the new revision marker despite an incomplete payload. Previous review therefore conflated package availability with failure-safe installation/promotion.
- **Checklist coverage at discovery time:** v4 carrier-creation gap, helper-internal throwable window, semantic preservation, filesystem/reference/cleanup authority, first-write/process-death fault injection, retry/restart, concurrency/exact ownership, and test/wiring evidence all apply. They were not applied as a generation-publication protocol for app-bundled runtime materialization. The `BUG-ABI-01` lesson's variant provenance matrix proves that bytes exist in the package, but does not ask whether a known-good installed generation remains authoritative until a replacement generation is completely verified.
- **General lesson:** packaged-resource availability and runtime publication are separate correctness questions. Any installer/upgrader that replaces a shared runtime, model, index, certificate set, database seed, or executable bundle needs generation semantics: stage privately, verify completeness, publish atomically, and retain or recover the previous verified generation until promotion succeeds. A lock only serializes attempts; it does not make destructive in-place publication failure-safe.
- **Proposed checklist improvement:** add a generation-publication matrix for installers/materializers of shared runtime artifacts. Record current verified generation, replacement trigger, first destructive mutation, staging identity, verification set, publish boundary, rollback/recovery carrier, nested swallowed failures, resolver acceptance predicate, process death at every boundary, and old/new generation behavior across retry/restart.
- **Suggested checklist wording:** "When an installer, updater, extractor, or materializer replaces a shared runtime/resource generation, distinguish artifact availability from publication safety. Build the order `current verified generation -> replacement decision -> staging/materialization -> completeness verification -> atomic promotion -> old-generation cleanup`. Inject failure/process death before and after each step and open nested helpers for swallowed per-file failures. The current verified generation must remain usable until the replacement is fully verified, and resolvers must prove the promoted generation's required contents/provenance rather than accepting directory/path existence. A mutex or revision filename alone is not proof of failure-safe publication."
- **False-positive guard:** require (1) a production-reachable replacement of an already usable shared artifact, (2) a real supported transition that can enter replacement, such as an application/runtime revision change, (3) a throwable or process-death boundary after old authority is destroyed but before replacement completeness is proven, and (4) downstream production behavior that depends on the now-missing/partial artifact. First-install failure with no prior usable generation, or a purely optional cache that is safely regenerated before any dependent use, is insufficient.
- **Disposition:** `PROPOSED`

- **Reviewed checkpoint SHA:** `ad1a8f026a7a05f3e1489775a74d8106dbfa510e`

- **Why earlier reviews missed it:** the earlier cache review found the analogous automatic `DOWNLOAD_TEMP` race (`BUG-CLEANUP-02`) and then treated the app cache category abstraction plus the Folder screen's explicit active-work check as sufficient coverage for manual cleanup. Review stopped at the presence of the second `hasActiveDownloads()` check before deletion instead of treating it as a revocable snapshot and enumerating each independently owned cache namespace. - **Checklist coverage at discovery time:** v4 first authoritative observation, filesystem/reference/cleanup authority, retry/re-entry inventory, cross-attempt matrix, expected-identity mutability, concurrency/exact ownership, candidate-rejection proof, and terminal fault matrix were all relevant. - **General lesson:** a maintenance path that recursively deletes a shared root must prove non-ownership at the mutation boundary for every actor namespace under that root. An aggregate "no active work" snapshot is not a lease: any actor that can become live after the snapshot needs either shared serialization with cleanup or a per-entry identity check immediately before deletion.
- **Proposed checklist improvement:** add a maintenance-vs-live-owner namespace matrix for cleanup, migration, vacuum, purge, and cache-management actions. Treat any earlier zero-count/idle check as a revocable snapshot. Between that observation and the first destructive mutation, prove either (a) a lock/lease/transaction prevents a new owner from being created, or (b) each entry is revalidated against exact current owner identity immediately before deletion while ownership acquisition is serialized with that decision. Do not inherit safety from a sibling cleanup defect or from an aggregate active-count helper when the underlying owner/carrier differs."
- **False-positive guard:** require (1) a production-reachable maintenance action that can select the affected category, (2) a production actor capable of acquiring/creating a resource under that category after the maintenance observation, (3) no shared ownership barrier or exact revalidation at deletion time, and (4) a concrete interleaving where deletion removes data the actor still requires and changes its durable/terminal behavior. Pure stale-cache deletion where no actor can reacquire the path until cleanup returns is insufficient.
- **Disposition:** `PROPOSED`

### 2026-08-24 — `BUG-LOCALADD-04` — Sequential Local Add batch loses sibling ownership on one entry failure

- **Reviewed checkpoint SHA:** `ad1a8f026a7a05f3e1489775a74d8106dbfa510e`
- **Ledger defect entry:** `TASKS_DELTA.md` / `BUG-LOCALADD-04`
- **Production-reachable failure path:** History Local Add selection -> `HistoryFragment` expands exact URI entries and persists a session -> one `LocalAddWorker` processes the list sequentially -> an entry-local provider/Room operation throws a non-cancellation exception inside a `try/finally` with no per-entry catch -> the exception exits `doWork()` -> earlier History inserts can remain committed, earlier unresolved candidates remain only in memory, and later selected siblings are never processed -> the input session key can remain in SharedPreferences but no failed-session successor/reconciliation path reacquires it, while the UI stops treating the work as active once it is no longer `RUNNING`/`ENQUEUED`.
- **Why earlier reviews missed it:** prior Local Add reviews decomposed the workflow into input identity (`BUG-LOCALADD-01`), input persistence before enqueue (`BUG-LOCALADD-02`), and unresolved-output durability at normal worker success (`BUG-LOCALADD-03`). That decomposition created a stopping assumption that once a session was stored and the worker had started, each loop iteration was effectively independent. The progress `finally` reinforced that impression, but review did not trace a per-entry throwable through the outer WorkManager result, the already committed sibling side effects, deferred in-memory pending output, later sibling execution, and the absence of a durable failed-session recovery owner.
- **Checklist coverage at discovery time:** v4 already requires helper-internal throwable windows, persistence barriers, multi-ledger/process-death durability, outer catch/final result, retry/re-entry inventory, concurrency/sibling isolation, candidate-rejection proof, test/wiring evidence, and a terminal fault matrix. Those items were applied deeply to concurrent Download children and terminal Download ledgers, but not equivalently to a sequential batch worker whose independent user-authorized items share one outer exception boundary and whose aggregate output is deferred until the loop finishes.
- **General lesson:** a sequential batch loop over independent durable intents has the same sibling-isolation obligation as a concurrent child scope. If one entry can fail after another entry commits, reviewers must identify who owns the unprocessed suffix, how already-produced aggregate output survives, and what durable carrier lets restart/retry resume exactly rather than relying on the original UI action.
- **Proposed checklist improvement:** add a batch-remainder fault matrix for workers/services that process multiple independently meaningful items under one outer result. For every item boundary, record prior durable side effects, deferred aggregate output, current-item throwable, later sibling state, batch terminal result, durable remaining-work carrier, restart discovery, and idempotent replay identity. Apply it to sequential loops as well as concurrent child scopes.
- **Suggested checklist wording:** "For any production worker/service that processes two or more independently user-authorized or independently durable items under one outer success/failure result, build a sibling/remainder matrix even when processing is sequential. Inject a non-cancellation failure at item N after item N-1 has committed. Prove (1) prior committed outcomes remain durably represented, (2) deferred output from earlier items is not lost, (3) unrelated items N+1... retain a discoverable durable owner or continue safely, (4) the outer result exposes partial/failure semantics rather than silently abandoning the suffix, and (5) retry/restart replays only the exact incomplete identities idempotently. A `finally` progress update or an orphaned input blob is not a recovery carrier by itself."
- **False-positive guard:** require (1) a production-reachable multi-item operation whose entries are semantically independent enough that partial per-entry commits are permitted by the implementation, (2) a real throwable boundary inside one entry, (3) at least one prior durable side effect or deferred earlier output plus at least one later sibling that can be stranded, and (4) no durable retry/reconciliation mechanism that automatically and exactly reacquires the incomplete suffix. A deliberately atomic transaction that rolls back every entry, or a batch with an explicit durable failed/remainder ledger and guaranteed replay, is insufficient.
- **Disposition:** `PROPOSED`
